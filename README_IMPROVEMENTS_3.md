# Infra Registry — реализация предложений по улучшению (шаг 3)

Продолжение пункта 4 приоритетного списка: перенос ещё одного редактора на общий helper
`attachNestedListEditor`.

## VLAN устройства — перенесён на attachNestedListEditor

Этот редактор был сложнее уже перенесённой пары (VM IP / VM Open Ports):
- список сортируется по числовому VLAN ID перед отображением, но `data-dv`-индексы в разметке
  должны указывать на реальную позицию в исходном массиве (не в отсортированном порядке) —
  иначе редактирование/удаление строки после сортировки затронуло бы не ту запись;
- удаление строки для уже сохранённого устройства должно немедленно удалять связь на бэкенде
  (не дожидаясь общего "Сохранить" формы устройства — это было отдельно исправлено ранее);
- добавление новой записи идёт не через «добавить пустую строку», а через отдельную модалку
  быстрого создания VLAN.

Под эти случаи `attachNestedListEditor` расширен двумя опциональными параметрами:
- `sortRows(rows)` — если передан, применяется перед отрисовкой; должен возвращать пары
  `[запись, исходный_индекс]`, чтобы `data-*`-атрибуты в разметке продолжали указывать на
  правильный элемент массива после сортировки;
- `onAfterRemove(removedRow)` — вызывается после удаления записи из локального состояния и
  перерисовки; используется для немедленного `DELETE` на бэкенде.

Для уже перенесённой пары (VM IP / VM Open Ports) эти параметры не передаются — поведение для
них не изменилось (проверено: `render()` без `sortRows` по-прежнему обходит записи в исходном
порядке, `remove()` без `onAfterRemove` работает как раньше).

Добавление новой VLAN-записи (через модалку) не тронуто — оно устроено принципиально иначе
(создаёт запись на сервере сразу, а не «пустую строку» для последующего заполнения), поэтому
`emptyRow`/`add()` для этого редактора не используются, что и предусмотрено необязательностью
этих параметров в helper'е.

## Проверка

- `node --check app.js` — чисто, дублирующихся объявлений функций/констант нет.
- Отдельно эмулирована в Node.js логика `sortRows`: подтверждено, что после сортировки по VLAN ID
  пары `[запись, индекс]` продолжают указывать на верную позицию в исходном (несортированном)
  массиве — именно это гарантирует, что `data-dv="${i}"` в разметке не потеряет связь с нужной
  записью.
- Полный тестовый набор backend (12 тестов) — без изменений в этой части, прогнан повторно для
  контроля побочных эффектов: 12/12 OK.

## Почему остальные два редактора (Порты/интерфейсы, детали ИС) не переносятся на этот helper

Оба намеренно оставлены как есть — не по недосмотру, а потому что решение шаблоном
«плоский список записей» для них не подходит без искусственного усложнения:

- **Порты/интерфейсы.** Каждая строка (интерфейс) сама содержит вложенный список — IP-адреса
  этого интерфейса, с собственной синхронизацией (`data-ip`/`data-j`). Это не плоский список, а
  список списков; втискивание в `attachNestedListEditor` потребовало бы либо игнорировать вложенный
  уровень (и вернуть дублирование на уровень ниже), либо добавлять в общий helper поддержку
  вложенности ради единственного случая использования — то есть искусственно усложнять
  универсальный код ради одного нетипичного потребителя.
- **Детали ИС.** Уже не так дублированы, как казалось на первый взгляд: `syncISDetails()` и
  `removeISItem(key, i)` (`app.js`) уже сейчас единой функцией обслуживают все четыре списка
  (подразделения/протоколы/источники/оборудование) через параметр `key`, а не четырьмя копиями
  кода. Структура состояния (`window.isEditor.details[key]`) отличается от «одна независимая
  глобальная переменная на список», которую использует `attachNestedListEditor` — переделка ради
  единообразия добавила бы риск при uже сравнительно небольшом фактическом дублировании.

Итог: unify стоит делать там, где он снижает реальное дублирование без искусственного усложнения
общего кода. Для оставшихся двух случаев это не так — доведение «всех пяти редакторов под один
helper» ради формального единообразия не соответствовало бы исходной цели рекомендации (снизить
риск регрессий), а создало бы новый риск другого рода.

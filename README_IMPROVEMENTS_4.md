## 1.2 (функционал) — важная находка. Внешние ключи в SQLite физически не проверялись

При разборе `db.py` обнаружено: SQLite объявляет `FOREIGN KEY` в схеме, но **не проверяет их**
на уровне БД, пока явно не выполнить `PRAGMA foreign_keys=ON` на каждом соединении — а это нигде
не делалось. На практике это означало: удаление, например, типа устройства, на который ссылаются
физические устройства, **проходило молча**, оставляя битые ссылки в других таблицах — ровно тот
риск, который был описан в исходном отчёте (п. 1.2), только хуже: даже уже существующий
`except IntegrityError` в `delete_resource` никогда не срабатывал на SQLite, потому что БД просто
не бросала эту ошибку.

Исправлено на двух уровнях:
1. **Корневая причина** (`db.py`): для SQLite-соединений теперь включается
   `PRAGMA foreign_keys=ON` через `sqlalchemy.event` — начинают реально работать уже объявленные
   в моделях ограничения.
2. **Понятное сообщение до попытки удаления** (`crud.py`): новая `_find_referencing_counts()`
   обходит реестр ресурсов, ищет колонки с FK на удаляемую таблицу и считает, сколько записей
   реально ссылается — так что вместо решения БД полагаться на исключение, пользователь сразу
   получает `409` с конкретикой: «Нельзя удалить: запись используется в других данных (Физические
   устройства: 3)» — а не на попытку удаления, тихо разваливающую данные, либо на общую фразу
   «на неё ссылаются другие объекты» без деталей.

Добавлен `backend/tests/test_referential_integrity.py` — 2 теста на реальной in-memory SQLite
через настоящий SQLAlchemy (для этого сценария мок неубедителен, нужна настоящая проверка FK).
В этом окружении fastapi/sqlalchemy не установлены, поэтому тесты корректно помечаются `skip`, а
не падают и не выдают ложный результат — они запустятся в окружении пользователя, где зависимости
есть. Дополнительно сам алгоритм обхода `MODEL_MAP`/сопоставления `target_fullname` проверен
отдельной лёгкой эмуляцией без реального SQLAlchemy — подтверждено, что он находит только реально
ссылающиеся колонки и не даёт ложных срабатываний.

## 2.3 (интерфейс). Предупреждение о несохранённых изменениях

Для двух самых объёмных форм приложения — «Физическое устройство» и «Информационная система»
(именно они были названы в исходном отчёте) — теперь при попытке закрыть форму с несохранёнными
изменениями (крестик или «Отмена») показывается подтверждение. Реализовано через сравнение снимка
состояния формы (обычные поля + вложенные редакторы — интерфейсы/VLAN устройства для устройства,
все детали ИС) в момент открытия и в момент попытки закрытия.

Специально ограничено этими двумя формами, а не всеми: остальные (справочники, подключения,
интерфейсы как отдельный ресурс, типы устройств, VLAN) при закрытии продолжают вести себя ровно
как раньше — `captureFormSnapshot()` возвращает `null` для прочих типов ресурсов, и в этом случае
`closeModal()` не показывает диалог, полностью сохраняя прежнее поведение. После успешного
сохранения (в любой из шести точек, где это происходит) диалог не показывается — `closeModal(true)`.

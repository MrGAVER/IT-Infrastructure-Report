# История изменений

Сводная хронология версий проекта — ранее находилась в `README.md`, начиная с версии 2.77.0
вынесена в отдельный файл, чтобы `README.md` не разрастался (собрана из всех ранее отдельных
`README_*.md` файлов проекта).

### 2.1 — исправление 404 на `/` в EXE
Путь к `frontend` теперь передаётся launcher-ом в EXE явно (`INFRA_REGISTRY_FRONTEND_DIR`), вместо
косвенного определения через расположение `main.py` внутри PyInstaller `_MEIPASS`. `GET /` в EXE
корректно отдаёт `frontend/index.html`.

### 2.2
- В форме физического устройства у полей «Тип устройства», «Производитель», «Модель», «Здание»,
  «Помещение», «Стойка» появилась кнопка быстрого добавления записи `＋` без перехода в справочники.
- Поле «№» ИС и колонка «№» листов 2–3 больше не вводятся вручную — нумерация всегда генерируется
  автоматически при экспорте.

### 2.5
Модель физического устройства однозначно связана с производителем и типом устройства (например,
Huawei 2288 нельзя выбрать как модель коммутатора) — в форме устройства модели фильтруются по
обеим характеристикам.

### 2.8 (ранее также фигурировала как 2.7)
- ОС физического устройства отображается в формате «Наименование + версия».
- Внешние ключи в списках и связях отображаются человекочитаемыми значениями вместо UUID.
- «Порт управления» стал свойством интерфейса; интерфейсы редактируются в едином окне формы
  устройства, с возможностью сгенерировать их по количеству портов (шаблоны `{n}`, `{n0}`).
- У интерфейса появился признак «Управление», используемый при формировании Excel.
- Добавлен атомарный API `PUT /api/v1/devices/{device_id}/interfaces`.

### 2.11
- Добавлены идемпотентные стандартные значения в справочники типов устройств, ОС/гипервизоров и
  скоростей интерфейсов (не удаляют пользовательские записи).
- Поля «Порт управления», «IP управления», «Количество интерфейсов» скрыты из основной формы
  устройства — ведутся в редакторе «Порты / интерфейсы».
- Миграция `f2a9c7d1e530_standard_catalog_values`.

- Backend: `main.py` стал минимальной application factory; CRUD, валидации, сериализация и

  индексы на часто используемые FK/поисковые запросы.
- Frontend: CSS и JS вынесены из `index.html` в `app.css`/`app.js`, отдаваемые через `/static`.
- Миграция `3a7c1e5d9b20_performance_indexes.py` (индексы для зданий/помещений/стоек, каталога,
  устройств, интерфейсов/IP, подключений, ОС и ВМ).

### 2.37.0 — устранение критичных замечаний по итогам код-ревью

- **Безопасность (без аутентификации — вынесена отдельно на потом):**
  - CORS больше не выдаёт `allow_credentials=True` вместе с origin `*` (небезопасная комбинация,
    заставлявшая браузер отражать любой вызывающий origin как доверенный). Список разрешённых
    origin'ов теперь настраивается через `INFRA_REGISTRY_CORS_ORIGINS` (по умолчанию `*` — для
    локальной сети/однопользовательского режима этого достаточно).
  - Пароль PostgreSQL вынесен из `docker-compose.yml` в `.env` (пример — `.env.example`); без
    заданного `POSTGRES_PASSWORD` `docker compose` теперь отказывается стартовать, а не тихо
    использует дефолтный пароль.
  - Docker-образ backend теперь запускается от непривилегированного пользователя `app`, а не от
    root; добавлен `HEALTHCHECK` (раньше был только у сервиса `db`).
  - `POST /api/v1/seed/test` (кнопка «Заполнить тестовыми данными») можно отключить переменной
    `INFRA_REGISTRY_ENABLE_TEST_DATA=0` для серверных развёртываний, где такая кнопка не нужна
    нескольким сотрудникам; по умолчанию осталась включена, чтобы не менять текущее поведение.
- **Качество кода / рефакторинг:**
  - 9 мест, где `except ... raise HTTPException(...)` терял исходный traceback, теперь
    пробрасывают причину через `raise ... from exc`.

### 2.39.0 — шаблон конструктора с точным воспроизведением регламентированного отчёта

При обновлении (data-миграция `b1f0a2265711`, применяется автоматически как обычная alembic-
миграция и в Docker, и в EXE-сборке) в конструктор отчётов добавляется готовый шаблон
**«Регламентированный отчёт — заготовка (4 листа)»** — те же 4 листа, те же заголовки колонок и,
что важнее, **то же содержимое строк**, что и у фиксированного регламентированного отчёта (кнопка
«Отчёт Excel» на дашборде), но собранный через grid-движок конструктора (`report_grid.py`), то
есть открытый для правки в визуальном редакторе (см. запись 2.38.0 выше).

- **Как достигнута точность 1:1, а не приближение.** Первая версия этой задачи (в рамках этой же
  ветки) пыталась выразить логику `reporting.py` обобщёнными путями полей конструктора (вида
  `a.b[].c`) и упёрлась в принципиальные ограничения этой модели — часть логики оригинала (цепочки
  резервных источников данных, объединение нескольких связей в одну колонку, фильтрация списка по
  вложенному признаку, открытые порты с полиморфным владельцем) обобщённым путём не выражается.
  Решение — `backend/app/services/report_registry_rows.py`: 4 "виртуальные" сущности конструктора
  (без своей таблицы в БД), каждая строка которых считается ДОСЛОВНО ТЕМИ ЖЕ функциями, что и сам
  `reporting.py` (`_is_row_values`/`_device_row_values`/`_connection_row_values_list`/
  `_vm_row_values` — вынесены из `reporting.py` в переиспользуемые функции, поведение исходного
  отчёта не изменилось ни на бит, проверено полным прогоном `test_reporting.py` до и после
  рефакторинга). У виртуальной сущности нет связей для обхода — все поля уже плоские, конструктору
  достаточно взять готовое значение по имени, поэтому обобщённые ограничения путей полей здесь
  просто не участвуют.
- Технически это новая возможность самого grid-движка, не только этого шаблона: сущность в
  конструкторе теперь может быть не только таблицей БД (`MODEL_MAP`), но и "виртуальной" —
  плоским списком уже посчитанных строк от функции-загрузчика (`ReportContext.all_rows()` в
  `report_engine.py` вызывает её вместо `SELECT`). Другие части приложения при желании могут
  зарегistrировать свои вычисляемые представления по этому же образцу.
- Точность проверена не только структурно: `backend/tests/test_report_registry_rows.py::ExactParityTestCase`
  строит ОБА отчёта (оригинал и шаблон конструктора) на одних и тех же тестовых данных (включая
  подключённые/неподключённые порты, VLAN, открытые порты устройства и ВМ, СКЗИ, привязку ИС и
  через актуальную модель источников, и через устаревшие таблицы-фолбэки) и построчно/поколоночно
  сравнивает содержимое ячеек — включая заголовки, не только данные.
- Лист 3 «Организация подключений» — по-прежнему по одной строке на каждый физический порт
  (подключённый или нет), с той же группировкой неподключённых портов по IP-сигнатуре и тем же
  порядком строк, что и в оригинале — теперь без структурных отличий.
- Оригинальный регламентированный отчёт (`reporting.py`, кнопка «Отчёт Excel») не изменился по
  наблюдаемому поведению и не затрагивается этим шаблоном — использует ту же общую логику, что и
  шаблон конструктора, а не наоборот, поэтому расхождений между ними впредь быть не должно (если
  вы отредактируете сам шаблон в конструкторе — это, конечно, изменит именно шаблон).
- Вставка идемпотентна (не дублирует шаблон при повторном `alembic upgrade head`) и не удаляет
  шаблон при откате (`downgrade`), если пользователь успел отредактировать его конфигурацию через
  конструктор после обновления — откат схемы не должен молча уничтожать пользовательскую правку.
- Тесты: `backend/tests/test_report_seed_templates.py` (структурная валидация конфигурации,
  поведение data-миграции — вставка/идемпотентность/безопасный откат в обоих сценариях) и
  `backend/tests/test_report_registry_rows.py` (регистрация виртуальных сущностей в общих
  метаданных конструктора, точная эквивалентность содержимого с оригиналом — включая граничный

### 2.40.0 — фикс: EXE падал на старте после 2.39.0

проекте отработало исправно уже на следующей проверке, вероятная причина конкретно этого падения

### 2.41.0 — фиксы grid-редактора и шаблона по обратной связи пользователя

- **Текст в ячейках сгенерированного `.xlsx` обрезался по высоте строки.** openpyxl, в отличие от
  интерактивного Excel, не пересчитывает высоту строки под перенесённый текст сам — заданная в
  конфигурации высота применялась как есть, независимо от того, сколько строк реально займёт
  текст при переносе. `report_grid.py`: новая `_estimate_row_height()` — осторожная оценка снизу
  (число строк текста при переносе с учётом ширины колонок и объединений, ~15pt на строку, потолок
  400pt), применяется как `max(заданная высота, расчётная)` — не сжимает то, что задано намеренно,
  но не даёт клетке оказаться меньше, чем нужно для содержимого. Тот же приём "символов на юнит
  ширины", что уже использует сам регламентированный отчёт (`reporting.py: finalize_sheet`) для
  подбора ширины колонок по факту содержимого.
- Заодно расширены колонки шаблона-заготовки, где значения типично длинные (списки через `; `) —
  оборудование, IP-адреса, протоколы, открытые порты, VLAN.
- **Строка "Лист — по состоянию на `{{report_date}}`" убрана** из всех 4 листов шаблона-заготовки
  — в оригинальном регламентированном отчёте такой строки нет, а задача шаблона — совпадать с
  оригиналом. Теперь оба отчёта совпадают ещё точнее: данные начинаются с той же строки листа
  (2-й, сразу после заголовков), что и в оригинале.
- **Кнопки действий в списке шаблонов конструктора** (Изменить/Сформировать/Дублировать/История/
  Удалить) перенесены из последней колонки таблицы в первую — раньше при длинном описании шаблона
  или узком экране до них приходилось скролить по горизонтали при каждом обращении к списку.
  Колонка "Описание" теперь переносится по словам с ограничением ширины вместо `nowrap`, чтобы не
  растягивать таблицу неограниченно.
- **Наползающие друг на друга поля/недоступные кнопки в самом grid-редакторе** — причина:
  `table-layout:fixed` на таблице листа фиксирует ширины колонок по первой строке (шапке с
  буквами колонок), а не по факту содержимого; шапка строки (кнопки ⚙/+/✕ + поле высоты) при этом
  сжималась в узкую колонку и накладывалась на соседние ячейки. Убран `table-layout:fixed`,
  содержимое шапки строки обёрнуто в flex-контейнер с переносом вместо `white-space:nowrap`.
- Тесты: `EstimateRowHeightTestCase` + 2 интеграционных теста в `BuildXlsxGridTestCase`

### 2.63.0 — задел на многопроцессный деплой (concurrency-safety)

Последний пункт из «возможных улучшений» 2.62.0 — не полноценный Redis/распределённый кеш (для
однопроцессного локального/EXE-сценария это было бы избыточно), а закрытие конкретных гонок,
которые реально проявляются только при нескольких ОДНОВРЕМЕННО пишущих процессах backend за общей
БД (см. «Быстрый старт» — серверный вариант, Docker + PostgreSQL).

- **Гонка «оба администратора разжалованы одновременно»**: `ensure_not_last_admin` раньше делала
  check-then-act («посчитать активных админов, потом изменить») — классический TOCTOU. Два admin'а
  A и B, каждый на своём процессе, одновременно разжалующие СЕБЯ ИЛИ ДРУГ ДРУГА, оба видели друг
  друга как «ещё есть один admin» и оба проходили проверку → ноль администраторов. Исправлено:
  `SELECT ... FOR UPDATE` по ВСЕМ активным администраторам (не «остальным, кроме текущего» — иначе
  блокировки над A и над B не пересекались бы и гонка сохранялась) перед проверкой и мутацией в
  одной транзакции. На PostgreSQL это реальная блокировка строк; на SQLite — безопасный no-op
  (диалект не рендерит `FOR UPDATE`, проверено эмпирически) — там гонки и так нет, SQLite
  сериализует писателей на уровне файла БД целиком.
- **Атомарный счётчик неудачных попыток входа**: было `user.failed_attempts += 1;
  session.commit()` — read-modify-write в Python. Два параллельных неверных пароля от одного
  пользователя на разных процессах могли прочитать один и тот же счётчик и оба записать n+1
  вместо n+2, теряя попытку из порога блокировки. Заменено на `UPDATE ... SET failed_attempts =
  failed_attempts + 1` одним SQL-запросом — атомарно на уровне БД независимо от числа процессов.
- **Самоочистка `auth_sessions`**: каждый логин (`create_session`) заодно удаляет ВСЕ просроченные
  сессии всех пользователей — без этого таблица только росла (строка убиралась явно лишь при
  logout или попытке использовать именно этот истёкший токен). Это ленивая уборка, не
  cron/планировщик: безопасна при любом числе процессов, поскольку `DELETE ... WHERE expires_at <
  now()` идемпотентен — два процесса, одновременно решившие подчистить одну и ту же строку, друг
  другу не мешают.
- Мёртвый код: `count_active_admins` (некритичный к гонкам подсчёт) удалён — после перехода
  критичных проверок на блокирующую `_lock_active_admins` он больше нигде не вызывался.
- 5 новых тестов (компиляция `FOR UPDATE` на диалекте PostgreSQL, атомарность инкремента, уборка
  просроченных сессий) — сам факт гонки под нагрузкой синхронный SQLite-тест не воспроизводит
  (нужен реальный параллелизм нескольких процессов), поэтому тесты фиксируют защитный SQL и
  наблюдаемое поведение уборки, а не гонку напрямую. Полный прогон: 241 pytest — зелёные.

### 2.78.0 — экспорт диаграмм: визуальный паритет .drawio/.vsdx с .svg (Фаза 1 плана доработок экспорта)

Реализована Фаза 1 отдельного отчёта-анализа экспорта диаграмм (.drawio/.vsdx на фоне эталонного
.svg): семь пунктов низкого риска, без изменения структуры графа.

1. **Находка №1 отчёта («.vsdx открывается пустым листом») подтверждена напрямую** (headless
   LibreOffice, `soffice --headless --convert-to png`, не только по описанию) и устранена — при
   более глубоком разборе причина оказалась не одна, а три одновременно:
   - библиотека `vsdx` 0.6.1 при импорте регистрирует четыре разных namespace на один и тот же
     пустой префикс подряд (`ET.register_namespace('', ...)` × 4) — из-за особенности
     `xml.etree.ElementTree.register_namespace` (новая регистрация вытесняет предыдущую с тем же
     префиксом) итоговый default-namespace остаётся только у последнего из четырёх; остальные
     части пакета при `save_vsdx()` сериализуются с синтетическим `xmlns:ns0=` — сторонние
     читатели такой файл не открывают, хотя сама `vsdx` читает его без единой жалобы;
   - `Shape.remove()` (та же библиотека) удаляет только сам элемент `<Shape>`, не трогая секцию
     `<Connects>` — при удалении шаблонных фигур на странице оставались висячие ссылки
     `FromSheet`/`ToSheet` на уже не существующие ID;
   - формулы динамической «приклейки» коннектора (`_WALKGLUE`/`_XFTRIGGER(Sheet.N!...)`),
     скопированные из шаблона дословно вместе с фигурой, ссылались по имени на те же удаляемые
     шаблонные фигуры.

     Фикс — не патч самой библиотеки, а постобработка результата (`_finalize_vsdx_package`):
     единственная часть пакета, которую граф реально меняет — сама страница с фигурами;
     все остальные части (мастера, настройки документа, метаданные, декларация content-types)
     теперь всегда берутся как есть из пристинного шаблона `media.vsdx`, а не из того, что с ними
     сделал `save_vsdx()`. Заодно поправлена сама формула Y-координаты: ось Y в Visio растёт
     снизу вверх от нижнего края страницы, а не сверху вниз, как в `.svg`/канвасе — простой смены
     знака недостаточно (вся диаграмма уходила ниже нижнего края страницы), нужно было ещё
     учитывать высоту страницы шаблона (`page.height`) и точку привязки фигуры (центр, а не левый
     верхний угол).
2. **`.vsdx`: цвет узла-устройства** — `shape.fill_color`/`shape.line_color` из цвета категории
   иконки (для custom-иконок, у которых цвета в дескрипторе нет вовсе — нейтральный fallback),

5. **Стрелки на связях `.drawio` убраны** (`line_end_source`/`line_end_target="none"`) — связь

6. **Скруглённые углы узлов в `.drawio`** (`rounded=1`) — паритет с `rx="8"` в `.svg`/канвасе.
7. **Тест на паритет атрибутов и открываемость файла** — один и тот же граф (с группой и
   неактивным ребром) прогоняется через все три экспортёра, проверяется совпадение «цвет узла

### 2.83.0 — экспорт диаграмм: растеризация иконок категорий для .vsdx (Фаза 3, п.5 плана доработок экспорта, часть 2)

Завершает находку №5 отчёта об экспорте диаграмм для всех трёх форматов.

XML-разметка (`Shape`/`ForeignData[ForeignType=Bitmap]`/`Rel[@r:id]`) сверена дословно с
официальной спецификацией MS-VSDX (openspecs) — `ObjectWidth`/`ObjectHeight` у `ForeignData`
помечены в спецификации как unused/ignored для `Bitmap`, поэтому размер задаётся обычными

картинкой целиком) в той же позиции/размере, что и в `.svg`/`.drawio`.

без системных Cairo/librsvg. Один PNG на уникальный `glyph`, а не на узел (белый цвет не зависит
от заливки узла, картинка кладётся поверх с прозрачным фоном) — де-дупликация для графов с
повторяющимися категориями. Новый `_embed_vsdx_category_icons` дописывает `media/imageN.png`,

`_finalize_vsdx_package`, а не вместо неё.

**Честная находка, не подтверждённая визуально**: XML корректен по спецификации, но ни headless
LibreOffice, ни другой доступный инструмент саму картинку не показывает — похоже на отсутствие
поддержки `ForeignData`/`Bitmap` в конкретно этом импорт-фильтре (`libvisio`), а не на ошибку в
разметке. LibreOffice не крашит и не пустит весь лист — тихо откатывает фигуру на обычную
геометрию, поэтому `icon_shape` явно очищает `text`/`fill`/`line`, чтобы фолбэк был опрятным
белым прямоугольником, а не унаследованным от шаблона текстом «RECTANGLE». Внедрено по решению
пользователя («внедряй, проверим позже») без доступа к настоящему Visio для подтверждения —
задокументировано в README и памяти проекта, к перепроверке при появлении доступа к Visio.

### 2.89.0 — InformationSystemSource: physical_device_id/virtual_machine_id/container_id объединены в owner_id

По итогам вопроса 5 (последнего из 9) отчёта по анализу БД: у `information_system_sources` было

Ключевое отличие от тех трёх: там полиморфный владелец ВЛАДЕЕТ дочерней записью (запись должна

регуляторного отчёта. `owner_id` НЕ является настоящим FK (одна колонка не может физически
ссылаться на три разные таблицы), поэтому защита воссоздана вручную в `crud.py:delete_resource()`

рассмотрения архитектурной развилки: не откладывать защиту «на потом».

Миграция `944bd490d967`: на SQLite — пересборка таблицы (как в `d8e35a1c7f60`), на PostgreSQL —
`ADD COLUMN` + backfill `COALESCE(...)` + `DROP COLUMN` на все три колонки. `downgrade()` не
поддерживается — тот же принцип, что и в остальных миграциях серии.

`vmOptions` по `owner_id`, а для ещё не выбранной ВМ используется отдельное клиентское поле
`vmHostHint` (в payload на backend не попадает).

### 2.90.0 — защита ссылочной целостности для owner_id без FK: пять уровней, рабочий downgrade

По итогам п.3 предложений после переработки БД (2.89.0): `InformationSystemSource.owner_id` (как
и `owner_id` у `OpenPort`/`DeployedSoftware`/`IPAddress`) — не настоящий FK, а вся защита от
удаления держалась на одном месте, `delete_resource()`. Любой новый путь удаления в обход него
молча оставлял бы «висячие» ссылки. Добавлены все пять уровней защиты (`services/integrity.py`):

1. `crud.assert_deletable()` — единая точка проверки «можно ли удалить» (FK-ссылки + `owner_id`-
   ссылки источников ИС); `delete_resource()` теперь вызывает её. Единый текст 409 —
   `format_referenced_message()`.
2. `before_delete` на `PhysicalDevice`/`VirtualMachine`/`Container` — срабатывает на любое
   ORM-удаление в обход `delete_resource()`; в HTTP-слое `ReferencedRecordError` превращается в
   тот же 409 с тем же кодом (обработчик в `main.py`), а не в 500.
3. Триггеры БД (миграция `5b1e7c94a2d8`) — `BEFORE DELETE` на `physical_devices`/`virtual_machines`/
   `containers`: последний рубеж, ловит и прямой SQL. SQLite — `RAISE(ABORT)`, PostgreSQL — функция
   на plpgsql с SQLSTATE 23503. Обе ветки проверены: SQLite — тестами, PostgreSQL 16 — реальным
   прогоном upgrade → блокировка → downgrade → повторный upgrade.
4. Диагностика: `find_orphaned_owner_references()` и `GET /api/v1/integrity` находят уже существующие
   «висячие» ссылки во ВСЕХ четырёх моделях без FK (плюс записи с неизвестным `owner_type`);
   только чтение.
5. Статическая проверка исходников (`tests/test_deletion_guards.py`): любой новый путь прямого
   удаления в `app/` (`session.delete`, `delete(...)`, `.query().delete()`, сырой `DELETE FROM`),
   не внесённый в `ALLOWED_DELETIONS`, роняет тест; Core-удаление защищённых моделей запрещено
   безусловно.

**Downgrade теперь обязан работать** (требование проекта для всех новых миграций): `downgrade()`
миграции `5b1e7c94a2d8` снимает триггеры и функцию, данных не меняет; проверен тестом (upgrade →
downgrade → upgrade). Прежние миграции серии с заглушкой `RuntimeError` не менялись.

Ограничения (описаны в `services/integrity.py`): `before_delete` не видит массовое Core-удаление
(его ловят триггер БД и статический тест); если в одной транзакции удаляются источник ИС и его
владелец, источник нужно удалить и сделать `flush()` раньше владельца. На SQLite пересборка
защищённой таблицы в будущей миграции удалит её триггер — это ловит тест на `head`.

Backend: 578 pytest (+32: 10 на миграцию с триггерами, 22 на защиты и диагностику), ruff check —
зелёные. Frontend без изменений: 772 vitest, vue-tsc -b, vite build — зелёные.

### 2.101.0 — «Применить текущую конфигурацию» по режиму порта: смена режима у группы соседа и связанных портов

Проблема: «Применить текущую конфигурацию» (окно расхождения режима порта в форме устройства) писало
режим соседнему порту прямым запросом и не знало о группах. Если порт соседа входил в группу, задающую
режим, значение возвращалось при следующем сохранении его устройства, и расхождение появлялось снова
без предупреждения. Менять режим у всех портов группы и у связанных с ними портов приходилось вручную.

Теперь режим меняется целиком, а область изменения считается так, чтобы на её границе расхождений не
осталось (`services/vlan_mode_cascade.py`). Замыкание от порта соседа:
- порт в группе, которая задаёт режим, меняется вместе со ВСЕЙ группой (все её порты и список VLAN группы);
- у каждого меняемого порта соседи по активным подключениям тоже должны получить целевой режим: если он у
  них другой, они (и их группы) входят в область, и так далее по цепочке устройств. Порты, у которых режим
  уже целевой, в область не входят и дальше не распространяют; неактивные подключения не учитываются.

Правила для VLAN при смене режима (как у переключателя режима в форме устройства):
- trunk → access: у порта или группы остаётся один VLAN (с наименьшим номером), остальные снимаются —
  список снимаемых VLAN показывается до применения;
- access → trunk: остаются уже назначенные VLAN, «все VLAN» автоматически не добавляются (операция не
  придумывает конфигурацию на чужих устройствах).

Предупреждения о последствиях показываются в окне подтверждения до применения: сколько портов, устройств и
групп изменится; что режим группы меняется у всех её портов; что изменения на других устройствах применяются
сразу и не отменяются кнопкой «Отмена» формы (записываются в журнал аудита по каждому устройству); что
изменения устройства формы попадут в форму и сохранятся только после «Сохранить» (иначе у соседей режим уже
другой и расхождения появятся снова); какие VLAN будут сняты и что это изменит VLAN ID и VLAN Name в отчётах
и на диаграммах; что неактивные подключения не учитываются; предупреждение, если область больше 100 портов.
Применение требует отметки «Я ознакомился с последствиями». Простой случай (один порт без групп и снимаемых
VLAN) применяется сразу, как раньше.

Устройство с открытой формой. Форма сохраняется целиком, поэтому сервер порты и группы этого устройства не
пишет: они возвращаются в плане (`deferred`), а клиент вносит изменения в черновик формы. План считается по
состоянию ЧЕРНОВИКА (режимы портов и групп форма присылает в `edited`), а не по БД: порт, у которого в форме
уже целевой режим, в область не входит — иначе окно подтверждения появлялось бы всегда и называло
«изменяемыми» порты, у которых в форме всё верно.

API (`api/port_config.py`):
- `POST /api/v1/interfaces/{id}/vlan-mode-cascade/preview` — тело `{mode, edited?}`; план: группы, порты, снимаемые
  VLAN, предупреждения и `hash`. Ничего не записывает.
- `POST /api/v1/interfaces/{id}/vlan-mode-cascade` — тело `{mode, edited?, plan_hash, confirm: true}`; одна
  транзакция. Без `confirm` — 422; если данные изменились после предпросмотра (hash не совпал) — 409 вместо
  применения не показанного пользователю плана: форма запрашивает новый план и просит подтвердить заново.
- Предел области — 1000 портов (422 с подсказкой менять режим по частям).

Ограничения: «Применить конфигурацию соседа» (взять режим соседа себе) для порта, чей режим задан его группой,
по-прежнему отклоняется с подсказкой «измените в группе»; принадлежность портов редактируемого устройства к
группам берётся из БД (не из черновика); назначение порта («Упр.» / «Данные») группы не задают и этим
механизмом не затрагиваются.

Проверено: backend pytest, ruff; frontend vue-tsc -b, vitest, vite build.

  подключение с расхождением молча. Для режима и VLAN подсказывает «Управлять портами»; если после выравнивания
  роли режим или VLAN всё ещё различаются, форма спросит про остаток. Расхождение, одобренное ранее и не изменившееся,
  повторно не спрашивается; неактивное подключение расхождением не считается.
- Сверку для формы делает сервер теми же правилами, что и дашборд: `GET /api/v1/connections/port-config/preview?
  source_interface_id=&destination_interface_id=&connection_id=&is_active=` → `{status, diff, source, destination}`
  (ничего не записывает; 404 для неизвестного порта/подключения). Поэтому предупреждение формы и статус на дашборде
  не расходятся. Если сервер не ответил, форма сверяет хотя бы роли по каталогу, как раньше (режим и VLAN тогда не
  показываются). «Сохранить» сразу после выбора порта дожидается ответа сервера; сверка пересчитывается при смене
  пары портов, активности, роли/режима и после «Управлять портами».

Известные ограничения: сверка по-прежнему строгая — порт сервера (trunk, без VLAN) против access-порта коммутатора
считается расхождением (идея: сверять режим и VLAN только у сетевых категорий устройств — не реализовано);
журнал аудита доступен только на чтение, экспорт не добавлялся.

Проверено: backend pytest, ruff, pip-audit, alembic upgrade head (с нуля, один head); frontend vitest, vue-tsc -b,
vite build, npm audit.

### 2.103.0 — каскад смены режима порта: «взять режим соседа» для порта из группы, состав групп из черновика, дашборд «Подключения»

Три ограничения каскада из 2.101.0 сняты.

1. «Применить конфигурацию соседа» (взять режим соседа себе) для порта, чей режим задан его группой, больше не
   отклоняется подсказкой «измените в группе». Каскад запускается от СВОЕГО порта с режимом соседа: меняется вся
   группа порта (все её порты и VLAN группы), а за ней — связанные порты, чтобы расхождений не осталось. Окно
   последствий то же, что при «Применить текущую конфигурацию». Если затрагивается только эта строка формы, режим
   правится в черновике сразу, как раньше (trunk по-прежнему отмечает «Все VLAN», как переключатель режима).
2. Состояние формы сервер берёт из черновика целиком: режим, ЧЛЕНСТВО портов в группах (в том числе в новой,
   ещё не сохранённой группе — по временному ключу), VLAN и имена портов и групп. Раньше состав групп брался из БД:
   порт, перенесённый в форме в другую группу или выведенный из группы, считался по старому составу, а новая группа
   формы вообще не попадала в область. Теперь такой порт меняется вместе с группой формы, а выведенный из группы —
   как одиночный; снимаемые VLAN и имена в плане совпадают с тем, что увидит пользователь в форме. Порты и группы,
   которые форма не передала, берутся из БД.
3. Дашборд «Подключения»: при расхождении режима в окне проверки две кнопки «Порту X задать режим как у Y (trunk)» —
   каскад от выбранного порта с окном последствий (без открытой формы всё записывается сразу, таблица
   перечитывается, статус сверки пересчитывает сервер). Кнопки «Настроить VLAN: …» (окно портов устройства) остаются
   для расхождения по VLAN — режим там больше не правится.

Изменения API (`POST /interfaces/{id}/vlan-mode-cascade[/preview]`, появился в 2.101.0): `edited.ports` и
`edited.groups` теперь объекты: порт — `{mode, group?, vlan_ids?, name?}` (`group` — ключ группы формы, `null` —
порт вне групп), группа — `{mode, vlan_ids?, name?}`, ключ группы — id сохранённой или временный ключ новой.
Опущенное поле берётся из БД. В плане `groups[].id` — ключ группы (у сохранённой равен id). Некорректное
состояние формы — 422; ссылка порта формы на группу другого устройства или неизвестный ключ означает «вне групп».

Прочее: логика каскада вынесена из `DeviceInterfacesEditor.vue` в composable `useVlanModeCascade` — им же
пользуется окно проверки на дашборде; окно последствий называет порт, с которого начинается смена («Gi0/1»
(это устройство) / «Gi0/3» (sw-03)).

Известные ограничения: порты, удалённые в форме без сохранения, сервер всё ещё видит по БД (в плане они помечены
как изменения формы и в черновик не попадают); кнопка «Управлять портами» в форме подключения по-прежнему открывает
окно портов, а не каскад; назначение порта («Упр.» / «Данные») группы не задают и этим механизмом не затрагиваются.

Проверено: backend pytest, ruff; frontend vue-tsc -b, vitest, vite build; мутационные проверки состава групп,
VLAN и имён из черновика, «своего» порта в каскаде, снимка формы при применении, дашборда.

### 2.104.0 — форма подключения: режим порта выравнивается каскадом
Раньше при расхождении режима (trunk / access) форма подключения советовала вернуться к правке и открыть «Управлять
портами» — окно портов правит один порт и не знает о группах: если режим порта задан его группой, он возвращался при
сохранении устройства, а у связанных портов расхождение появлялось в другом месте.

Теперь в окне выбора решения при расхождении режима две кнопки «Порту X задать режим как у Y (trunk)» — тот же
каскад, что на дашборде «Подключения» и в форме устройства (`useVlanModeCascade`, `services/vlan_mode_cascade.py`):
- сервер считает область изменения от выбранного порта (группы, которые задают режим, и порты, связанные с
  изменяемыми); простой случай (один порт, без групп и снимаемых VLAN) применяется сразу;
- иначе открывается окно последствий (сколько портов, устройств и групп изменится, какие VLAN будут сняты, что
  изменения применяются сразу и попадают в журнал аудита) и требуется отметка «Я ознакомился с последствиями»;
  «Отмена» ничего не записывает и возвращает к выбору решения;
- как и выравнивание роли, режим записывается сразу, до сохранения подключения; затем сверка пересчитывается, и
  если режим и роль совпали, подключение сохраняется. Если осталось расхождение по VLAN, форма снова спрашивает решение
  — теперь с подсказкой про «Управлять портами»: окно портов остаётся для правки VLAN.

Известное ограничение: порты, удалённые в форме устройства без сохранения, сервер по-прежнему видит по БД (в плане
каскада они помечены как изменения формы и в черновик не попадают).

Проверено: frontend vue-tsc -b, vitest, vite build; мутационные проверки формы (направление выравнивания,
сохранение после каскада, отмена, остаток по VLAN, подпись порта, ошибка предпросмотра). Backend не менялся.

### 2.105.0 — открытые порты: порядок строк и сохранение ВМ; VLAN домена на всех устройствах домена
**Порядок строк в списке открытых портов.** Раньше список упорядочивался по номеру порта сразу при выборе записи
справочника — только что добавленная строка «уезжала» из-под курсора, и дозаполнить её (транспорт, описание) было
неудобно. Теперь список сортируется только при нажатии «+ Открытый порт» (заполненные строки встают по возрастанию
номера, новая пустая — в конец) и при повторном открытии формы. Правило общее для всех форм с редактором портов
(ВМ, порты интерфейсов устройства, группы портов).

**Сохранение ВМ больше не пересоздаёт открытые порты.** Форма ВМ при каждом сохранении удаляла все порты ВМ и создавала
их заново (2N+1 запросов, новые id, лишние записи в журнале, при сбое посередине — потерянные порты). Теперь один
атомарный `PUT /api/v1/vms/{id}/open-ports`: порты с id обновляются на месте, без id создаются, убранные в форме
удаляются (`services/crud.py:sync_vm_open_ports`, общая с портами интерфейсов `sync_owner_open_ports`):
- id и дата создания портов сохраняются; запись в журнале аудита пишется только при реальном изменении;
- уникальность номеров проверяется по списку целиком, поэтому две строки могут поменяться номерами за одно сохранение;
- любая ошибка откатывает весь запрос; отсутствие ключа `open_ports` — 422, а не молчаливое удаление всех портов;
- новой ВМ без заполненных портов запрос не отправляется.
Лист 4 отчёта теперь явно сортирует порты ВМ по номеру (раньше порядок обеспечивался пересозданием записей).
IP-адреса и программные активы ВМ по-прежнему сохраняются через удаление и создание заново.

**VLAN домена попадают во все устройства домена.** VLAN, заведённый в домен (или привязанный к нему позже), раньше
назначался только устройству-источнику — остальные участники получали его лишь после ручного «Синхронизировать».
Теперь он сразу появляется в «VLAN устройства» и у источника, и у всех участников домена (два запроса на весь домен,
уже назначенное не дублируется). VLAN, перенесённые из домена в другой домен, у прежних участников не снимаются.

Проверено: backend pytest (858), ruff; frontend vue-tsc -b, vitest, vite build; мутационная проверка назначения VLAN
участникам домена. Миграций БД нет.

### 2.106.0 — IP-адреса и программные активы ВМ сохраняются без удаления и пересоздания
Продолжение 2.105.0: форма ВМ больше не удаляет и не создаёт заново ни один из вложенных списков. Раньше при каждом
сохранении IP-адреса и программные активы ВМ удалялись по одному и создавались заново (новые id и даты создания,
2N+1 запросов на список, при сбое посередине — потерянные записи, лишние записи в журнале). Теперь на каждый список
один атомарный запрос, как у открытых портов:
- `PUT /api/v1/vms/{id}/ip-addresses` (ключ `ip_addresses`) и `PUT /api/v1/vms/{id}/deployed-software` (ключ
  `deployed_software`); записи с id обновляются на месте, без id создаются, отсутствующие в списке удаляются;
- общая основа для портов, IP и ПО — `services/crud.py:_sync_owned_rows` (единственное место удаления; на нём
  держится белый список `test_deletion_guards.py`); `sync_owner_open_ports` стала её тонкой надстройкой;

  программного актива в справочнике, чужой или повторяющийся id — 422 с откатом всего запроса; отсутствие ключа списка —

- id и дата создания сохранённых записей не меняются; запись в журнале аудита («IP-адреса: добавлено N, изменено N,

- фронтенд: `api/vmOpenPorts.ts` переименован в `api/vmNestedLists.ts` (`syncVmOpenPorts`, `syncVmIpAddresses`,

(1242), vite build; мутационная проверка «аудит только при реальном изменении». Миграций БД нет.

### 2.107.0 — ПО физических устройств без пересоздания; перенос VLAN между доменами
**ПО физического устройства.** Последнее место, где форма удаляла и создавала записи заново: `DeviceFormModal.vue` при
каждом сохранении удалял всё ПО устройства и создавал его снова (новые id и даты создания, 2N+1 запросов, потеря ПО
при сбое посередине). Теперь один атомарный `PUT /api/v1/devices/{id}/deployed-software` (ключ `deployed_software`) —
записи с id обновляются на месте, без id создаются, убранные в форме удаляются; правила те же, что у ВМ
(`services/crud.py:sync_device_deployed_software`, общий каркас `_sync_owner_collection` для ВМ и устройств):
- проверка всего списка до записи (актив есть в справочнике, версия ≤ 100 символов, чужой или повторяющийся id — 422),
  отсутствие ключа списка — 422, неизвестное устройство — 404, любая ошибка откатывает весь запрос;
- запись в журнале аудита («Программные активы: добавлено N, изменено N, удалено N», сущность `devices`) только при
  реальном изменении;
- фронтенд: `api/deviceDeployedSoftware.ts`; новому устройству без заполненных строк запрос не отправляется.

**Перенос VLAN из одного домена в другой.** Раньше VLAN, перенесённый в другой домен, получали устройства нового
домена, но с устройств прежнего он не снимался: следующее сохранение такого устройства упиралось в 422 «Устройство не
включено в домен этого VLAN», а порты с этим VLAN — в «VLAN не разрешён». Теперь при смене `domain_id` с одного домена
на другой VLAN снимается с устройств прежнего домена (участников и источника), которых нет в новом
(`services/crud.py:_unassign_moved_vlan_from_former_domain_devices`):
- вместе с назначением на устройстве убираются связи этого VLAN с портами и группами портов того же устройства; если
  тип устройства разрешает VLAN своим каталогом (`device-type-vlans`), связи портов остаются — порт вправе использовать
  такой VLAN и без назначения на устройстве;
- устройства, оставшиеся в новом домене (в том числе его источник), другие VLAN прежнего домена и устройства вне
  доменов не затрагиваются; перенос в «без домена» и привязка локального VLAN к домену ничего не снимают;
- запросы идут по наборам устройств; в журнал VLAN пишется «VLAN снят с устройств прежнего домена: N».

Проверено: backend pytest (894; новых 19: 8 — ПО устройств, 11 — перенос VLAN), ruff; frontend vue-tsc -b, vitest
(1249), vite build; мутационные проверки переноса VLAN (очистка не вызывается / не учитывается каталог типа / не
исключаются устройства нового домена). Миграций БД нет.

### 2.108.0 — правила автоматического согласования данных порта (роль, режим, VLAN)
- Новый модуль «Правила согласования портов» (раздел «Система»): правила, по которым данные порта (роль, режим
  trunk/access, VLAN) согласуются с портом на другом конце активного подключения. Правила можно создавать и менять,
  в том числе стандартные (условия, действие, порядок, «включено»); стандартное правило нельзя удалить, но можно
  отключить или вернуть к исходному виду («Сбросить»). Страница показывает правило предложением («Если порт: режим
  trunk, VLAN не назначены совсем; соседний порт: … — порту применяется: режим, набор VLAN соседнего порта»), пометки
  «Стандартное» / «Изменено» / «Отключено», кнопки «Выше» / «Ниже», «Что сделает», «Изменить», «Сбросить», «Удалить».
- Правило — шаблон над парой «порт ← соседний порт»: условия на каждый порт (роль; режим; состояние VLAN: не назначены
  совсем / назначены, в том числе все / назначены все — «Все VLAN»), отношение значений двух портов (совпадают /
  различаются), действие и то, что порт берёт у соседа (роль, режим; VLAN: не менять / взять набор соседа / привести к
  режиму — в access остаётся один VLAN с наименьшим номером). Действие: «Автоматически» (направление определяют
  условия), «Решает человек» (какой порт менять, выбирает человек, как и раньше), «Не трогать» (пару не согласовывать).
  Проверка идёт по порядку сверху вниз, решает первое подходящее правило; автоматическое правило, подходящее обоим
  портам пары, уходит на ручное решение.
- Стандартные правила: «Пустой trunk получает VLAN соседа» (автоматически: на порту trunk совсем без VLAN, на соседнем
  trunk с назначенными VLAN или с «Все VLAN» — порту применяются режим и набор VLAN соседа; проверяется первым) и три
  правила «Решает человек», повторяющие сверку дашборда подключений: «Роль порта совпадает с ролью соседа»,
  «Режим порта совпадает с режимом соседа», «Наборы VLAN на концах линии совпадают». Тест на всех комбинациях роль ×
  режим × набор VLAN подтверждает, что стандартные правила видят расхождение ровно там, где его видит сверка дашборда.
- Где применяется: кнопка «Согласовать по правилам…» на дашборде «Подключения» (все активные подключения с
  неодобренным расхождением), блок «По правилам согласования» в окне проверки расхождения (одно подключение), «Что
  сделает» на странице правил (только это правило, даже отключённое). Везде сначала показывается план — что изменится,
  что нельзя применить и почему, что остаётся за человеком; изменения записываются одной транзакцией только после
  отметки «Я проверил план». Согласование не срабатывает само при сохранении данных — только по запросу пользователя.
- Безопасность применения: без `confirm: true` — 422; план пересчитывается заново и сверяется по `plan_hash` с
  показанным — при изменении данных после предпросмотра 409. VLAN переносятся по номеру в записи, доступные устройству
  целевого порта; номера, которых у устройства нет, пропускаются с предупреждением (VLAN устройству не добавляются).
  Не меняются порты группы, задающей режим и VLAN, результат с несколькими VLAN в access и порт, который в этом же плане
  уже изменяет другое подключение. Изменения роли зеркалируются на IP-адреса порта, как у «Задать роль порта»; в журнал
  аудита пишется «Согласование порта … по правилу …: что изменено».
- API `/api/v1/port-sync`: `GET|POST /rules`, `PUT|DELETE /rules/{id}`, `POST /rules/{id}/reset`,
  `POST /rules/reorder`, `POST /preview` (`{connection_ids?, rule_id?}` → план, ничего не пишет), `POST /apply`
  (`{connection_ids?, rule_id?, plan_hash, confirm: true}`). Создание, правка, удаление, сброс и порядок пишутся в журнал
  аудита.
- Миграция `d4b9e1a7c352`: таблица `port_sync_rules` (пустая). Стандартные правила добавляются при старте приложения по
  устойчивому коду — идемпотентно: правила, появившиеся в новых версиях, подхватываются без новой миграции, а
  изменённые администратором стандартные правила не перезаписываются. `downgrade()` удаляет таблицу вместе с правилами.

Известные ограничения: правила «Не трогать» исключают пару только из согласования по правилам — статус расхождения на
дашборде подключений остаётся строгим; запуск при сохранении данных и по расписанию не реализован; для правил «Решает
человек» план показывает варианты, но применять их нужно прежними действиями (выровнять роль, «взять режим соседа»).

### 2.109.0 — подключения портов в форме устройства (блок «Порты / интерфейсы»)
Порт теперь можно подключить к порту другого устройства прямо при создании и редактировании устройства — без перехода
на экран «Подключения». В раскрытой строке порта появился блок «Подключение»: устройство-сосед → его порт, тип физической
линии связи, описание; кнопки «Подключить» / «Отключить».

**Сервер.** У нового порта до сохранения нет id, поэтому отдельным запросом подключение не создать. Элемент `interfaces[i]`
в `PUT /api/v1/devices/{id}/interfaces` получил необязательный ключ `connection`
(`services/interface_connections.py`, вызывается из `services/crud.py:sync_interfaces` в той же транзакции):
- ключа нет — подключения порта не трогаются (старые клиенты и `DevicePortsModal` работают как раньше);
- `null` — активное подключение порта удаляется; освобождённый порт соседа может быть занят другой строкой этого же
  запроса независимо от порядка строк (сначала применяются все отключения);
- `{peer_interface_id, connection_type_id, description}` — подключение создаётся; если у порта уже есть активное
  подключение к тому же соседу, оно обновляется на месте (id и направление сохраняются), к другому — переключается на
  нового соседа с тем же id, а одобрение расхождения конфигурации (`port_config_approved_signature`) сбрасывается;
- проверки: форма ключа и существование типа линии и порта соседа — 422 (в том числе «порт нельзя подключить к самому
  себе»), занятый порт — 409 из `validate_connection`; любая ошибка откатывает весь запрос, включая созданные порты;
- удаление порта, у которого есть подключение (в том числе неактивное), теперь даёт понятный 409 с именами портов
  вместо ошибки внешнего ключа; сначала порт нужно отключить;
- в журнале аудита подключения пишутся как `CREATE` / `UPDATE` / `DELETE` сущности `connections`, запись `SYNC`
  интерфейсов дополнена «подключений изменено: N». Прямое удаление подключения внесено в `ALLOWED_DELETIONS`
  (`test_deletion_guards.py`): на таблицу `connections` не ссылается ни один внешний ключ (проверяется тестом).

**Интерфейс.** `InterfaceConnectionEditor.vue` + `utils/interfaceConnections.ts`:
- из списка соседей исключены текущее устройство, порты, занятые активными подключениями, и порты, выбранные в соседних
  строках формы; соседом может быть только уже сохранённый порт другого устройства;
- на сервер уходят только изменённые подключения (снимок на момент открытия формы), нетронутые порты не затрагиваются;
  незаконченный черновик («Подключить» нажато, а порт или тип линии не выбраны) блокирует сохранение с понятным текстом;
- расхождение «Управление» / «Передача данных» / режима порта с портом соседа показывается сразу и сохранению не мешает —
  после сохранения расхождение попадает в уведомление и на экран «Подключения»; копия устройства создаётся без
  подключений.
Ограничения: сосед — только на другом устройстве и только из сохранённых портов; обмен соседями между двумя портами за
один запрос (A: P→Q, B: Q→P) даёт 409.

Проверено: backend pytest (1052; новых 12 в `test_interface_connections.py`), ruff; frontend vue-tsc -b, vitest
(1371), vite build; мутационная проверка отправки ключа `connection`. Миграций БД нет.


### 2.110.0 — безопасность по код-ревью: первичная настройка, CORS/Host, автор в журнале, SVG, вход

Аутентификация по-прежнему **выключена по умолчанию**: реестр открыт без входа, как и раньше. Меняется только то, что
при выключенной аутентификации позволяло постороннему захватить приложение.

- **Захват при выключенной аутентификации (п. 1 ревью).** Раньше любой, кто достаёт до порта, мог создать
  администратора, включить аутентификацию и закрыть реестр от владельца. Теперь `POST/GET /auth/users` и
  `PUT /auth/settings` при выключенной аутентификации доступны только при прямом соединении с `localhost` (без
  заголовков прокси `X-Forwarded-For`/`Forwarded`/`X-Real-IP`) либо по заголовку `X-Setup-Token` — если задана

  проекта аутентификация по умолчанию выключена; в серверном режиме по-прежнему пишется предупреждение в лог.
- **CORS и Host (п. 2).** `INFRA_REGISTRY_CORS_ORIGINS` по умолчанию пуст (CORS выключен; раньше `*`), добавлена
  проверка заголовка `Host` (`INFRA_REGISTRY_ALLOWED_HOSTS`, по умолчанию `localhost,127.0.0.1`). В

- **Автор действия в журнале аудита (п. 3).** Новые колонки `audit_log.actor_id`, `actor_username`, `actor_ip`

  рядом с id — запись переживает удаление учётной записи. Колонка «Пользователь» в экране «Журнал аудита» (адрес — во
  всплывающей подсказке) и в Excel-экспорте (+ «IP-адрес»). Вход и неудачный вход записываются с адресом клиента.
- **SVG (п. 4).** `validate_svg_markup` — белый список тегов и атрибутов на `defusedxml` вместо регулярки: больше не
  проходят `<s:script>` с префиксом пространства имён, `javascript:` через HTML-сущность, SMIL-анимация `href`, внешние

### 2.111.0 — подключения в форме устройства: повтор после сбоя, обмен соседями, серверные списки портов
Доработки блока «Подключение» (2.109.0): три пункта из списка улучшений.

**1. Повтор сохранения после частичного сбоя.** Создание нового устройства — это несколько запросов (устройство, ПО,
VLAN, порты, связи с доменами). Если устройство создалось, а следующий шаг упал, форма запоминает созданное устройство
(`createdDevice`): повторное «Сохранить» обновляет его через `PUT`, а не создаёт дубль (раньше повтор упирался в
«Серийный номер уже используется»), заголовок и сообщение говорят, что устройство уже создано, а список устройств
перечитывается. Связи с доменами (`POST`, не идемпотентны) повторно не отправляются (`joinedDomainIds`); полные замены
ПО, VLAN и портов (`PUT`) повторяются безопасно.

**2. Подключения между портами одного устройства и обмен соседями.** Ограничения 2.109.0 сняты:
- сервер (`services/interface_connections.py`) строит *план* подключений запроса целиком: разбор всех → отключения →
  план → проверка согласованности → применение. Прежние порты переставляемых подключений считаются свободными
  (`validate_connection(..., ignore_connection_ids=…)`), поэтому A: P→Q и B: Q→P в одном запросе проходят;
- у `connection` вместо `peer_interface_id` можно указать `peer_row` — номер элемента массива `interfaces` в этом же
  запросе. Так подключаются порты без id (новые) и порты одного устройства; ровно одно из полей соседа, `peer_row` —
  целое ≥ 0, не `bool`, «самому себе» и несуществующий номер — 422;
- кабель, описанный с обеих сторон, схлопывается в одно подключение (одинаковые параметры) либо 422 (разные); порт в
  двух разных парах одного запроса — 409 «Порт «X» указан в нескольких подключениях…»;
- форма: в списке соседей первым пунктом «<имя> (это устройство)» / «Это устройство (новое)»; кандидаты — порты других
  строк без собственного подключения (подпись «имя (строка N)»); порты, освобождаемые этой же формой, доступны сразу;
  удаление строки очищает ссылки на неё, оставшийся висячий сосед блокирует сохранение.

**3. Масштаб: порты и подключения с сервера.** Новые эндпоинты (`services/device_connectivity.py`, `api/devices.py`):
- `GET /api/v1/devices/{id}/free-interfaces` — свободные порты устройства в естественном порядке имён (`eth2` < `eth10`);
  `q` (подстрока), `offset`, `limit` 1..500 (по умолчанию 100), повторяемый `include` — вернуть и занятые порты
  (`occupied: true`), чужие id игнорируются; «занятый» = есть подключение с `is_active IS NOT FALSE` с любой стороны;
- `GET /api/v1/devices/{id}/interface-connections` — действующие подключения портов устройства со сведениями о соседе
  (кабель между портами одного устройства даёт две записи, по одной на каждый порт); несуществующее устройство — 404.
Редактор подключения и загрузка подключений формы больше не зависят от общих списков (`limit=1000`) и стора подключений:
порты соседа догружаются постранично (`fetchAllFreeInterfaces`, страница 200), ответ устаревшего запроса отбрасывается.
Ограничение: уведомление о расхождениях после сохранения и `interfaceConflicts` по-прежнему считаются по общим спискам
(потолок 1000), `devicesStore` грузит `/devices` целиком — следующий шаг масштабирования.

Проверено: backend pytest (1135; новых 21: 10 в `test_interface_connections.py`, 11 в `test_device_connectivity.py`),
ruff; frontend vue-tsc -b, vitest (1433), vite build; мутационные проверки: повтор без `createdDevice`, снятая защита
`joinedDomainIds`, пустой `moved_ids`, отключённая проверка claim порта, неразрешённый дубль пары, пустой
`freedPeerIds`, `clearReferencesTo` без очистки, `peer_row` всегда 0, снятая защита `loadSeq`, потерянный `include`,
только первая страница, неизменяемый `offset` — каждая поломка роняет тест. Миграций БД нет.


### 2.112.0 — корректность данных по код-ревью: порядок строк, слот стойки, ошибки БД, отчёты

- **Стабильная пагинация (п. 6 ревью).** `list_resource` теперь всегда сортирует `ORDER BY created_at, id` (журнал
  аудита — по-прежнему от новых к старым). Раньше у всех ресурсов, кроме журнала, `offset/limit` работали без
  сортировки, и на PostgreSQL соседние страницы могли дублировать или пропускать записи. Поиск `q` экранирует `%` и
  `_` (`contains(..., autoescape=True)`): раньше они действовали как шаблон LIKE.
- **Слот в стойке защищён в БД (п. 7).** Частичный уникальный индекс `uq_device_rack_slot` (`rack_id` + `rack_position`,
  только где заданы оба и позиция не пустая) — миграция `b5d2f8a1c673`. Перед созданием индекса миграция устраняет
  существующие дубли: самое раннее устройство слота сохраняет позицию, у остальных она снимается (`NULL`). **Перед
  обновлением БД, где мог остаться один слот у двух устройств, проверьте такие дубли вручную** — снятые позиции не
  восстанавливаются при `downgrade`. Валидатор больше не меняет данные: освобождение подтверждённого слота вынесено в
  `crud._release_rack_slot` и идёт отдельным `flush()` до сохранения устройства (иначе SQLAlchemy выполнил бы INSERT
  раньше UPDATE и индекс отверг бы запись). Гонка двух запросов за один слот даёт 409 `RACK_POSITION_OCCUPIED`.
- **Ошибки целостности без утечек (п. 8, часть).** Единый `integrity.integrity_error_response` вместо
  `str(exc.orig)[:300]` в шести местах `crud.py`: клиент получает 409 `INTEGRITY_ERROR` с общим текстом, а имена таблиц и
  ограничений пишутся только в лог сервера. **Контракт изменился:** `detail` теперь объект `{code, message}`, а не
  строка с текстом ошибки БД. Схемы Pydantic для остальных эндпоинтов и `extra="forbid"` в этот релиз не вошли.
- **Роль viewer и отчёты (п. 9).** `viewer` может формировать отчёты и предпросмотр: `POST /reports/inventory`,
  `/reports/audit-log`, `/report-builder/preview` и `/report-templates/{id}/generate` не меняют реестр. Создание,
  правка, удаление и дублирование шаблонов, `/seed` и все остальные записи по-прежнему только у администратора;
  допустимы точные пути, похожие адреса (`.../generate/extra`) остаются запрещёнными.
- **Отчёты (п. 11).** К имени файла добавлен случайный суффикс (два отчёта в одну секунду больше не перезаписывают друг
  друга); сформированные отчёты старше `INFRA_REGISTRY_REPORT_RETENTION_DAYS` (30 дней, `0` — не удалять) удаляются при
  формировании нового; Excel-экспорт журнала аудита проходит через `excel_safe`; `\t` и `\r` добавлены к символам,
  с которых начинается формула.
- **VLAN (п. 12, часть).** `POST /devices/{id}/vlan-copy` идемпотентен (повторный вызов не создаёт дубли определений и
  назначений) и грузит VLAN источника одним запросом; `bulk-assign` проверяет устройства одним запросом вместо
  `session.get` на каждое.
- **CI (п. 13, часть).** `permissions: contents: read`, действия закреплены по SHA, добавлен smoke-тест собранного
  образа (`docker run`, затем `/api/v1/health` и `/`).

Не вошло (см. ревью): job CI с PostgreSQL, lock-файл зависимостей бэкенда, отдельный шаг миграций, схемы Pydantic для
`sync_*`, разбиение `crud.py`/`system.py`, пагинация `/api/v1/devices`, потоковый экспорт журнала аудита, кеш
`AuthSettings` в middleware, линтеры сложности и стиля.



### 2.113.0 — схемы тел запросов синхронизации, дубль маршрута «/», потоковый экспорт журнала аудита

  принимают Pydantic-схемы с `extra="forbid"` вместо сырого `dict`. Главное следствие: опечатка в имени поля
  (`interfases`) раньше молча давала пустой список, и PUT на полный список **удалял все порты/VLAN/ПО устройства** — теперь
  это 422, данные не трогаются. Неверные типы (строка вместо списка, нечисловая позиция в стеке, `position < 1`) тоже
  дают 422 на входе, а OpenAPI (`/docs`) описывает эти тела. Семантика «ключ не прислан — не менять» сохранена
  (`groups` у `/interfaces`: нет ключа — группы не трогаются, `[]` — удаляются). Элементы списков по-прежнему словари:
  их разбор и доменные правила остаются в сервисах. Ответы с отказом по неизвестному ключу — стандартный 422 FastAPI
  (`detail` — список), а не 422 со строкой.
- **Дубль маршрута `/` (п. 10, часть).** Убран `GET /` из `api/system.py`: ту же страницу отдаёт `spa_fallback` в
  `main.py`; сообщение об отсутствующей сборке фронтенда теперь одно и содержит подсказку `npm run build`.
- **Журнал аудита (п. 12, часть).** Excel-экспорт пишется потоково (`Workbook(write_only=True)`, порциями по 5 000
  записей): память не растёт с числом записей (потолок прежний — 100 000). Оформление то же (шапка, закреплённая
  строка, автофильтр); ширина колонок теперь фиксирована, а не подбирается по содержимому.

Не вошло (см. ревью): схемы для остальных `payload: dict` (диаграммы, шаблоны отчётов, порты, `information-systems/{id}/details`),
`Literal` для статусов и `extra="forbid"` у схем `devices`/`information-systems`/`vlans` (требует сверки со всеми полями,
которые шлёт фронтенд), разбиение `crud.py`/`system.py`, пагинация `/api/v1/devices`, кеш `AuthSettings` в middleware.


### 2.114.0 — generic CRUD: неизвестные поля в устройствах, ИС и VLAN дают 422

- **Опечатка в имени поля больше не «успех» (п. 8 ревью, продолжение).** `POST/PUT /resources/devices`,
  `/information-systems` и `/vlans` отвечают 422 на ключ, которого нет среди колонок модели, например
  `serial_numbr` или `rack_positon`; в сообщении перечислены все неизвестные поля и ближайшее допустимое имя
  («возможно, `serial_number`»). Раньше generic CRUD молча отбрасывал такой ключ: при создании запись появлялась без
  значения, при правке ничего не менялось, и об ошибке узнавали позже.
- **Проверка идёт по колонкам модели, а не через `extra="forbid"` схем.** Схемы объявляют не все колонки (форма
  устройства, например, отправляет `diagram_icon_id`, которого нет в `PhysicalDeviceCreate`), и `forbid` сломал бы
  сохранение; проверка по модели не отстаёт от неё. Допустимы также служебные флаги `confirm_system_name_duplicate` /
  `confirm_rack_position_reassign` и ключи, которые клиент мог вернуть «эхом» из полученной записи (`id`,
  `created_at`, `updated_at`, `number`) — они по-прежнему игнорируются без ошибки.
- **Что может сломаться.** Внешние скрипты, которые отправляли в эти три ресурса целиком обогащённую запись
  (с вычисляемыми полями вроде названий справочников), теперь получат 422 с перечнем лишних ключей — отправляйте только
  поля записи. Веб-интерфейс шлёт только колонки (проверено по формам устройства, ИС и VLAN).
- **`Literal` для `status` не добавлен.** Набор допустимых значений нигде в коде и интерфейсе не определён (форма
  статус не отправляет, а шаблон отчёта фильтрует по `active`); ограничивать его, не зная значений в существующих БД,
  значило бы рисковать отказом на старых данных. Решение — за владельцем: нужен список статусов.

Не вошло: остальные ресурсы по-прежнему отбрасывают неизвестные ключи молча (это отдельный шаг — нужна проверка
всех форм и квик-добавления), схемы для оставшихся `payload: dict`.

### 2.115.0 — форма устройства: расхождения портов и выбор соседа — на сервере
Снимает два ограничения 2.111.0: расчёт расхождений конфигурации портов и список устройств-соседей больше не зависят
от общих списков, которые клиент грузит целиком (потолок 1000 записей, полный `GET /devices`).

**Расхождения конфигурации портов с соседями.** Значок расхождения в форме, окно сравнения и уведомление после сохранения
искали соседа по общему списку подключений и каталогу интерфейсов: в большом реестре расхождение с портом, не попавшим в
выборку, пропадало молча. Теперь источник — подключения самого устройства
(`GET /devices/{id}/interface-connections`, 2.111.0): в каждой записи уже есть имя и устройство соседнего порта, его
«Управление», «Передача данных» и режим порта.
- `utils/portConflicts.ts:computePortConflicts(rows, connections)` принимает подключения устройства с сервера; у порта с
  несколькими подключениями берётся первое в порядке ответа (как раньше).
- `DeviceFormModal.vue`: соседи загружаются при открытии формы тем же запросом, что и подключения портов, и перечитываются
  после сохранения с изменёнными подключениями. Форма больше не загружает общий список подключений при открытии; если он
  уже загружен другим экраном, после изменения подключений он по-прежнему обновляется.
- `DeviceInterfacesEditor.vue`: новое событие `neighbors-changed` — после «Применить текущую конфигурацию» соседу и после
  каскада режима порта. Форма перечитывает соседей, и значок расхождения исчезает сразу (раньше правился кэш каталога).
- `DevicePortsModal.vue` («Управлять портами») берёт подключения устройства с сервера вместо общего стора.

**Выбор соседнего устройства.** Блок «Подключение» брал устройства из стора, а он грузит `GET /devices` целиком (с
обогащением: стеки, адреса, справочники) ради одного выпадающего списка.
- Сервер: `GET /api/v1/devices/options` (`services/device_connectivity.py:list_device_options`) — лёгкие записи `{id, label,
  system_name, serial_number}`; `q` (подстрока имени или серийного номера без учёта регистра), `offset`, `limit` 1..200
  (по умолчанию 50), повторяемые `include` (вернуть независимо от `q` — выбранный сосед) и `exclude` (не возвращать —
  редактируемое устройство; сильнее `include`). Порядок — по подписи без учёта регистра, затем по id. Регистр сравнивается
  `casefold` в Python, а не `lower()` в SQL: `lower()` в SQLite знает только ASCII, и поиск «Альфа» по «альфа» не работал бы.
- Клиент: `SearchableSelect.vue` получил режим `remote` (опции не фильтруются локально, ввод уходит событием `search`,
  `loading`, `hint`); редактор запрашивает устройства при открытии списка и при вводе с паузой 250 мс, отбрасывает ответы
  устаревших запросов, показывает «Показаны первые 50 из N — уточните поиск» и ошибку загрузки. Подпись выбранного соседа
  хранится в черновике (`peer_device_name`, на сервер не уходит) и приходит вместе с подключением. Пункт «это устройство»
  подписывается именем из формы и при поиске показывается, только если подходит под введённый текст.
- Форма устройства больше не запрашивает ни `GET /devices`, ни общий список подключений при открытии (список устройств
  для экрана «Инвентаризация» по-прежнему обновляется после сбоя создания).

Не сделано (сознательно): соединение портов одного устройства цепочкой (A↔B и B↔C) — соседом из этой же формы остаётся
только порт без собственного подключения.

Проверено: backend pytest (1211; новых 5 в `test_device_connectivity.py`), ruff; frontend vue-tsc -b, vitest (1457), vite
build; мутационные проверки: нет события `neighbors-changed` после записи соседу и после каскада, безусловная
перезагрузка общего списка подключений, нет перечитывания соседей после сохранения, последнее вместо первого подключения
порта, форма снова грузит список устройств и подключений, потерян `include` / `exclude`, нет защиты от устаревших ответов,
поиск без паузы, не запоминается подпись устройства, локальная фильтрация в режиме `remote`; на сервере — поиск с учётом
регистра, `include` сильнее `exclude`, `include` не обходит поиск, сортировка без `casefold`. Миграций БД нет.

# frontend-vue — концепция «Диспетчерская» (Vue 3 + TypeScript)

Экспериментальная реализация UI поверх существующего FastAPI-бэкенда, не
заменяющая текущий `frontend/` (vanilla JS), а развивающаяся рядом на отдельной
ветке для сравнения. Это концепция **Б, «Диспетчерская»**: тёмная NOC-консоль
дежурного инженера с несколькими выбираемыми цветовыми схемами.

## Статус

Полностью реализован и подключён к реальному API один экран —
**«Инвентаризация физических устройств»** (`/devices`), включая:

- поиск (имя / серийный номер / IP управления);
- фильтры по зданию, типу устройства, признаку SIEM;
- фильтр по структурным единицам с деревом (выбор родителя включает всех
  потомков — тот же принцип parent→child expansion, что в
  `backend/app/reporting.py`);
- резолв FK id → отображаемое имя через общий стор справочников;
- пагинация на клиенте (бэкенд `/api/v1/devices` отдаёт все записи разом —
  тот же подход, что и в текущем vanilla-фронтенде, см. `CACHEABLE_LIST_RESOURCES`
  в `frontend/static/core.js`);
- **CRUD**: добавление, редактирование и удаление устройства через модальную
  форму (`DeviceFormModal.vue`) с каскадными списками (модель → тип
  устройства, помещение → здание, стойка → помещение) и обработкой
  структурированных 409-конфликтов бэкенда (`DUPLICATE_SYSTEM_NAME`,
  `RACK_POSITION_OCCUPIED`, `REFERENCED_BY_OTHER_RECORDS`) — тот же
  retry-with-confirm UX, что в `frontend/static/app.js:saveForm`, включая
  `window.confirm()` вместо кастомного диалога, для консистентности с
  остальным приложением;
- toast-уведомления об успехе/ошибке (`useToast`/`ToastHost.vue`) — аналог
  `notify()`/`notifyError()` из vanilla-фронтенда.

Дашборд (`/dashboard`) подключён к `/api/v1/dashboard` и показывает реальные
счётчики.

Второй полностью рабочий экран — **«Информационные системы»** (`/information-systems`,
Лист 1): список с поиском/фильтром SIEM, CRUD через модалку. Форма покрывает
только собственные поля `InformationSystem` (см. «Ещё не сделано» — вложенные
связи пока не редактируются).

Третий — **«Виртуальные машины»** (`/vms`, Лист 4): список, поиск, CRUD.
Форма учитывает бизнес-правила бэкенда: хост (`physical_device_id`) отфильтрован
на клиенте до устройств типа «Сервер»/«Система хранения» (сервер всё равно
отклонит остальные типы с 422 — фильтр только для UX), а `hypervisor_os_id`
не редактируется — бэкенд всегда пересчитывает его сам из ОС выбранного хоста,
форма показывает это как read-only предпросмотр. Форма также редактирует
IP-адреса ВМ (`VmIpListEditor.vue`, ресурс `/resources/vm-ips`) и её открытые
порты (`OpenPortListEditor.vue`, `/resources/open-ports?owner_type=virtual_machine`)
— строки staged локально (можно заполнить ещё до сохранения новой ВМ, когда
её id ещё не существует) и персистятся после сохранения самой ВМ по схеме
delete-затем-recreate, аналогично `saveVMIPs()`/`saveVMOpenPorts()` в
vanilla-версии (`frontend/static/vm-editors.js`). `OpenPortListEditor.vue`
не завязан на владельца (принимает готовые строки и справочник портов через
props) и переиспользуется как есть для будущего редактора открытых портов
устройства — см. «Ещё не сделано».

Четвёртый — **«Подключения»** (`/connections`, Лист 3), самый структурно
сложный: каскадный выбор устройство→порт для источника и назначения, список
портов на каждом шаге исключает уже занятые активным подключением (сервер
всё равно отклонит конфликт 409 — фильтр только для UX). Использует общий
`/resources/connections`, где `enrich_connections()` уже возвращает резолвленные
имена устройств/портов/типа линии — без клиентских джойнов для отображения таблицы.

Пятый — **«Отчёты»** (`/reports`): генерация регламентного Excel-отчёта
(4 листа) с опциональными фильтрами (по одной ИС, по структурным единицам —
переиспользует `StructuralUnitTree.vue` из фильтра устройств) и выгрузки
журнала аудита за период. Файл скачивается без ухода со страницы SPA
(`<a download>`, программный клик). Визуальный конструктор произвольных
отчётов (`report_builder.py`, drag-and-drop grid-редактор, Word-шаблоны) —
отдельная большая задача, не перенесена.

Шестой — **«Журнал аудита»** (`/audit-log`): только чтение (аудиторский след
намеренно не редактируется через UI), поиск, фильтр по действию и по разделу.
Имя раздела резолвится не хардкодом, а через `GET /api/v1/resources` (то же,
что `DISPLAY_NAMES` на бэкенде) — не расходится при добавлении новых ресурсов.

Седьмой — **«VLAN»** (`/vlans`): группировка по VLAN ID через специализированный
`/api/v1/vlan-dashboard` (один и тот же ID может иметь разные определения в
разных доменах — например, «локальный» VLAN без домена; экран это явно
отмечает как «требует внимания», а не считает ошибкой). CRUD отдельных
определений через общий `/resources/vlans`. VLAN-домены с автосинхронизацией
от устройства-источника (`/vlan-domains/{id}/sync`) не реализованы — см.
«Ещё не сделано».

Восьмой — **«Здания и помещения»** (`/buildings`): трёхуровневая иерархия
Здание → Помещение → Стойка с раскрывающимися узлами и CRUD на каждом уровне.

Девятый — **«Структурные подразделения»** (`/structural-units`): дерево с
CRUD (добавить корневую/дочернюю единицу, редактировать, удалить). Удаление
единицы с живыми потомками блокируется на клиенте до похода на сервер
(понятное сообщение вместо непрозрачного 409), сервер всё равно проверяет
это самостоятельно — двойная защита.

**Все разделы меню теперь имеют рабочие экраны в новом UI**, кроме визуального
конструктора произвольных отчётов (`report_builder.py`) — сознательно не
переносится, см. «Ещё не сделано».

## Стек

Vue 3 (`<script setup>` + TypeScript) · Pinia · vue-router · Vite · Vitest +
`@vue/test-utils`.

## Разработка

```bash
npm install
npm run dev        # Vite dev-сервер на :5173, проксирует /api на 127.0.0.1:8000
npm run build       # vue-tsc (проверка типов) + сборка в dist/
npm test            # vitest run
```

Бэкенд должен быть поднят отдельно на `127.0.0.1:8000` (см. корневой README) —
`vite.config.ts` содержит прокси `/api -> http://127.0.0.1:8000`, тот же
same-origin принцип, что и в проде, где собранный `dist/` будет раздаваться
самим FastAPI (см. `backend/app/api/system.py`, `FRONTEND_DIR`).

## Цветовые схемы

Три схемы: **Бирюза** (по умолчанию), **Индиго**, **Медь** — см.
`src/stores/theme.ts` и `src/styles/theme.css`. Меняется только фирменный
акцент (`--brand`/`--brand-soft`) и лёгкий оттенок фона; статусные цвета
(норма/внимание/тревога) зафиксированы во всех схемах, чтобы выбор акцента не
мог сделать предупреждение неотличимым от активного пункта меню. Выбор
сохраняется в `localStorage` (`itr.colorScheme`).

## Архитектурные решения, важные для продолжения работы

- **Формы ответов API.** `/api/v1/resources/{resource}` всегда отдаёт
  `{items, total, offset, limit}` (см. `backend/app/services/crud.py:list_resource`),
  а специализированный `/api/v1/devices` — `{items, total}` без `offset/limit`
  (без серверной пагинации). Это разные формы — см. `PagedResponse<T>` vs
  `DevicesResponse` в `src/api/types.ts` / `src/api/client.ts`.
- **serialize() не резолвит внешние ключи** — отдаёт сырые id колонок.
  Резолв в отображаемое имя — на фронтенде, через `useCatalogsStore().label()`.
  Исключение: `enrich_connections()` (и `enrich_devices()`) резолвят некоторые
  поля сами на бэкенде — см. `Connection`/`Device` типы, где часть полей уже
  готовые строки, а не id.
- **Ключ ресурса в `/resources/{key}` не всегда очевиден из имени модели** —
  например, `DeviceInterface` живёт под ключом `interfaces`, а не
  `device-interfaces` (наступили на это при разработке `ConnectionFormModal`:
  404 на ровном месте). Источник истины — `backend/app/registry.py`, а не
  интуиция по названию SQLAlchemy-модели.
- **Структурные единицы** — самоссылающаяся иерархия `parent_id` (тот же
  паттерн, что `Department`). Фильтр по единице должен разворачиваться на всех
  потомков, а не быть точным совпадением id — см.
  `catalogs.unitAndDescendantIds()` и покрывающий тест в
  `src/stores/__tests__/catalogs.spec.ts`.
- Тесты стора используют фикстуры (`src/stores/__tests__/fixtures.ts`),
  снятые по форме с реальных ответов локально поднятого бэкенда, а не
  придуманы вручную.

## Ещё не сделано

- VLAN-домены: управление составом домена (`/vlan-domains/{id}/members`) и
  автосинхронизация состава от устройства-источника
  (`/vlan-domains/{id}/sync`) — сами домены видны только как read-only опция
  в форме VLAN, не управляются через новый UI.
- **Визуальный конструктор произвольных отчётов** (`report_builder.py`,
  drag-and-drop grid-редактор, Word-блочный редактор шаблонов) — большая
  отдельная задача, не перенесена. Реализована только генерация
  фиксированного регламентного отчёта и выгрузки журнала аудита.
- На экране устройств: привязка VLAN/интерфейсов/открытых портов к устройству
  (в vanilla-версии это `saveDeviceVlans`/`saveDeviceInterfaces`/
  `saveDeviceOpenPorts` в `app.js:saveForm`) — форма сейчас покрывает только
  собственные поля `PhysicalDevice`.
- На экране информационных систем: вложенные связи (подразделения, IP-адреса,
  протоколы, источники размещения — `/resources/information-systems/{id}/details`)
  не редактируются, только основные поля самой ИС.
- На экране подключений: интерфейсы (порты) создаются только через API
  напрямую или в текущем vanilla-интерфейсе — управление портами устройства
  (создание/переименование) в новом UI не реализовано, только выбор уже
  существующих при создании подключения.
- Интеграция сборки в `docker-compose.yml` / `infra_registry.spec` (PyInstaller) —
  CI (`build` + `vitest`) уже подключён (см. `.github/workflows/ci.yml`), но
  собранный `dist/` пока никуда не разворачивается.

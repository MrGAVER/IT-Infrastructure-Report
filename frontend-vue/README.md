# frontend-vue — концепция «Диспетчерская» (Vue 3 + TypeScript)

**Единственный UI приложения** (с версии 2.60.0 — vanilla-фронтенд `frontend/` и раздача на
`/legacy` удалены, см. корневой README, раздел «Изменения»; до этого — основной UI с 2.45.0,
поверх существующего FastAPI-бэкенда). Это концепция **Б, «Диспетчерская»**: тёмная NOC-консоль
дежурного инженера с несколькими выбираемыми цветовыми схемами.

## Раздача бэкендом

`GET /` отдаёт собранный `dist/` этого фронтенда (`backend/app/config.py:FRONTEND_DIR`,
по умолчанию `frontend-vue/dist`) — каталог нужно собрать (`npm run build`)
до первого запуска бэкенда, иначе `/` ответит понятной 500-ошибкой с
указанием отсутствующего файла. Клиентский роутинг
(`vue-router`, режим `createWebHistory()`) поддержан на бэкенде SPA-фоллбэком:
любой не-API GET-путь (`/vms`, `/devices` и т.п.) тоже отдаёт `index.html` —
см. `backend/app/main.py:spa_fallback`.

## Статус

Полностью реализован и подключён к реальному API один экран —
**«Инвентаризация физических устройств»** (`/devices`), включая:

- поиск (имя / серийный номер / IP управления);
- фильтры по зданию, типу устройства, признаку SIEM;
- фильтр по структурным единицам с деревом (выбор родителя включает всех
  потомков — тот же принцип parent→child expansion, что в
  `backend/app/reporting.py`);
- резолв FK id → отображаемое имя через общий стор справочников;
- пагинация на клиенте (бэкенд `/api/v1/devices` отдаёт все записи разом —
  тот же подход, что и в текущем vanilla-фронтенде, см. `CACHEABLE_LIST_RESOURCES`
  в `frontend/static/core.js`);
- **CRUD**: добавление, редактирование и удаление устройства через модальную
  форму (`DeviceFormModal.vue`) с объединённым полем «Тип / производитель /
  модель» (один select с опциями типов без модели и моделей, сгруппированных
  по производителю — выбор модели сам подставляет тип/производителя) и
  каскадными списками здание → помещение → стойка, у каждого из трёх —
  кнопка быстрого добавления, и обработкой
  структурированных 409-конфликтов бэкенда (`DUPLICATE_SYSTEM_NAME`,
  `RACK_POSITION_OCCUPIED`, `REFERENCED_BY_OTHER_RECORDS`) — тот же
  retry-with-confirm UX, что в `frontend/static/app.js:saveForm`, включая
  `window.confirm()` вместо кастомного диалога, для консистентности с
  остальным приложением. Форма также редактирует открытые порты,
  программные активы, физические интерфейсы и VLAN устройства
  (`OpenPortListEditor.vue`/`SoftwareAssetListEditor.vue` — те же
  компоненты, что у ВМ; `DeviceInterfacesEditor.vue` — компактная таблица
  портов (VLAN на порту/IP-адреса/описание — под разворачиваемой строкой) с
  генерацией по шаблону и вложенными IP, persist через атомарный
  `PUT /devices/{id}/interfaces`; `DeviceVlanListEditor.vue` — назначение
  VLAN устройству, доступные VLAN ограничены членством в VLAN-домене) —
  подробности и явные ограничения см. «Ещё не сделано»;
- toast-уведомления об успехе/ошибке (`useToast`/`ToastHost.vue`) — аналог
  `notify()`/`notifyError()` из vanilla-фронтенда.

Дашборд (`/dashboard`) подключён к `/api/v1/dashboard` и показывает реальные
счётчики.

Второй полностью рабочий экран — **«Информационные системы»** (`/information-systems`,
Лист 1): список с поиском/фильтром SIEM, CRUD через модалку. Форма покрывает
собственные поля `InformationSystem`, а также вложенные связи — подразделения
(`CatalogPickerListEditor.vue`), протоколы передачи данных
(`ISProtocolsListEditor.vue` — та же логика автоподстановки протокола/порта из
справочника, что в `OpenPortListEditor.vue`), источники размещения и IP
(`ISSourcesListEditor.vue` — унифицированная замена устаревших отдельных
таблиц устройство/ВМ/контейнер/IP; выбор ВМ автоподставляет её хост, ВМ
текущего хоста строки поднимаются в начале списка) и места размещения
(`CatalogPickerListEditor.vue`, тот же компонент, что у подразделений — обе
связи имеют форму "выбери одну запись справочника"). Персистится через
атомарный `PUT /resources/information-systems/{id}/details` — тот же приём,
что интерфейсы устройства (см. четвёртый экран ниже), только путь под
`/resources/`, а не `/devices/`. При первом открытии формы для ИС, у которой
ещё нет записей в унифицированной таблице `sources`, но есть данные в
устаревших таблицах, они на лету собираются в `sources` — портировано
дословно с `openInformationSystemForm()`/`migrateLegacyToSources()`-логики
`frontend/static/information-systems.js`, иначе такая ИС выглядела бы в
новом UI так, будто у неё вообще нет источников.

Третий — **«Виртуальные машины»** (`/vms`, Лист 4): список, поиск, CRUD.
Форма учитывает бизнес-правила бэкенда: хост (`physical_device_id`) отфильтрован
на клиенте до устройств типа «Сервер»/«Система хранения» (сервер всё равно
отклонит остальные типы с 422 — фильтр только для UX), а `hypervisor_os_id`
не редактируется — бэкенд всегда пересчитывает его сам из ОС выбранного хоста,
форма показывает это как read-only предпросмотр. Форма также редактирует
IP-адреса ВМ (`VmIpListEditor.vue`, ресурс `/resources/vm-ips`), её открытые
порты (`OpenPortListEditor.vue`, `/resources/open-ports?owner_type=virtual_machine`)
и развёрнутые программные активы (`SoftwareAssetListEditor.vue`,
`/resources/vm-software`) — строки staged локально (можно заполнить ещё до
сохранения новой ВМ, когда её id ещё не существует) и персистятся после
сохранения самой ВМ по схеме delete-затем-recreate, аналогично
`saveVMIPs()`/`saveVMOpenPorts()`/`saveVMSoftware()` в vanilla-версии
(`frontend/static/vm-editors.js`). `OpenPortListEditor.vue` и
`SoftwareAssetListEditor.vue` не завязаны на владельца (принимают готовые
строки и справочник через props) — переиспользованы без изменений на экране
устройств ниже.

Четвёртый — **«Подключения»** (`/connections`, Лист 3), самый структурно
сложный: каскадный выбор устройство→порт для источника и назначения, список
портов на каждом шаге исключает уже занятые активным подключением (сервер
всё равно отклонит конфликт 409 — фильтр только для UX). Использует общий
`/resources/connections`, где `enrich_connections()` уже возвращает резолвленные
имена устройств/портов/типа линии — без клиентских джойнов для отображения таблицы.
Порты устройства можно редактировать прямо с этого экрана — не заходя в форму
устройства: кнопка «Управлять портами» рядом с каждым select порта в форме
подключения (`ConnectionFormModal.vue`) и такая же кнопка у каждого порта прямо
в строке таблицы (`ConnectionsView.vue`) открывают `DevicePortsModal.vue` —
переиспользует `DeviceInterfacesEditor.vue` и общий модуль
`api/deviceInterfaces.ts` (тот же, которым пользуется `DeviceFormModal.vue`,
без дублирования логики load/persist). После сохранения список интерфейсов в
`catalogs.items['interfaces']` обновляется точечно (`catalogs.replaceDeviceInterfaces`),
без полной перезагрузки справочников; если отредактированный порт был удалён,
его выбор в форме подключения сбрасывается автоматически.

Пятый — **«Отчёты»** (`/reports`): генерация регламентного Excel-отчёта
(4 листа) с опциональными фильтрами (по одной ИС, по структурным единицам —
переиспользует `StructuralUnitTree.vue` из фильтра устройств) и выгрузки
журнала аудита за период. Файл скачивается без ухода со страницы SPA
(`<a download>`, программный клик). Рядом — экран **«Шаблоны отчётов»**
(`/report-templates`, `ReportTemplatesView.vue`, ссылка с этого же экрана):
жизненный цикл шаблонов конструктора произвольных отчётов — список,
создание, переименование, дублирование, удаление, генерация, история
версий с восстановлением. Визуальный редактор содержимого — **«Конструктор»**
— доступен для обоих форматов: xlsx открывает `ReportGridEditorView.vue`
(`/report-templates/{id}/editor` — листы, колонки, строки с привязкой к
данным, ячейки с выделением/объединением и 4 типами содержимого), docx —
`ReportDocxEditorView.vue` (`/report-templates/{id}/editor-docx` — блоки
заголовок/абзац/таблица/разрыв страницы, добавление/удаление/перемещение,
блок-таблица переиспользует ту же логику источника данных, что и
повторяющаяся строка xlsx). Оба редактора и общая логика между ними
подробно описаны в «Ещё не сделано» ниже.

Шестой — **«Журнал аудита»** (`/audit-log`): только чтение (аудиторский след
намеренно не редактируется через UI), поиск, фильтр по действию и по разделу.
Имя раздела резолвится не хардкодом, а через `GET /api/v1/resources` (то же,
что `DISPLAY_NAMES` на бэкенде) — не расходится при добавлении новых ресурсов.

Седьмой — **«VLAN»** (`/vlans`): группировка по VLAN ID через специализированный
`/api/v1/vlan-dashboard` (один и тот же ID может иметь разные определения в
разных доменах — например, «локальный» VLAN без домена; экран это явно
отмечает как «требует внимания», а не считает ошибкой). CRUD отдельных
определений через общий `/resources/vlans`. Массовое назначение одного VLAN
нескольким устройствам сразу (`VLANFormModal.vue`-соседняя панель,
`POST /device-vlans/bulk-assign`) и полное управление VLAN-доменами
(`VLANDomainsPanel.vue`/`VLANDomainFormModal.vue` — CRUD, состав участников,
кнопка синхронизации от устройства-источника) раскрываются отдельными
кнопками рядом с фильтром.

Восьмой — **«Здания и помещения»** (`/buildings`): трёхуровневая иерархия
Здание → Помещение → Стойка с раскрывающимися узлами и CRUD на каждом уровне.

Девятый — **«Структурные подразделения»** (`/structural-units`): дерево с
CRUD (добавить корневую/дочернюю единицу, редактировать, удалить). Удаление
единицы с живыми потомками блокируется на клиенте до похода на сервер
(понятное сообщение вместо непрозрачного 409), сервер всё равно проверяет
это самостоятельно — двойная защита.

**Все разделы меню теперь имеют рабочие экраны в новом UI**, включая оба
редактора конструктора отчётов (xlsx и docx) и предпросмотр содержимого в
обоих — конструктор отчётов полностью перенесён.

## Стек

Vue 3 (`<script setup>` + TypeScript) · Pinia · vue-router · Vite · Vitest +
`@vue/test-utils`.

## Разработка

```bash
npm install
npm run dev        # Vite dev-сервер на :5173, проксирует /api на 127.0.0.1:8000
npm run build       # vue-tsc (проверка типов) + сборка в dist/
npm test            # vitest run
```

Бэкенд должен быть поднят отдельно на `127.0.0.1:8000` (см. корневой README) —
`vite.config.ts` содержит прокси `/api -> http://127.0.0.1:8000`, тот же
same-origin принцип, что и в проде, где собранный `dist/` раздаётся самим
FastAPI (см. `backend/app/api/system.py`, `backend/app/main.py`, `FRONTEND_DIR`).

## Цветовые схемы

Три схемы: **Бирюза** (по умолчанию), **Индиго**, **Медь** — см.
`src/stores/theme.ts` и `src/styles/theme.css`. Меняется только фирменный
акцент (`--brand`/`--brand-soft`) и лёгкий оттенок фона; статусные цвета
(норма/внимание/тревога) зафиксированы во всех схемах, чтобы выбор акцента не
мог сделать предупреждение неотличимым от активного пункта меню. Выбор
сохраняется в `localStorage` (`itr.colorScheme`).

## Архитектурные решения, важные для продолжения работы

- **Формы ответов API.** `/api/v1/resources/{resource}` всегда отдаёт
  `{items, total, offset, limit}` (см. `backend/app/services/crud.py:list_resource`),
  а специализированный `/api/v1/devices` — `{items, total}` без `offset/limit`
  (без серверной пагинации). Это разные формы — см. `PagedResponse<T>` vs
  `DevicesResponse` в `src/api/types.ts` / `src/api/client.ts`.
- **serialize() не резолвит внешние ключи** — отдаёт сырые id колонок.
  Резолв в отображаемое имя — на фронтенде, через `useCatalogsStore().label()`.
  Исключение: `enrich_connections()` (и `enrich_devices()`) резолвят некоторые
  поля сами на бэкенде — см. `Connection`/`Device` типы, где часть полей уже
  готовые строки, а не id.
- **Ключ ресурса в `/resources/{key}` не всегда очевиден из имени модели** —
  например, `DeviceInterface` живёт под ключом `interfaces`, а не
  `device-interfaces` (наступили на это при разработке `ConnectionFormModal`:
  404 на ровном месте). Источник истины — `backend/app/registry.py`, а не
  интуиция по названию SQLAlchemy-модели.
- **Структурные единицы** — самоссылающаяся иерархия `parent_id` (тот же
  паттерн, что `Department`). Фильтр по единице должен разворачиваться на всех
  потомков, а не быть точным совпадением id — см.
  `catalogs.unitAndDescendantIds()` и покрывающий тест в
  `src/stores/__tests__/catalogs.spec.ts`.
- Тесты стора используют фикстуры (`src/stores/__tests__/fixtures.ts`),
  снятые по форме с реальных ответов локально поднятого бэкенда, а не
  придуманы вручную.
- **"Устройство-хост" (сервер/СХД) определяется по названию типа устройства**,
  не по отдельному флагу на `PhysicalDevice` (такого поля нет в модели) —
  вынесено в `src/utils/deviceFilters.ts:filterHostDevices()`, используется и
  в форме ВМ (выбор хоста), и в форме ИС (`ISSourcesListEditor.vue`, тип
  источника «Физический сервер»). Совпадает с фильтром на бэкенде
  (`validate_vm_host` в `backend/app/services/validation.py`) — если меняется
  список ключевых слов там, стоит проверить и здесь.
- **Атомарные вложенные ресурсы поверх `/resources/`.** Не всё сохраняется
  через generic create/update/delete у ресурса — интерфейсы устройства
  (`PUT /api/v1/devices/{id}/interfaces`) и детали ИС
  (`PUT /api/v1/resources/information-systems/{id}/details`) представляют собой
  атомарные "пересобери всё целиком" эндпоинты: одним запросом
  создают/обновляют/удаляют набор дочерних записей по diff'у с тем, что уже
  в БД (см. `sync_interfaces`/`sync_information_system_details` в
  `backend/app/services/crud.py`). Оба используют `api.put()` напрямую
  (`src/api/client.ts`), а не `createResource`/`updateResource`/`deleteResource`.
  Загрузка/валидация/сохранение интерфейсов вынесены в `api/deviceInterfaces.ts`
  (не дублируются между `DeviceFormModal.vue` и `DevicePortsModal.vue`) —
  если понадобится третья точка входа для управления портами, использовать
  этот модуль, а не копировать логику снова.

## Ещё не сделано

- **VLAN-домены** теперь полностью управляются в новом UI —
  `VLANDomainsPanel.vue` (раскрывается кнопкой «Домены VLAN» на экране VLAN):
  CRUD домена (включая `source_device_id`, которого нет в generic-форме
  vanilla-версии — без него домен нельзя было бы синхронизировать),
  управление составом (`POST /vlan-domains/{id}/members` на добавление,
  обычный DELETE на удаление — доступно только при редактировании уже
  существующего домена, для нового сначала нужно сохранить) и запуск
  синхронизации (`POST /vlan-domains/{id}/sync`). **Не перенесены** только
  два вспомогательных сценария из `loadDeviceVlanEditor()` в
  `device-interfaces.js` — «Создать домен VLAN» и «Скопировать VLAN с
  другого устройства» прямо из формы устройства (оба в vanilla построены на
  нативных `window.prompt()`, не вписываются в стиль этого интерфейса);
  тот же результат теперь достижим через панель доменов на экране VLAN.
- **Быстрое добавление в справочники прямо из формы** (кнопка «＋» рядом с
  select'ом) реализовано через универсальные `QuickAddButton.vue`/
  `QuickAddModal.vue` — форма строится динамически по схеме
  (`quickAdd/schema.ts`, портировано с `quickFields`/`quickLabels` в
  `frontend/static/core.js`) вместо отдельного Vue-компонента на каждый
  справочник. **Подключено везде**, где выбор справочника мог заблокировать
  ввод остальных данных: форма устройства (объединённое поле «Тип /
  производитель / модель» — квик-добавление модели синхронизирует
  device_type_id/manufacturer_id формы; здание/помещение/стойка —
  синхронизируют родительские поля формы при создании; ОС; встроенная ОС;
  VLAN устройства — квик-добавление также обновляет централизованный стор
  VLAN, а не только каталоги, см. событие `vlan-created` в
  `DeviceVlanListEditor.vue`/`DeviceFormModal.vue`), форма здания и
  структурной единицы (структурная единица/родительская единица), форма
  VLAN (домен VLAN), ВМ (ОС), ИС (организация техподдержки, способ
  техподдержки, средство СКЗИ), подключений (тип физической линии связи),
  во всех переиспользуемых row-редакторах —
  `OpenPortListEditor.vue`/`ISProtocolsListEditor.vue` (протокол/порт),
  `SoftwareAssetListEditor.vue` (программный актив),
  `CatalogPickerListEditor.vue` (подразделения и места размещения ИС —
  кнопка опциональна через проп `quickAddResource`, не показывается, если
  он не передан), а также тип/скорость по умолчанию в генераторе
  `DeviceInterfacesEditor.vue` (в отдельных строках таблицы интерфейсов
  кнопки нет намеренно — при десятках строк она была бы избыточной;
  заведённый через генератор тип/скорость уже доступны для выбора в любой
  строке, т.к. опции общие). **Вложенное быстрое добавление** внутри формы
  быстрого добавления (флаг `nestedQuickAdd` на fk-поле в
  `quickAdd/schema.ts`) точечно подключено там, где отсутствие значения в
  справочнике реально блокирует заполнение формы: «Добавить: Модель
  устройства» → «+» у «Тип устройства»/«Производитель»; «Добавить: VLAN» →
  «+» у «Домен VLAN». Не обобщено на все fk-поля подряд и не поддерживает
  второй уровень вложенности. Не перенесено предзаполнение fk-полей
  текущими значениями внешней формы. `parent_id` для иерархии подразделений
  (`departments`) в это квик-добавление тоже не входит (осталась бы вторая
  вложенная модалка ради выбора родителя — не оправдано для формы из одного
  поля), но с 2.58.1 доступен в полноценной форме на экране «Другие
  справочники» (`CatalogRecordFormModal.vue`) — там же, где теперь и весь
  остальной CRUD для `departments`, см. корневой README.
  *Важные детали реализации:* `QuickAddModal.vue` телепортируется в
  `document.body` (`<Teleport to="body">`) — без этого, открытая из кнопки
  внутри формы устройства/ВМ/ИС, она оказалась бы вложенным `<form>`
  внутри `<form>` вызывающего компонента, что HTML не допускает.
  Компоненты, где после квик-добавления нужно не просто подставить `id`, а
  ещё и автозаполнить другие поля строки по данным созданной записи
  (`OpenPortListEditor.vue`/`ISProtocolsListEditor.vue` — порт/протокол,
  `DeviceFormModal.vue` — синхронизация типа устройства при добавлении
  модели), используют для этого сам объект `record`, эмитированный
  `@created`, а не повторный поиск по `catalogEntries`/`catalogs.items[...]`:
  `emit('created', ...)` в `QuickAddModal.vue` происходит синхронно сразу
  после обновления стора, до следующего цикла реактивности Vue — проп
  `catalogEntries`, переданный вниз через несколько уровней компонентов, в
  этот момент ещё не обязательно успел синхронизироваться.
- **Визуальный конструктор произвольных отчётов** (`report_builder.py`) —
  движок (grid-раскладка для xlsx, блочная раскладка для docx) и сам
  vanilla-редактор уже существовали в `main` до начала переноса на Vue, см.
  `report_grid.py`/`report_engine.py`/`report_builder.js`. Из Vue-интерфейса
  доступно управление ЖИЗНЕННЫМ ЦИКЛОМ шаблона — экран `/report-templates`
  (`ReportTemplatesView.vue`, ссылка с экрана «Отчёты»): список, создание
  (заводит минимальный валидный каркас config — бэкенд не принимает пустой
  `sheets`/`blocks`, см. `api/reportTemplates.ts:seedConfig`),
  переименование/правка описания (`ReportTemplateFormModal.vue` — формат
  нельзя сменить у существующего шаблона, это сделало бы уже сохранённый
  config невалидным для новой схемы), дублирование, удаление, генерация
  файла, история версий с восстановлением (`ReportTemplateVersionsModal.vue`).

  Визуальный редактор СОДЕРЖИМОГО перенесён для **обоих форматов**.

  **xlsx** — `ReportGridEditorView.vue` (`/report-templates/{id}/editor`,
  кнопка «Открыть в конструкторе» в строке шаблона): листы
  (добавление/удаление/переименование), колонки (ширина,
  добавление/удаление с переносом содержимого), строки (высота,
  добавление/удаление, повторение с источником данных — сущность,
  разворачивание по связи "многие", фильтры, сортировка), ячейки
  (выделение кликом, Shift+клик — диапазон, объединение/разъединение,
  4 типа содержимого: статический текст/поле БД/№ записи/формула, стиль).

  **docx** — `ReportDocxEditorView.vue`
  (`/report-templates/{id}/editor-docx`, та же кнопка — маршрут выбирается
  по формату шаблона): список блоков (заголовок с уровнем 1–6, абзац с
  выравниванием, разрыв страницы, таблица) с добавлением/удалением/
  перемещением вверх-вниз. Блок-таблица (`DocxTableBlockEditor.vue`) —
  тот же формат источника данных {`root_entity`/`expand`/`filters`/
  `sort_by`}, что повторяющаяся строка xlsx, плюс колонки (заголовок,
  источник поле/статика/№, для колонок можно менять порядок кнопками
  влево/вправо). Смена сущности таблицы при уже заполненных колонках/
  фильтрах/сортировке запрашивает подтверждение и сбрасывает их — иначе
  пути молча остались бы указывать на несуществующие в новой сущности поля.

  Общее для обоих редакторов: вставка полей БД через клик по select'у
  «Вставить поле» (`utils/reportEntityPaths.ts:flattenEntityPaths`, точный
  порт `rbFlattenPaths()`, путь до 2 связей вглубь, не более одной связи
  "многие" на путь), а не drag-and-drop, как в vanilla — тот же результат,
  надёжнее тестируется и доступнее с клавиатуры. Список операторов фильтра
  (`utils/reportFilterOps.ts:FILTER_OPS`) — общий модуль, переиспользуется
  и `GridCellInspector.vue` (фильтр повторяющейся строки xlsx), и
  `DocxTableBlockEditor.vue` (фильтр блока-таблицы docx), т.к. формат
  фильтра `{path, op, value}` одинаковый на обоих форматах. Оба редактора
  разбиты на чистую логику без побочных эффектов (`utils/gridCoverage.ts`,
  `utils/reportEntityPaths.ts`) с юнит-тестами и props-in/events-out
  панели свойств (`GridCellInspector.vue`, `DocxTableBlockEditor.vue`, не
  мутируют состояние сами) — отдельно от самих `ReportGridEditorView.vue`/
  `ReportDocxEditorView.vue`, которые владеют состоянием `sheets`/`blocks`
  и мутируют его напрямую (оправдано для чисто локального состояния
  экрана редактирования, не v-model).

  **Предпросмотр** (`POST /report-builder/preview`) тоже подключён к
  обоим редакторам — кнопка «Предпросмотр» отправляет текущее (ещё не
  сохранённое) содержимое на сервер и показывает первые записи каждого
  листа (xlsx, `GridPreviewTable.vue` — те же colspan/rowspan, что в
  редакторе, через ту же обобщённую `utils/gridCoverage.ts:
  visibleCellsForRow`, вынесенную из `ReportGridEditorView.vue` именно для
  переиспользования здесь) или каждого блока-таблицы (docx, в
  предпросмотре участвуют только блоки-таблицы — заголовок/абзац/разрыв
  страницы в предпросмотре нет смысла показывать). Ошибка структурной валидации по
  конкретному листу/блоку показывается прямо в его секции, не как общая
  ошибка запроса — тот же формат ответа, что и у самого сохранения. На
  этом визуальный конструктор произвольных отчётов можно считать
  полностью перенесённым на Vue: жизненный цикл шаблона, оба редактора
  содержимого, предпросмотр в обоих.
- На экране устройств: физические интерфейсы (порты), открытые порты,

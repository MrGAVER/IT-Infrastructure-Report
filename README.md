# РИС — Реестр ИТ-инфраструктуры

[![CI](https://github.com/MrGAVER/IT-Infrastructure-Report/actions/workflows/ci.yml/badge.svg)](https://github.com/MrGAVER/IT-Infrastructure-Report/actions/workflows/ci.yml)

Приложение для учёта информационных систем, физических устройств, сетевой инфраструктуры,
виртуальных машин, контейнеров и программных активов организации с выгрузкой регламентированного
Excel-отчёта из 4 листов (перечень ИС, инвентаризация физических устройств, организация
подключений, организация управления ВМ).

Стек: **FastAPI + SQLAlchemy + Alembic** на бэкенде, **Vue 3 + TypeScript + Vite** — фронтенд
(см. [Фронтенд](#фронтенд)), **SQLite** (локально/EXE) или **PostgreSQL** (Docker/сервер)
в качестве СУБД, выгрузка отчётов через **openpyxl**.

## Возможности

### CRUD по всем сущностям

Единый REST CRUD реализован для всех основных сущностей БД: организации, подразделения, структурные
единицы, здания, помещения, стойки, типы устройств/производители/модели, физические устройства,
информационные системы (и их подразделения, IP, протоколы), интерфейсы и IP интерфейсов, VLAN и
привязки VLAN, физические подключения, среды виртуализации, виртуальные машины и их IP, контейнеры,
программные активы, ПО физических устройств и ВМ, связи ИС с устройствами/ВМ/контейнерами, открытые
порты, журнал аудита.

Для каждой сущности доступен единый набор эндпоинтов:

```text
GET    /api/v1/resources/{resource}
GET    /api/v1/resources/{resource}/{id}
POST   /api/v1/resources/{resource}
PUT    /api/v1/resources/{resource}/{id}
DELETE /api/v1/resources/{resource}/{id}
GET    /api/v1/resources/{resource}/schema
```

Поддерживаются полнотекстовый поиск (`?q=`), точная фильтрация по полю (`?field=value`),
`offset`/`limit`, проверка уникальности и обработка внешних ключей. Удаление объекта, на который
есть ссылки, блокируется с HTTP 409 и понятным сообщением о том, где именно он используется.

### Структурные единицы

Справочник организационных структурных единиц (филиал, площадка, подразделение и т. п.) с
иерархией через родительскую единицу — тот же паттерн, что и у подразделений. Адрес размещения
физического оборудования (здание) дополнительно связывается со структурной единицей: у каждого
здания есть необязательное поле «Структурная единица», а через него — у всего оборудования,
размещённого в этом здании.

Эта связь используется при формировании отчётов (регламентированного и построенных в конструкторе
на сущностях реестра): отчёт можно ограничить оборудованием одной, нескольких или сразу всех
структурных единиц — выбор родительской единицы автоматически захватывает вложенные, без
необходимости отмечать каждую по отдельности. См. «Отчёт Excel» → «Фильтр по структурным единицам».

### Интерфейс

- Динамические CRUD-формы, построенные по схеме конкретной таблицы: текстовые/числовые/большие
  текстовые поля, Boolean как «Да/Нет», выпадающие списки для внешних ключей.
- Быстрое добавление справочных значений прямо из формы (кнопка «+»), без перехода в раздел
  справочников.
- Отдельные редакторы для сложных сущностей: интерфейсы физического устройства (с генерацией по
  шаблону имени/номера и подинтерфейсами порта — логическими интерфейсами на отдельном VLAN со своим
  IP и открытыми портами, как у маршрутизаторов и межсетевых экранов), VLAN устройства, IP-адреса и открытые порты ВМ, детали информационной
  системы (подразделения, протоколы, источники размещения, оборудование/ПО).
- Единые правила для всех мест, где добавляется открытый порт (TCP/UDP): ВМ, порты физических устройств,
  группы портов и протоколы передачи данных информационной системы. Список упорядочивается по номеру порта,
  но только когда добавляется следующая строка или форма открывается заново (заполняемая строка не «уезжает»
  из-под курсора); строки с одним номером порта подсвечиваются, сохранение с повтором блокируется (в форме и на
  сервере: `422` с номером порта — для ИС и в общем CRUD `/is-protocols` тоже); записи синхронизируются по id, без
  удаления и повторного создания. Уже существующие повторы показывает `GET /api/v1/integrity/open-port-duplicates`
  (ВМ, порты устройств, группы портов, ИС). Логика общая: `utils/openPorts.ts` и `composables/useUniquePortRows.ts`.
- Единый каталог оборудования «Производитель → Тип устройства → Модель».
- Сквозной поиск по нескольким сущностям сразу (устройства, ИС, ВМ, интерфейсы, IP интерфейсов,
  IP ВМ) с резолвингом IP-адреса до владеющего устройства/ВМ.
- Импорт физических устройств из CSV.
- Журнал аудита (read-only раздел): постраничная выборка с сервера — поиск по деталям и id записи, фильтры по
  действию и разделу, счётчики по всему журналу (`GET /api/v1/audit-log?q=&action=&entity_type=&offset=&limit=`);
  доступны все записи, а не только последние.
- Сортировка таблиц списков по клику на заголовок, предупреждение о несохранённых изменениях при
  закрытии форм устройства/ИС и вкладки браузера.
- Основные разделы вынесены в левое меню: ИС, устройства, интерфейсы, подключения, ВМ, контейнеры,
  ПО, VLAN, открытые порты, аудит и справочники.

### Миграции Alembic

`Base.metadata.create_all()` не используется как механизм создания схемы — схема БД создаётся и
обновляется только миграциями:

```bash
cd backend
alembic upgrade head
```

Новая миграция после изменения моделей:

```bash
cd backend
alembic revision --autogenerate -m "описание изменения"
alembic upgrade head
```

Откат последней миграции:

```bash
alembic downgrade -1
```

В Docker миграция выполняется автоматически перед запуском Uvicorn, в EXE — автоматически при
старте приложения.

### Правила согласования данных порта

Страница «Правила согласования портов» (раздел «Система») — модуль правил, по которым данные порта (роль,
режим trunk/access, VLAN) согласуются с портом на другом конце активного подключения. Правила хранятся в БД
(таблица `port_sync_rules`), их можно создавать и менять, **в том числе стандартные**: изменить условия, действие,
порядок, отключить; стандартное правило нельзя удалить, но можно вернуть к исходному виду («Сбросить»).

Правило — шаблон над парой «порт ← соседний порт»: условия на каждый порт (роль, режим, состояние VLAN: «не назначены
совсем» / «назначены (в том числе все)» / «назначены все — галочка “Все VLAN”»), отношение между ними («совпадают» /
«различаются»), действие и то, что порт берёт у соседа (роль, режим, VLAN: «не менять» / «взять набор соседа» /
«привести к режиму» — в access остаётся один VLAN с наименьшим номером; «объединить» — оба порта получают объединение
наборов VLAN, ни один VLAN не снимается; политика симметрична, поэтому не сочетается со сменой роли или режима;
«назначить все VLAN своего устройства» — «Все VLAN»: порт получает все VLAN, доступные его устройству, а не номера VLAN
соседа; уже назначенные не снимаются, в access не применяется).
Действие: **Автоматически** (направление
определяют условия; изменения применяются после предпросмотра и подтверждения), **Решает человек** (расхождение
известного вида, какой порт менять — выбирает человек, как и раньше) или **Не трогать** (пару не согласовывать).
Проверка идёт сверху вниз по порядку, решает первое подходящее правило; для каждой пары проверяются обе ориентации,
а автоматическое правило, подходящее обоим портам, уходит на ручное решение (кроме правил с политикой «объединить» —
они меняют оба порта сразу).

Стандартные правила: **«“Все VLAN” на порту — “Все VLAN” у соседа»** (автоматически, проверяется первым: на порту trunk
с «Все VLAN», а соседний порт тоже trunk, но «Все VLAN» у него нет — соседу назначаются все VLAN его устройства; если у
устройств разные наборы VLAN, наборы на концах линии могут остаться разными — план предупреждает об этом и помечает
подключение «расхождение останется»; на существующих установках правило добавляется при старте приложения без
миграции), **«“Все VLAN” на обоих портах — не трогать»** («Не трогать», приоритет 6: на обоих портах trunk с «Все VLAN», роли
совпадают, а номера VLAN различаются, потому что у устройств разные наборы VLAN, — пара не согласовывается и показывается в
плане как «Исключено правилом», а не «Нельзя применить»; расхождение на дашборде остаётся, его можно одобрить; при разных
ролях правило не срабатывает), «Пустой trunk получает VLAN соседа» (автоматически: на порту trunk совсем без VLAN, а на соседнем
trunk с VLAN или с «Все VLAN» — порту применяется trunk с VLAN соседа), **«Trunk: наборы VLAN на концах линии
объединяются»** (автоматически: на обоих концах trunk с наборами VLAN, и наборы различаются — оба порта получают
объединение номеров VLAN; ни один VLAN не снимается, поэтому правило безопасно; VLAN, которых нет у устройства порта,
пропускаются с предупреждением — расхождение на таком подключении может остаться, его решает человек) и три правила
«решает человек», повторяющие сверку дашборда: «Роль порта совпадает с ролью соседа», «Режим порта совпадает с режимом соседа», «Наборы VLAN на
концах линии совпадают».

Где применяется: кнопка «Согласовать по правилам…» на дашборде «Подключения» (все активные подключения с неодобренным
расхождением), блок «По правилам согласования» в окне проверки расхождения (одно подключение) и «Что сделает» на
странице правил (только это правило, даже отключённое). Ещё одно место — уведомление после сохранения устройства, в котором изменился список VLAN: порты в состоянии «Все VLAN» подхватывают новый VLAN сами, а согласование с соседями идёт только вручную, поэтому форма (после закрытия) проверяет подключения этого устройства предпросмотром плана и, если есть что согласовать, показывает предупреждение с кнопкой «Показать план» (автоматически ничего не применяется; «исключено правилом» и «расхождения нет» в счёт не идут; у устройства больше 500 подключений — общее напоминание без подсчёта). Везде сначала показывается **план** — что изменится, что
нельзя применить и почему, что остаётся за человеком; изменения записываются только после отметки «Я проверил план»
и одной транзакцией. VLAN переносятся по номеру в записи, доступные устройству целевого порта; номера, которых у
устройства нет, пропускаются с предупреждением. Не меняются порты группы, задающей режим и VLAN, и результат с
несколькими VLAN в access. Если правило меняет оба порта, план показывает изменения каждого порта отдельно, а порт,
который изменить нельзя, не мешает второму. Подключения, у которых расхождение после применения останется (часть VLAN
пропущена — нет у устройства, или один из двух портов не меняется), помечаются в плане, а в сводке называется их число
(«расхождение останется у: N», `summary.partial` по всему плану). Применение пишет порты пакетно: на 6000 портов (3000
подключений) — около 2–4 с вместо ~10 с, число запросов к БД от числа портов не зависит. Согласование не срабатывает само при сохранении данных — только по запросу
пользователя. Новое стандартное правило добавляется в существующую установку при ближайшем запуске приложения (по коду
правила; изменённые администратором правила не перезаписываются), миграция БД не нужна.

Элементы плана показываются **страницами** (до 300 за раз, кнопка «Показать ещё»), а сводка и `plan_hash` относятся ко
всему плану: применяется весь план, а не показанная часть. Первая страница считает план и кладёт его в серверный кэш
(ключ — условия плана и `plan_hash`; живёт 5 минут, не более 4 планов в памяти процесса); следующие страницы
запрашиваются с `plan_hash` первой и берутся срезом из кэша без запросов к БД. Применение кэш не читает — всегда
считает план заново. Кэш сбрасывается после применения и после любой правки правил; если он уже пуст (срок вышел,
другой воркер) и план изменился, страница отвечает 409 — предпросмотр нужно начать заново.

API (`/api/v1/port-sync`): `GET|POST /rules`, `PUT|DELETE /rules/{id}`, `POST /rules/{id}/reset`,
`POST /rules/reorder`, `POST /preview` (`{connection_ids?, rule_id?, offset?, limit?, plan_hash?}` → страница плана,
`summary` и `plan_hash` по всему плану, `page: {offset, limit, total, has_more}`; ничего не пишет), `POST /apply`
(`{connection_ids?, rule_id?, plan_hash, confirm: true}`; при изменении данных после предпросмотра — 409).

### Аутентификация и авторизация

По умолчанию выключена (`AuthSettings.enabled = False`) — однопользовательский локальный режим,
`/api/*` открыт без токена, поведение не отличается от версий до 2.61.0. Включается на экране
«Настройки» (нужен хотя бы один пользователь с ролью «Администратор» — завести его можно, пока
переключатель ещё выключен). Две роли: `admin` (полный доступ, управление пользователями и самим
переключателем) и `viewer` (только чтение данных; формировать и скачивать отчёты — журнал аудита, инвентаризацию,
предпросмотр и «Сформировать» по шаблону — viewer может, это не изменяет реестр). Пароли — `pbkdf2_hmac(sha256)`, токены сессий —
непрозрачные (в БД хранится только их sha256-хеш), блокировка учётной записи после серии неудачных
попыток входа и троттлинг входа по паре «IP + логин» с растущей задержкой (см. 2.110.0). **Блокировка и «знакомые» адреса.** После `INFRA_REGISTRY_AUTH_MAX_ATTEMPTS` (10) неверных паролей учётная запись блокируется на
`INFRA_REGISTRY_AUTH_LOCKOUT_MINUTES` (15) минут, но блокировка отклоняет вход (423 `ACCOUNT_LOCKED`) только с **незнакомых** адресов:
адрес, с которого этот пользователь уже входил успешно за последние `INFRA_REGISTRY_AUTH_KNOWN_CLIENT_DAYS` (30) дней, проходит
проверку пароля (верный пароль снимает блокировку), а подбор с него по-прежнему увеличивает счётчик и ограничивается
троттлингом входа. Без этого любой, кто достаёт до `/login`, мог бы держать администратора заблокированным постоянно. Адреса берутся
из записей `LOGIN` журнала аудита. За обратным прокси задайте `FORWARDED_ALLOW_IPS`, иначе у всех клиентов будет адрес прокси и
«знакомым» окажется любой; `INFRA_REGISTRY_AUTH_LOCKOUT_KNOWN_CLIENT_BYPASS=0` возвращает прежнее поведение (блокировка для всех адресов).
Любая роль может сменить свой собственный пароль (неверный текущий пароль — HTTP 422 с кодом
`WRONG_CURRENT_PASSWORD`, а не 401; такая попытка засчитывается как неудачный вход: счётчик блокировки, запись `LOGIN_FAILED`
в журнале аудита, а у заблокированной учётной записи пароль не проверяется — ответ 423) и посмотреть/завершить свои же
активные сессии (раздел «Моя учётная запись», см. 2.62.0), не дожидаясь администратора. Все
проверки, критичные для «не остаться без единого администратора» и учёт неудачных попыток входа,
устойчивы к нескольким одновременно пишущим процессам backend за общей БД — актуально для
серверного варианта (см. 2.63.0). Подробности реализации — в записях
[2.61.0](#история-изменений)/[2.62.0](#история-изменений)/[2.63.0](#история-изменений) истории
изменений.

## Быстрый старт

### Docker

Перед первым запуском скопируйте `.env.example` в `.env` и задайте свой `POSTGRES_PASSWORD` и
`INFRA_REGISTRY_SETUP_TOKEN` (без них `docker compose` откажется стартовать; токен — длинная случайная строка,
например `openssl rand -hex 24`):

```bash
cp .env.example .env
# отредактируйте .env
docker compose up --build
```

Данные хранятся в двух томах Docker: `pgdata` — база PostgreSQL, `appdata` (`/app/data` в контейнере приложения) —
сформированные отчёты (и база, если `DATABASE_URL` указывает на SQLite). Оба переживают пересоздание контейнеров
(`docker compose up --build`, `down`); `docker compose down -v` удаляет их. Процесс приложения работает от
непривилегированного пользователя `app` и может писать только в `/app/data`: код в образе доступен ему лишь для чтения.
`docker stop` завершает приложение штатно (uvicorn — PID 1 контейнера и получает SIGTERM).

Переменные окружения `.env` (все опциональны, кроме `POSTGRES_PASSWORD` и `INFRA_REGISTRY_SETUP_TOKEN`):

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `POSTGRES_PASSWORD` | — (обязательна) | пароль пользователя БД; допустимы любые символы (при `#`, `$` или пробеле возьмите значение в одинарные кавычки) |
| `POSTGRES_DB` / `POSTGRES_USER` | `infra_registry` / `infra` | имя БД и пользователя |
| `DATABASE_URL` | пусто | готовый адрес БД (внешний сервер, нестандартные параметры); имеет приоритет над `POSTGRES_*`, пароль в нём нужно экранировать самому (`@` → `%40`). Без него адрес собирается из `POSTGRES_*` и `INFRA_REGISTRY_DB_HOST` (в compose — `db`), с экранированием |
| `INFRA_REGISTRY_CORS_ORIGINS` | пусто (CORS выключен) | список разрешённых origin'ов через запятую; нужен только для отдельного фронтенда. Такие origin'ы также могут отправлять запросы, меняющие данные (см. «Защита от межсайтовых запросов») |
| `INFRA_REGISTRY_ALLOWED_HOSTS` | `*` в compose, `localhost,127.0.0.1` без него | допустимые значения заголовка `Host` (защита от DNS-rebinding) |
| `INFRA_REGISTRY_ALLOWED_CLIENTS` | пусто (без ограничений) | IP-адреса и подсети клиентов через запятую (`192.168.1.15,10.0.5.0/24`); остальные получают `403`. EXE задаёт его сам из `infra_registry.toml` |
| `INFRA_REGISTRY_SETUP_TOKEN` | — (обязателен в compose) | токен первичной настройки аутентификации (заголовок `X-Setup-Token`); `docker compose` не стартует без него |
| `INFRA_REGISTRY_BIND` | `127.0.0.1` | адрес, на котором compose публикует порт `8000`; `0.0.0.0` — доступ по сети (сначала включите аутентификацию) |
| `FORWARDED_ALLOW_IPS` | `127.0.0.1` | адреса обратных прокси, которым uvicorn доверяет при определении IP клиента; если указан не loopback-адрес (или `*`), для проверки origin учитывается и `X-Forwarded-Host` |
| `INFRA_REGISTRY_CSP` | строгая политика по умолчанию | `Content-Security-Policy` ответов; пустое значение отключает заголовок |
| `INFRA_REGISTRY_REPORT_RETENTION_DAYS` | `30` | через сколько дней удаляются сформированные отчёты (очистка при формировании нового); `0` — не удалять по возрасту |
| `INFRA_REGISTRY_REPORT_MAX_FILES` | `200` | сколько файлов отчётов (.xlsx/.docx) остаётся в каталоге: при формировании нового самые старые сверх лимита удаляются независимо от возраста (отчёт может сформировать роль viewer, без квоты цикл запросов заполнил бы диск); `0` — без ограничения по количеству |
| `INFRA_REGISTRY_DB_POOL_SIZE` / `INFRA_REGISTRY_DB_MAX_OVERFLOW` / `INFRA_REGISTRY_DB_POOL_TIMEOUT` | не заданы (значения SQLAlchemy: `5` / `10` / `30` с) | размер пула соединений PostgreSQL и время ожидания соединения; поднимайте при многих одновременных пользователях (не выше `max_connections` сервера БД). Для SQLite не применяются |

**Перед обновлением (Docker/PostgreSQL).** Контейнер `app` при каждом старте выполняет `alembic upgrade head`, а часть
миграций необратима, поэтому перед `docker compose up --build` с новой версией сделайте копию базы (автоматически для
PostgreSQL она не создаётся — это делается средствами сервера БД):

```bash
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > infra_registry_$(date +%Y%m%d-%H%M%S).dump
```

Восстановление (приложение остановите: `docker compose stop app`):

```bash
docker compose exec -T db sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists' < infra_registry_<дата-время>.dump
```

Для внешнего сервера (`DATABASE_URL`) выполните `pg_dump` с него. Том `pgdata` не заменяет копию: он защищает только от
перезапуска контейнера, но не от ошибочной миграции.

### Безопасность по умолчанию

**Docker.** По умолчанию compose публикует порт только на `127.0.0.1`, а `INFRA_REGISTRY_SETUP_TOKEN` обязателен.
Выключенная аутентификация оставляет реестр (IP-адреса, VLAN, ПО, топологию) открытым на чтение и запись всем, кто
достаёт до порта, а из контейнера включить защиту без токена нельзя: адрес клиента — шлюз Docker, не `localhost`.
Порядок для сервера:

1. Задайте `INFRA_REGISTRY_SETUP_TOKEN` в `.env` и запустите `docker compose up --build`.
2. Откройте `http://localhost:8000` на этом же компьютере (или по SSH-туннелю): «Настройки → Аутентификация», введите
   токен, создайте администратора и включите вход.
3. Только теперь, если нужен доступ по сети, добавьте в `.env` `INFRA_REGISTRY_BIND=0.0.0.0` и перечислите реальные
   имена/адреса сервера в `INFRA_REGISTRY_ALLOWED_HOSTS`, затем `docker compose up -d`.

Аутентификация по-прежнему **выключена** — реестр открыт без входа, как и раньше. Но выключенная
аутентификация больше не позволяет постороннему захватить приложение:

- **Первичная настройка** (создание пользователей и включение аутентификации) при выключенной
  аутентификации доступна только с `localhost` (прямое соединение, без заголовков прокси) либо — если
  задан `INFRA_REGISTRY_SETUP_TOKEN` — по заголовку `X-Setup-Token`. Интерфейс сам просит токен в
  «Настройки → Аутентификация», когда сервер отвечает 403 `SETUP_ACCESS_DENIED`. За обратным прокси или в
  Docker задайте токен.
- **CORS выключен**, а заголовок `Host` проверяется: чужая веб-страница в браузере владельца не может ни
  читать, ни менять данные локального приложения. Отдельному фронтенду разрешите origin явно.
- **Защита от межсайтовых запросов (CSRF).** CORS не мешает браузеру *отправить* «простой» POST без тела, поэтому при
  выключенной аутентификации вредоносная страница могла вслепую запустить `POST /api/v1/seed`, дублирование диаграмм,
  формирование отчётов или синхронизацию VLAN. Теперь запросы `POST`/`PUT`/`PATCH`/`DELETE` к `/api/` с чужим `Origin`
  (не совпадающим с `Host`, включая `null`) или с `Sec-Fetch-Site: cross-site` получают `403` с кодом
  `CROSS_ORIGIN_BLOCKED` до выполнения; проверка включена всегда, при любой настройке аутентификации. Не затрагиваются:
  запросы без `Origin` (curl, скрипты, Power Query), безопасные методы (`GET`, `HEAD`, `OPTIONS`) и работа интерфейса со
  своего адреса. Исключения: origin'ы из `INFRA_REGISTRY_CORS_ORIGINS` (запись `*` разрешает любой origin — защита тогда
  не работает, как и CORS); за обратным прокси, который подменяет `Host`, добавьте его внешний адрес в
  `INFRA_REGISTRY_CORS_ORIGINS` либо передавайте исходный `Host` (`proxy_set_header Host $host;` в nginx). Если в
  `FORWARDED_ALLOW_IPS` перечислены адреса прокси не из loopback, учитывается и первый адрес из `X-Forwarded-Host`.
  Отклонённый origin один раз записывается в журнал сервера с подсказкой. **Разработка:** прокси Vite (`npm run dev`,
  `changeOrigin: true`) заменяет `Host`, а браузер шлёт `Origin: http://localhost:5173` — перечислите его в
  `INFRA_REGISTRY_CORS_ORIGINS=http://localhost:5173`, иначе запись отвечает `403 CROSS_ORIGIN_BLOCKED`.
- **Журнал аудита** хранит автора действия: имя пользователя (если аутентификация включена) и IP-адрес.
- **Иконки диаграмм** проходят проверку по белому списку тегов и атрибутов SVG; `.svg`-экспорт вкладывает
  пользовательскую иконку как изображение (data URI), а не как исполняемую разметку.
- Ответы содержат `Content-Security-Policy` (кроме `/docs`, `/redoc`).

Открыть:

```text
http://localhost:8000        # UI (Vue)
http://localhost:8000/docs
```

### Запуск как EXE (Windows)

`InfraRegistry.exe` — самостоятельное Windows-приложение с локальным веб-интерфейсом, не требующее
интернета, PostgreSQL или Docker. При запуске оно:

1. создаёт/использует каталог рядом с самим EXE;
2. создаёт или обновляет SQLite БД `infra_registry.db`;
3. автоматически выполняет `alembic upgrade head` (если база создана предыдущей версией — сначала делает её резервную копию, см. ниже);
4. запускает локальный FastAPI/Uvicorn-сервер;
5. открывает браузер на `http://127.0.0.1:8000`.

**Хранение данных.** База данных SQLite и каталог отчётов хранятся **рядом с исполняемым файлом**,
а не внутри него:

```text
InfraRegistry.exe
infra_registry.db
reports\
```

Это позволяет переносить каталог приложения целиком вместе с базой, а обновление самого EXE не
удаляет накопленный реестр. Каталог с EXE должен быть доступен для записи текущему пользователю —
приложение создаёт/изменяет `infra_registry.db`, каталог `reports` и выполняет миграции.

**Резервные копии базы при обновлении.** Часть миграций необратима (удаляет данные), а в SQLite изменение схемы
нельзя откатить транзакцией: сбой посреди миграции оставляет базу в промежуточном состоянии. Поэтому, если при запуске
`infra_registry.db` существует, содержит данные и её версия схемы не равна текущей (то есть вы заменили EXE на более
новый), перед миграцией рядом с базой создаётся согласованная копия (средствами SQLite, это безопасно и при открытой базе):

```text
infra_registry.db
infra_registry.pre-3a7c1e5d.20261024-093000.bak   <- <имя базы>.pre-<версия схемы>.<дата-время>.bak
```

Путь копии выводится в консоли при запуске. Хранятся **5 последних** копий, более старые удаляются; удаляются только файлы
этой маски — ваши собственные `.bak` рядом с базой не затрагиваются. На уже актуальной базе, новой или пустой копия не
создаётся (запуск без обновления ничего не копирует). Если копию создать не удалось (нет места, нет прав на запись),
приложение **не запускает миграцию**, сообщает причину и завершается с кодом 2 — база остаётся нетронутой.

*Восстановление после неудачного обновления:* закройте приложение, верните прежний EXE, переименуйте повреждённый
`infra_registry.db` (например, в `infra_registry.broken.db`) и скопируйте нужный `.bak` под именем `infra_registry.db`.
Копия — обычный файл SQLite, открывается любым клиентом SQLite. Запуск без копии (на свой риск, например при нехватке
места) — переменная окружения `INFRA_REGISTRY_SKIP_BACKUP=1`.

**Сборка** выполняется **на Windows** (PyInstaller собирает исполняемый файл под текущую ОС;
сначала собирается основной UI — `installer\build_windows.bat` делает это автоматически,
поэтому требуется установленный Node.js 20+):

```bat
installer\build_windows.bat
```

Результат — `dist\InfraRegistry.exe`.

Рядом с ним скрипт кладёт `dist\README_EXE.md` (краткая инструкция для пользователя; исходник — `installer\README_EXE.md`) и
`dist\run_infra_registry.bat`. Ошибка копирования любого из файлов, как и ошибка PyInstaller, прерывает сборку с ненулевым кодом.

**Запуск** — двойным щелчком по `InfraRegistry.exe`, либо с параметрами (они важнее файла настроек):

```bat
InfraRegistry.exe --port 8010
InfraRegistry.exe --no-browser
```

**Перенос на другой ПК** — достаточно скопировать `InfraRegistry.exe`; при первом запуске
приложение самостоятельно создаст БД, каталоги и файл настроек.

#### Файл настроек и доступ с других компьютеров

Настройки EXE хранятся в файле `infra_registry.toml` **рядом с `InfraRegistry.exe`**. Если файла нет, приложение
при запуске создаёт его со значениями по умолчанию (существующий файл не перезаписывается; изменения применяются
после перезапуска). Подробные комментарии с примерами — в самом файле.

```text
InfraRegistry.exe
infra_registry.toml
infra_registry.db
reports\
```

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `[server] port` | `8000` | порт веб-интерфейса (`--port` важнее) |
| `[server] open_browser` | `true` | открывать браузер при запуске (`--no-browser` важнее) |
| `[access] allowed_clients` | `[]` | IP-адреса и подсети компьютеров, которым разрешено подключаться по сети |
| `[access] allowed_hosts` | `[]` | имена компьютера, по которым открывают приложение (по IP-адресу — без настройки) |

**По умолчанию доступ только с этого компьютера:** приложение слушает порт на `127.0.0.1`, из сети он не виден.
Чтобы пускать другие компьютеры, перечислите их в `allowed_clients` и перезапустите приложение — оно начнёт слушать
порт на всех интерфейсах, а подключения с адресов вне списка получат `403`. Этот компьютер разрешён всегда.

```toml
allowed_clients = ["192.168.1.15"]                      # один компьютер
allowed_clients = ["192.168.1.15", "192.168.1.20"]      # несколько компьютеров
allowed_clients = ["192.168.1.0/24"]                    # вся подсеть (192.168.1.1 – 192.168.1.254)
allowed_clients = ["192.168.1.0/24", "10.0.5.7"]        # подсеть и отдельный компьютер
```

Запись `/24` — длина маски подсети (`255.255.255.0`); `/16` — `255.255.0.0`, `/32` — один адрес. Поддерживается
только IPv4. Дальше нужно:

1. **Брандмауэр Windows.** Разрешить входящие TCP-подключения на порт приложения (командная строка администратора):
   `netsh advfirewall firewall add rule name="RIS" dir=in action=allow protocol=TCP localport=8000`
   (добавьте `remoteip=192.168.1.0/24`, чтобы правило действовало только для своей подсети).
2. **Адрес.** С другого компьютера открыть `http://<IP-адрес компьютера с EXE>:8000`. Адрес-литерал принимается
   сразу; если нужно открывать по имени (`http://reestr-pc:8000`), добавьте имя в `allowed_hosts`.
3. **Аутентификация.** Пока вход выключен, любой разрешённый компьютер читает и меняет весь реестр без пароля
   (при запуске в консоль выводится предупреждение). Первичная настройка (создание администратора, включение
   входа) по-прежнему доступна **только с самого компьютера, где запущено приложение**, поэтому сначала включите
   аутентификацию в «Настройки → Аутентификация», затем открывайте доступ.

Ошибка в файле (неверный адрес, неизвестный параметр, опечатка в синтаксисе) не игнорируется: приложение выводит
причину и не запускается, чтобы запись о доступе не оказалась «молча не применённой». Исправьте файл или удалите
его — он будет создан заново. Если каталог с EXE недоступен для записи и файл создать нельзя, приложение работает с
настройками по умолчанию (только локально).

> **Ограничения.** Подключение идёт по HTTP без шифрования — используйте только доверенную сеть. SQLite и один
> процесс рассчитаны на небольшое число одновременных пользователей (записи выполняются по очереди). Для
> постоянной работы многих сотрудников используйте серверный вариант: Docker + PostgreSQL.

## Отчёт Excel

Отчёт формируется по техническому заданию и состоит из 4 листов.

**Лист 1. Перечень ИС** — №, наименование и описание ИС, назначение использования, работники и
подразделения, использующие ИС, локализация, оборудование, на котором размещена ИС, протокол и
IP-адрес взаимодействия, применение сертифицированных СКЗИ, признак получения событий в SIEM,
организация внешнего взаимодействия/техподдержки и способ её оказания, описание процесса
функционирования ИС, а также физический сервер/ВМ (контейнер), обеспечивающие работу ИС, с их
IP-адресами.

**Лист 2. Инвентаризация физических устройств ИС** — №, вид устройства (сервер, сетевое
оборудование, средство защиты информации, рабочий ПК администратора), производитель, модель,
серийный номер, системное имя, версия ОС, порт и IP-адрес управления, признак получения событий в
SIEM, количество физических портов, адрес и здание расположения, помещение/место размещения.

**Лист 3. Организация подключений** — №, вид устройства, серийный номер и системное имя, ОС,
физический/логический порт и его IP-адрес, перечень открытых портов с протоколами, VLAN ID/Name,
тип и назначение физической линии связи, а также аналогичный набор колонок для соседнего
подключённого устройства (вид, серийный номер, системное имя, ОС, IP-адрес порта).

**Подинтерфейсы портов в отчёте** выводятся внутри строки своего порта, отдельных строк у них нет. Колонка порта:
`Gi0/0 (подинтерфейсы: Gi0/0.10 [VLAN 10], Gi0/0.20 [VLAN 20])`; IP, открытые порты и назначение подинтерфейса идут
в тех же колонках с его именем (`Gi0/0.10: 10.0.10.1/24`); VLAN подинтерфейсов добавляются в колонки VLAN ID / Name без
повторов. Если управление устройством висит на подинтерфейсе (у него стоит «Управление»), его порт и IP — это порт и IP
управления на Листе 2, в колонке IP соседа на Листе 3 и в IP физического сервера на Листе 1. Количество физических портов
подинтерфейсы не увеличивают. На схеме подключений IP подинтерфейсов входят в IP узла (назначение начинается с имени
подинтерфейса), а VLAN — во VLAN ребра порта.

**Подинтерфейсы в форме устройства и в группах портов.** Подинтерфейсы порта — таблица («Имя», «VLAN», «Управление», «Данные» и
разворачиваемый столбец «IP-адреса / маски», по умолчанию свёрнутый). VLAN подинтерфейса выбирается (`SearchableSelect`) только из
VLAN, выбранных на этом порту, и только из ещё не занятых другими подинтерфейсами порта. Группа портов может задавать подинтерфейсы
всех своих портов (галочка «Задать подинтерфейсы»): каждому порту записываются подинтерфейсы `<порт>.<номер VLAN>` с общими ролью,
IP и открытыми портами, остальные подинтерфейсы порта удаляются; у такого порта список только для просмотра. Правило «VLAN
подинтерфейса — один из VLAN порта» (у порта с «Все VLAN» — любой VLAN устройства) проверяют и форма, и сервер: `PUT /devices/{id}/interfaces`
отвечает 422, если после записи портов и групп подинтерфейс остался на VLAN, не выбранном на его порту. В окне группы «Скопировать
значения с порта» умеет копировать и подинтерфейсы порта: они становятся шаблонами группы (без имён и id), а те, чей VLAN не входит
в VLAN группы, не копируются, и уведомление называет их.

**Подинтерфейсы на дашборде устройств и «устаревший» VLAN.** Подинтерфейс с ролью «Управление» показывается в списке
устройств как порт и IP управления (`Gi0/0 (подинтерфейс Gi0/0.99)`), как и в отчёте. Подинтерфейс никогда не удаляется
молча: если VLAN сняли с устройства, убрали из его типа или перенесли в другой домен, подинтерфейс остаётся на этом VLAN.
Форма устройства предупреждает об этом сразу при снятии VLAN, помечает порт значком и до отправки на сервер не даёт
сохранить, пока подинтерфейсу не выбран другой VLAN (или он не удалён); при переносе VLAN между доменами оставшиеся
подинтерфейсы перечисляются в журнале аудита. Автоимена подинтерфейсов (`<порт>.<VLAN>`) следуют за переименованием
порта, имена, введённые вручную, остаются как есть.

Все подинтерфейсы на недоступном VLAN по реестру сразу показывает диагностика
`GET /api/v1/integrity/stale-subinterfaces` (устройство, порт, подинтерфейс, VLAN и причина `reason`: `device` — VLAN больше не разрешён
устройству, `port` — разрешён устройству, но не выбран на порту; в `group_subinterfaces` — шаблоны подинтерфейсов групп портов на VLAN,
которого у группы больше нет; только чтение). В форме устройства
предупреждение о снятом VLAN имеет кнопку «Показать» (раскрывает порты с такими подинтерфейсами), а у самого подинтерфейса —
список «Перенести на VLAN…»: VLAN меняется одним действием, автоимя пересчитывается. Если таких подинтерфейсов много, над
таблицей портов появляется панель «Перенести все на VLAN…»: все они переносятся на выбранный VLAN устройства разом (где на
порту этот VLAN уже занят, подинтерфейс остаётся на месте, и уведомление называет такие).

Диагностика видна и в интерфейсе: на экране «VLAN» над таблицей появляется карточка «Подинтерфейсы на VLAN, не разрешённом
устройству» со списком по устройствам и кнопкой «Открыть устройство» (откроется форма, где подинтерфейс переносят или удаляют);
после сохранения устройства карточка обновляется, а если проблем нет — на экране её нет.

Назначение линии связи (управление / передача данных) не вводится в подключении — оно берётся из
ролей портов (`is_management` / `is_data_transfer` у самого интерфейса). Дашборд «Подключения»
сверяет конфигурацию портов-соседей: **роль**, **режим порта** (trunk / access) и **набор VLAN**
(по номеру VLAN, не по записи справочника). Если что-то из этого различается (например, порт
управления сервера включён в порт коммутатора, настроенный на передачу данных, или один конец
линии — trunk, другой — access), подключение попадает в «Расхождения»: можно выровнять роль,
поправить режим и VLAN в окне портов устройства или одобрить расхождение.

**Правка порта прямо с дашборда.** Карандаш рядом с именем порта в строке (и кнопки «Изменить порт…» в окне проверки
расхождения) открывает окно «Конфигурация порта»: роль (тип использования: управление / передача данных), режим
(access / trunk) и набор VLAN. VLAN предлагаются те же, что в форме устройства (типа устройства и собственные); в access
выбирается один VLAN, при переходе trunk → access остаётся VLAN с наименьшим номером. Кнопка «Задать как у соседа» берёт
роль, режим и VLAN порта на другом конце линии (по номеру VLAN; номера, которых нет у устройства, не назначаются, об
этом сообщается). Окно сразу показывает, совпадёт ли порт с соседом после сохранения. Режим меняется общим каскадом
(`POST /interfaces/{id}/vlan-mode-cascade[/preview]`): сервер считает связанные порты и группы, а окно показывает
последствия до применения. Роль и VLAN уходят в том же запросе (поле `port: {role?, vlan_ids?}`) и записываются **одной
транзакцией** с каскадом: либо записано всё, либо ничего — состояния «режим сменён, а роль и VLAN нет» не бывает; ошибку в
роли или VLAN (например, VLAN, которого нет у устройства, или несколько VLAN при целевом access) сервер показывает уже при
предпросмотре, до подтверждения. Если режим не меняется, роль и VLAN записываются атомарным запросом
`PUT /api/v1/interfaces/{id}/port-config` (`{role?, vlan_ids?, mode?}`; `vlan_ids` — полный набор, `mode` — только проверка:
если режим порта изменился, ответ 409). Порт в группе, которая задаёт режим и VLAN, по VLAN не правится (409) — меняйте
группу; роль у такого порта менять можно. Запись попадает в журнал аудита, статус сверки пересчитывает сервер. Форма подключения
перед сохранением показывает роль, режим и VLAN обоих портов и не сохраняет подключение с
расхождением молча: нужно выровнять роль порта или одобрить расхождение (режим и VLAN правятся в окне
портов — кнопка «Управлять портами» в форме). Сверку для формы делает сервер теми же правилами
(`GET /api/v1/connections/port-config/preview?source_interface_id=&destination_interface_id=&connection_id=&is_active=`),
поэтому предупреждение формы и статус на дашборде не расходятся; если сервер не ответил, форма
сверяет хотя бы роли по каталогу. Дашборд показывает такие подключения
(счётчик, фильтры «Расхождения» / «Одобренные», пакетное одобрение), а одобрение теряет силу, как
только меняется роль, режим или набор VLAN любого из портов. Неактивные подключения в сверке не
участвуют.

Таблица дашборда постраничная: поиск, фильтры, статус сверки и счётчики считает сервер
(`GET /api/v1/connections?q=&is_active=&port_config_status=&offset=&limit=`), браузер держит только
текущую страницу, поэтому число подключений не ограничено 1000 записями. Поиск нечувствителен к
регистру и для кириллицы (в SQLite для этого подменяется встроенный `LOWER()`, см. `app/db.py`).
«Одобрить все найденные» одобряет расхождения по всем страницам под текущими поиском и фильтром.

**Лист 4. Организация управления ВМ** — название и ОС виртуальной машины, наименование контейнера,
физическое устройство-хост по его системному имени, среда виртуализации и её версия, целевое
назначение ВМ/контейнера, IP-адрес и IP-адрес администрирования, открытые порты с протоколами,
развёрнутые программные активы (1С, веб-сервер, файловый сервер, AD и т. п.).

**Фильтр по структурным единицам.** Перед формированием отчёта (кнопка «Сформировать Excel» на
дашборде, и генерация шаблонов конструктора, построенных на сущностях реестра — см. ниже) можно
ограничить его оборудованием, размещённым в одной, нескольких или всех структурных единицах сразу
(см. раздел «Возможности» → «Структурные единицы»). Без выбора отчёт формируется как раньше, без
ограничения.

## Приложение к структурной схеме (Word)

Отдельный отчёт (страница «Отчёты» → «Приложение к структурной схеме», `POST /api/v1/reports/structural-appendix`,
тело `{is_name?, structural_unit_ids?}`) — Word-документ из трёх пронумерованных таблиц под заголовком
«Приложение к структурной схеме» / «ЕАИС `<имя>`». Имя ИС (по умолчанию «ЕАИС ТО»; ведущее «ЕАИС»/«ИС» в заголовках не дублируется) подставляется в заголовки
(«ЕАИС ТО», «… ИС ТО»); необязательный фильтр по структурным единицам действует так же, как у Excel-отчёта.

1. **Сведения о назначении линий связи** — строка на каждое действующее подключение
   (`Производитель модель (системное имя) (порт)` — то же для второго конца). Назначение — одна объединённая
   ячейка на группу линий: «управление активами», «передача данных», «передача данных и управление активами»
   (объединение ролей обоих портов и их подинтерфейсов; линии без роли идут последними). Неактивные
   подключения не попадают в документ.
2. **Перечень VLAN** — под строкой-заголовком устройства (`Тип Производитель модель (имя) (серийные номера)`)
   идут его VLAN: идентификатор, имя, адресация «IP/префикс» как введено на устройстве. Участники одного стека —
   одна группа без дублей; устройства без VLAN не показываются.
3. **Перечень телекоммуникационного оборудования** — все устройства: наименование, заводской номер, системное
   имя, IP управления (по одному на строку ячейки, без префикса), место размещения — объединённая ячейка на
   устройства одного помещения.

Порядок устройств — порядок их создания в реестре, участники стека идут подряд. Данные собирает
`backend/app/services/structural_appendix.py` (на том же загрузчике реестра, что и Excel-отчёт), документ
рисует `structural_appendix_docx.py`; оформление (Times New Roman, сетка, поля) выбрано по обычаям делового
документа. Прежний шаблон конструктора «Приложение к структурной схеме (по образцу)» (плоские таблицы без
объединения ячеек) удалён миграцией `a9e3d4f17b26`: она убирает только нетронутую заготовку, отредактированный
пользователем шаблон с этим именем остаётся.

## Конструктор произвольных отчётов

Помимо регламентированного 4-листового отчёта (см. выше), приложение включает **конструктор
произвольных отчётов** — модуль, позволяющий пользователю без программирования собрать
собственный отчёт `.xlsx` или `.docx` на основе данных реестра. Открывается пунктом меню «🧩
Конструктор отчётов». Формат `.xlsx` редактируется визуальным **grid-редактором листа** (см.
ниже), формат `.docx` — **блочным редактором документа** (см. ниже).

При обновлении в список шаблонов автоматически добавляется готовый шаблон:
- **«Регламентированный отчёт — заготовка (4 листа)»** (`.xlsx`) — точное воспроизведение
  содержимого фиксированного отчёта выше (данные и заголовки совпадают 1:1 — проверено тестом на
  реальных данных, не только структурно), но собранное через grid-движок конструктора и открытое
  для дальнейшей правки. Подробности — в записи 2.39.0 в истории изменений ниже и в комментарии в
  начале `backend/app/services/report_seed_templates.py`.

Word-документ «Приложение к структурной схеме» формирует отдельный отчёт (см. раздел
[«Приложение к структурной схеме (Word)»](#приложение-к-структурной-схеме-word)); бывший шаблон-заготовка
конструктора для него (запись 2.42.0) удалён миграцией `a9e3d4f17b26`.

### Что умеет grid-редактор (.xlsx)

Редактор показывает лист как настоящую таблицу-канвас (строки/колонки/ячейки), а не форму со
списком колонок — состав, положение и оформление каждой ячейки задаются визуально:

- **Перетаскивание полей из палитры прямо на ячейку листа** (drag-and-drop). Палитра строит
  плоский список доступных путей на глубину до двух связей, включая связи «многие-ко-многим»
  через связующие таблицы (например, `is_departments[].department.name` — подразделения ИС).
  Первое поле, перетащенное в строку, автоматически включает для неё повторение (см. ниже) и
  привязывает её к соответствующей сущности.
- **Повторяющиеся строки.** Любая строка листа может быть отмечена как «повторяющаяся» —
  тогда при генерации файла она клонируется по одной физической строке на каждую запись
  выбранной сущности (с опциональным циклическим разворотом по связи «один/многие-ко-многим» —
  например, отдельная строка на каждую ВМ каждого физического сервера — и фильтрами по любому
  доступному пути поля: равно / не равно / содержит / не содержит / не пусто / да·нет).
  Остальные строки — статические (заголовки, титульная часть, произвольный текст).
- **Объединение ячеек** по горизонтали и вертикали (выделение диапазона — клик по первой ячейке,
  Shift+клик по последней) — с проверкой, что вертикальное объединение не пересекает
  повторяющуюся строку.
- **Оформление ячейки**: жирный/курсив/подчёркнутый, рамка, перенос текста, выравнивание по
  горизонтали/вертикали, цвет фона и текста, числовой формат (в т.ч. даты) — сохраняется как
  настоящее форматирование ячейки в итоговом `.xlsx` (не только текст); высота строки при
  необходимости автоматически увеличивается под перенесённый текст (см. запись 2.41.0).
- **Формулы Excel** — ячейка может содержать формулу (`=...`), которую вычислит сам Excel при
  открытии файла; в тексте формулы, как и в статическом тексте, работает подстановка параметров
  (`{{ключ}}`, `{{report_date}}`).
- **Параметры отчёта**, которые пользователь вводит непосредственно перед формированием файла
  (например, «Организация», «Дата отчёта», «Составил»).
- **Живой предпросмотр** — материализованные строки/ячейки (с учётом объединений и оформления)
  можно посмотреть прямо в редакторе, не сохраняя шаблон и не создавая файл.
- Несколько листов на шаблон; шаблоны можно **сохранять, дублировать, смотреть историю версий и
  восстанавливать** предыдущее состояние, удалять.

### Что умеет блочный редактор (.docx)

Документ собирается из блоков сверху вниз, порядок блоков — это порядок содержимого в файле:

- **Заголовок** (уровень 1-6) и **Абзац** (с выравниванием) — текст, в котором работает
  подстановка параметров (`{{ключ}}`, `{{report_date}}`), как и в xlsx.
- **Таблица** — привязывается к сущности реестра (тот же выбор сущности/поля/фильтров/сортировки/
  циклического вывода по связи, что и в xlsx-редакторе, с тем же помощником-подсказкой пути поля);
  колонка — заголовок + один из трёх источников: поле из БД (с разделителем для полей-списков),
  статический текст или № по порядку. Колонки и блоки переставляются кнопками (←/→ и ↑/↓).
- **Разрыв страницы.**
- **Живой предпросмотр** табличных блоков и сохранение/формирование — по общей схеме с xlsx.

### Ограничения текущей версии

- В grid-редакторе (.xlsx) нет многоклеточного выделения мышью (только Shift+клик по паре ячеек),
  undo/redo, копирования ячеек и авто-подбора ширины колонок по содержимому — состав и порядок
  листов/строк/колонок настраивается явными действиями (кнопки +/✕, инспектор ячейки/строки справа).
- В блочном редакторе (.docx) нет drag-and-drop полей на таблицу (путь поля вводится текстом с
  помощником-подсказкой, как в старом xlsx-редакторе до grid) и нет группировки строк таблицы под
  вложенным заголовком (см. пример в описании шаблона «Приложение к структурной схеме» выше) —
  один блок-таблица всегда плоский, на одной сущности.

### Как это устроено технически

- `backend/app/services/report_meta.py` — граф полей и связей (`to_one`/`to_many`) выводится
  **автоматически** из существующих моделей БД (`MODEL_MAP`) через `sqlalchemy.inspection`, без
  ручного описания каждой пары таблиц; при добавлении новой сущности/поля в схему БД конструктор
  подхватывает её без изменений в этом модуле.
- `backend/app/services/report_engine.py` — разбор путей полей, подстановка параметров,
  циклический вывод строк по связи и (для формата `.docx`) структурная валидация блоков документа.
- `backend/app/services/report_grid.py` — grid-движок формата `.xlsx`: валидация листа (позиции и
  объединения ячеек, источники данных повторяющихся строк), материализация конфигурации в
  физические строки/ячейки и рендеринг в настоящий `.xlsx` через openpyxl (стили, объединение,
  числовой формат, формулы), а также предпросмотр без записи файла на диск.
- `backend/app/services/report_render.py` — сборка `.docx` (python-docx: заголовки, абзацы,
  таблицы, разрывы страниц) и предпросмотр блоков документа.
- `backend/app/api/report_builder.py` — REST API: `GET /api/v1/report-builder/entities` (список
  сущностей/полей/связей для UI), CRUD `/api/v1/report-templates` (+ история версий и
  восстановление), `POST /api/v1/report-templates/{id}/generate`, `POST
  /api/v1/report-templates/{id}/duplicate`, `POST /api/v1/report-builder/preview` — валидация и
  предпросмотр диспетчеризуются по `format` шаблона (`xlsx` → `report_grid.py`, `docx` →
  `report_engine.py`/`report_render.py`), поскольку обе структуры конфигурации хранятся в одном
  JSON-поле `config` и неразличимы по форме без знания формата.
- Конфигурация шаблона (листы/строки/ячейки, параметры) хранится одним JSON-документом в таблице
  `report_templates` — набор возможных полей/связей динамический и выводится из схемы БД, поэтому
  жёсткая реляционная схема под конструктор отчётов дублировала бы её и требовала бы отдельной
  миграции на каждый новый тип ячейки.
- **`frontend-vue/src/views/ReportGridEditorView.vue`** (.xlsx) и **`ReportDocxEditorView.vue`**
  (.docx) — визуальные редакторы содержимого шаблона в браузере: листы/колонки/строки и ячейки с
  выделением/объединением (xlsx) или блоки заголовок/абзац/разрыв/таблица (docx). Поля БД
  вставляются кликом по select'у «Вставить поле» — не drag-and-drop, как было в удалённом
  vanilla-варианте: тот же результат, но надёжнее тестируется и доступнее с клавиатуры. Оба
  редактора подключены к живому предпросмотру и истории версий шаблона. Подробности — в
  [`frontend-vue/README.md`](frontend-vue/README.md).

### Зависимости backend

`backend/requirements.txt`, `requirements-dev.txt` и `requirements-build.txt` задают допустимые диапазоны версий; **точные
версии с хешами** зафиксированы в `backend/requirements.lock` (runtime), `backend/requirements-dev.lock` (runtime + тесты и
анализ) и `backend/requirements-build.lock` (runtime + PyInstaller для сборки EXE). Docker-образ, CI и сборка EXE
(`installer/build_windows.bat`) ставят пакеты из lock-файлов (`pip install --require-hashes -r ...`), поэтому сборка завтра даёт те
же версии, что сегодня, а подмена пакета на PyPI не пройдёт проверку хеша. Версии общих пакетов во всех трёх lock-файлах
одинаковы: в EXE попадает ровно то, что тестируется в CI. Lock универсальный (Linux, Windows, macOS), Python 3.12. Скрипт
сборки EXE не обновляет `pip` (версия из venv Python 3.12 понимает `--require-hashes`) и не удаляет лишние пакеты из уже
существующего `.venv`: для воспроизводимой сборки удалите каталог `.venv` перед запуском.

Обновление после правки `requirements*.txt` (или чтобы подтянуть свежие версии в пределах диапазонов):

```bash
pip install uv
cd backend
uv pip compile requirements.txt       --universal --generate-hashes --python-version 3.12 -o requirements.lock       --no-header
uv pip compile requirements-dev.txt   --universal --generate-hashes --python-version 3.12 -o requirements-dev.lock   --no-header
uv pip compile requirements-build.txt --universal --generate-hashes --python-version 3.12 -o requirements-build.lock --no-header
# подтянуть новые версии: добавьте --upgrade (или --upgrade-package <имя> для одного пакета), затем прогоните тесты
```

CI проверяет, что lock-файлы актуальны (пересборка не даёт diff), запускает `pip-audit` по `requirements.lock` (блокирует сборку)
и по `requirements-build.lock` (только сообщает: PyInstaller и его хуки иногда дают замечания, не относящиеся к рантайму).

### Пакет `backend/app/services/crud/`

Бывший `crud.py` на 1382 строки разрезан по ответственностям; публичный API (`from app.services.crud import ...`)
прежний. Зависимости идут в одну сторону, циклов нет (проверяет `tests/test_crud_package.py`):

## Известные ограничения и заметки

- EXE-вариант — однопользовательский локальный режим; для одновременной работы нескольких
  сотрудников по сети используйте серверный вариант (Docker + PostgreSQL). С 2.61.0 это не жёсткое
  ограничение, а настройка по умолчанию: аутентификацию можно включить и в EXE-варианте
  («Настройки → Аутентификация»), если несколько человек работают с одним и тем же файлом БД. С 2.150.0
  подключение к EXE с других компьютеров открывается в `infra_registry.toml` (`allowed_clients`), см.
  [«Запуск как EXE»](#запуск-как-exe-windows).
- `backend/alembic/README` — служебный файл, сгенерированный самим Alembic, и не относится к
  документации приложения.
- **Alembic-миграции и PyInstaller:** если новая data-миграция импортирует что-то из `app.services.*`
  ТОЛЬКО внутри своих `upgrade()`/`downgrade()` (а не так, как обычный код приложения — через
  цепочку импортов, достижимую из `main.py`), добавьте этот модуль явной строкой в `hiddenimports`
  в `infra_registry.spec` — `collect_submodules('app')` не всегда достаточно (см. запись 2.40.0 в
  [CHANGELOG.md](./CHANGELOG.md)), и падение проявляется только в frozen EXE-сборке, не в
  Docker/обычном запуске.
- **Тесты не проверяют реальную цепочку alembic-миграций.** `tests/conftest.py` строит схему БД
  через `Base.metadata.create_all()` из текущих определений моделей — быстро, но означает, что
  расхождение между моделью и тем, что реально накопится в БД после `alembic upgrade head` на
  продовой истории миграций, невидимо для pytest (см. запись 2.43.0 — так `information_systems.name`
  потеряло UNIQUE на несколько миграций и ни один тест этого не заметил). При добавлении
  `batch_alter_table()` на SQLite стоит вручную проверять итоговую DDL (`sqlite_master`), а не
  полагаться только на зелёный pytest.
- **PostgreSQL: цепочка миграций Alembic проходит на пустой базе** (с 2.156.0; проверено на PostgreSQL 16). Раньше
  `alembic upgrade head` на чистом томе падал, и контейнер из `docker-compose.yml` не стартовал. Исправлено в девяти
  миграциях: булевы литералы `1`/`0` в сырых SQL заменены параметрами (`e8c2f1a9b430`, `e7a2c9f4d813`, `8c5d1f7a2b40`,
  `b7f2c1e5a904`), для `6f4b2c8d1a90` и `c9a4e7d2f610` добавлены ветки PostgreSQL вместо пересборки таблицы сырым
  SQLite-DDL (внешний ключ и уникальность меняются на месте), у `f4a29c7e1d60` убран алиас в `HAVING` и повторное
  ограничение уникальности, у `c4a91e6f2b83` и `d8e35a1c7f60` `DateTime(timezone=True)` заменён на `DateTime()` (в
  SQLite DDL тот же, в PostgreSQL столбцы стали `TIMESTAMP`, как в моделях). Путь SQLite не менялся.
  **Что проверено:** `tests/test_migrations_postgres.py` (пустая база доходит до единственного head, повторный `upgrade`
  ничего не меняет, все таблицы и колонки моделей на месте, уникальность и внешние ключи моделей действуют, VLAN
  уникален в пределах домена, ветки с данными трёх миграций), весь набор тестов на схеме из миграций (job
  `test-postgres-migrations`) и живой запуск приложения на пустой базе (`backend/tests/tools/pg_app_smoke.py`: `alembic
  upgrade head`, `uvicorn`, создание данных по API, Excel-отчёт).
  **Чего это не гарантирует.** Ветки миграций, работающие с накопленными данными старой схемы, на PostgreSQL проверены
  только для трёх миграций выше; остальные (`38e9b2624a53`, `944bd490d967`, `a1b7c9d3e502`, `c4e8a7d91b20`,
  `d8e35a1c7f60`) на пустой базе проходят, а на строках не проверялись — это важно, только если прогонять цепочку с
  нуля поверх базы с данными. Модели и миграции по-прежнему расходятся, причём одинаково на SQLite и PostgreSQL
  (`alembic check`: остатки старых колонок `os_name`, `os_version`, `virtualization_platform_id`, таблица
  `virtualization_platforms`, обязательность `created_at`/`updated_at`, часть индексов); приложению это не мешает
  (лишние колонки необязательны), а `test_migrations_postgres.py` следит за тем, чтобы так оставалось. Порядок
  сортировки по тексту в PostgreSQL зависит от локали базы (в `en_US` порт `eth0` стоит перед `Gi0/1`, в SQLite — после),
  пустые значения в выдаче отчёта идут первыми на обоих движках (`ORDER BY … IS NULL DESC`).
- **Тесты backend идут и на SQLite, и на PostgreSQL.** Job `test-postgres` в CI выполняет весь набор на PostgreSQL 16
  (`INFRA_REGISTRY_TEST_DATABASE_URL`; схема создаётся из моделей, между тестами таблицы очищаются), job
  `test-postgres-migrations` — тот же набор на схеме, собранной цепочкой миграций (`INFRA_REGISTRY_TEST_SCHEMA=migrations`),
  и затем живой запуск приложения. Локально:
  `INFRA_REGISTRY_TEST_DATABASE_URL=postgresql+psycopg://user:pass@localhost:5432/infra_test pytest` (к этой команде
  добавьте `INFRA_REGISTRY_TEST_SCHEMA=migrations` для схемы из миграций). Тесты с пометкой `@pytest.mark.sqlite_only` в
  этом режиме пропускаются, а с `@pytest.mark.postgres_only` (например, `test_migrations_postgres.py`) выполняются только в нём.
  Для воспроизведения CI создавайте базу с локалью `en_US.UTF-8`, как у образа `postgres:16`: сортировка текста зависит от неё.
  **Что учитывать при написании тестов с БД.** SQLite прощает то, что PostgreSQL отвергает или делает иначе, поэтому тест,
  зелёный локально, может упасть в `test-postgres`:
  - не кладите в БД через ORM значения, которые PostgreSQL не хранит. Главный пример — NUL-байт `\x00` в текстовых полях
    (`DataError: PostgreSQL text fields cannot contain NUL (0x00) bytes`; так упал `test_structural_appendix.py` в 2.149.0).
    Такой вход проверяйте unit-тестом функции без БД, а в тесте с БД берите значение, которое хранится на обоих движках
    (например, `\x08` вместо `\x00`);
  - порядок строк, блокировки `FOR UPDATE`, частичные индексы и типы ведут себя иначе (см. комментарий к job в
    `.github/workflows/ci.yml`): тест, зависящий от порядка, должен задавать его явно (`ORDER BY`/сортировка), а не
    полагаться на порядок вставки;
  - если тест трогает схему, ограничения или сырой SQL, прогоните его локально на PostgreSQL (команда выше) до слияния.
- **Образ Docker не только собирается, но и запускается** (smoke-тест `/api/v1/health` и `/` в CI — на SQLite
  внутри контейнера; PostgreSQL и цепочку миграций на ней проверяет job `test-postgres-migrations`, но не сам образ:
  `docker compose up` на PostgreSQL в CI не выполняется).
- **Миграция `38e9b2624a53` (2.64.0) необратимо удаляет данные.** Перед `alembic upgrade head` на
  реальной БД, где уже есть устройства типов `Сетевое оборудование`/`Средство защиты информации`,
  нужно явное подтверждение, что эти устройства и вся их «дочерняя» история (интерфейсы,
  подключения, VLAN-привязки, размещённые ВМ, ПО, связи с ИС) не нужны — восстановить их после
  миграции нельзя, `downgrade()` этой ревизии сознательно поднимает исключение вместо тихого
  отката только схемы. Проверено на тестовых данных (`backend/tests/test_migrations_diagram.py`),
  не на продовой истории миграций конкретного инстанса.
- **Экспорт диаграммы в `.vsdx` (2.64.0) — не точная копия `.svg`/`.drawio`.** Библиотека `vsdx`
  устроена как редактор уже существующего файла, а не конструктор объектной модели с нуля;
  геометрия узла воспроизводится копированием готовой фигуры-прямоугольника из встроенного
  шаблона пакета. Три сознательных упрощения:
  - **нет отдельных фигур-засечек портов** на switch/сервер/файрвол-устройствах (в `.svg`/
    `.drawio` они есть) — при этом связи с 2.79.0 всё равно точно анкерятся в нужную точку
    нижней грани фигуры (находка №2 отчёта об экспорте, Фаза 2 п.1), просто без самой видимой
    отметки-прямоугольника под ней;
  - **иконка категории в `.vsdx` встроена, но не подтверждена визуально** (находка №5, Фаза 3
    п.5, часть 2) — растровая PNG-картинка (через `resvg_py`, см. `_rasterize_glyph_png`)
    встраивается как отдельная фигура-оверлей поверх основной через `ForeignData`/`Rel`,
    XML-разметка сверена дословно с открытой спецификацией MS-VSDX. Но ни headless LibreOffice,
    ни какой-либо другой доступный инструмент проверки саму картинку не показывает — фильтр
    импорта, похоже, просто не поддерживает `ForeignData`/`Bitmap` и молча откатывает фигуру на
    обычную геометрию (небольшой белый прямоугольник на месте иконки, без искажения остальной
    диаграммы — `icon_shape` поэтому явно очищает текст/заливку, чтобы фолбэк был опрятным).
    Доступа к настоящему Microsoft Visio для проверки нет; различение категорий в `.vsdx` и без
    видимой иконки по-прежнему есть по цвету заливки (`shape.fill_color`, находка №1);
  - **размер шрифта не приведён явно к тому же значению, что и `.svg`/`.drawio`** (находка №4,
    Фаза 2 п.4) — семейство шрифта у трёх форматов и так совпадает без единой правки (Calibri —
    единственный шрифт в таблице шрифтов самого шаблона `media.vsdx`, задан явно в `.svg`/
    `.drawio` тем же именем), но КОНКРЕТНЫЙ размер живёт в ShapeSheet-секции `Character`, которой
    у шаблонных фигур нет вовсе, а `vsdx` не даёт API для её создания с нуля (есть только
    точечные сеттеры вроде `text_color`, которые молча ничего не делают, если секции ещё не
    существует) — собирать такую секцию вручную сочтено более рискованным, чем эта конкретная
    правка того стоит.

  Если библиотека получит более высокоуровневый API в будущей версии — стоит пересмотреть
  `backend/app/services/diagram_export.py:export_vsdx`.
- **Пользовательские (загруженные) иконки устройства** (`icon.mode == "custom"`) в `.drawio` и
  `.vsdx` рисуются не поверх всей фигуры узла, как на канвасе, а отдельной плиткой в верхней части
  узла (тёмный фон, иконка вписана с сохранением пропорций) — нижняя полоса высотой
  `CUSTOM_ICON_LABEL_HEIGHT` всегда остаётся под подпись, потому что в `.vsdx` нет способа задать
  цвет текста шаблонной фигуры (см. пункт выше про размер шрифта), а без этого белая подпись поверх
  тёмной custom-иконки в некоторых читателях была бы нечитаема. В `.drawio` плитка — `shape=image`
  с data URI (та же техника, что у глифа категории); в `.vsdx` — растровая PNG-картинка через
  `resvg_py`, с тем же ограничением видимости в headless LibreOffice, что и у иконки категории
  (см. предыдущий пункт). Битая, пустая или слишком большая (>256 КБ) разметка не ломает экспорт
  всей диаграммы — конкретная иконка просто пропускается, а узел остаётся с нейтральной заливкой.

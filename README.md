# РИС — Реестр ИТ-инфраструктуры

[![CI](https://github.com/MrGAVER/IT-Infrastructure-Report/actions/workflows/ci.yml/badge.svg)](https://github.com/MrGAVER/IT-Infrastructure-Report/actions/workflows/ci.yml)

Приложение для учёта информационных систем, физических устройств, сетевой инфраструктуры,
виртуальных машин, контейнеров и программных активов организации с выгрузкой регламентированного
Excel-отчёта из 4 листов (перечень ИС, инвентаризация физических устройств, организация
подключений, организация управления ВМ).

Стек: **FastAPI + SQLAlchemy + Alembic** на бэкенде, **Vue 3 + TypeScript + Vite** — фронтенд
(см. [Фронтенд](#фронтенд)), **SQLite** (локально/EXE) или **PostgreSQL** (Docker/сервер)
в качестве СУБД, выгрузка отчётов через **openpyxl**.

## Возможности

### CRUD по всем сущностям

Единый REST CRUD реализован для всех основных сущностей БД: организации, подразделения, структурные
единицы, здания, помещения, стойки, типы устройств/производители/модели, физические устройства,
информационные системы (и их подразделения, IP, протоколы), интерфейсы и IP интерфейсов, VLAN и
привязки VLAN, физические подключения, среды виртуализации, виртуальные машины и их IP, контейнеры,
программные активы, ПО физических устройств и ВМ, связи ИС с устройствами/ВМ/контейнерами, открытые
порты, журнал аудита.

Для каждой сущности доступен единый набор эндпоинтов:

```text
GET    /api/v1/resources/{resource}
GET    /api/v1/resources/{resource}/{id}
POST   /api/v1/resources/{resource}
PUT    /api/v1/resources/{resource}/{id}
DELETE /api/v1/resources/{resource}/{id}
GET    /api/v1/resources/{resource}/schema
```

Поддерживаются полнотекстовый поиск (`?q=`, не длиннее 200 символов), точная фильтрация по полю (`?field=value`),
`offset`/`limit` (`offset` — не больше 2 147 483 647; значения за пределами и слишком длинный `q` дают 422, а не 500),
проверка уникальности и обработка внешних ключей. Удаление объекта, на который
есть ссылки, блокируется с HTTP 409 и понятным сообщением о том, где именно он используется.

**Одновременная правка записи.** `PUT /api/v1/resources/{resource}/{id}` принимает необязательное поле `expected_updated_at` —
`updated_at` записи из последнего ответа сервера (строка ISO 8601, любое смещение UTC; сравнение с точностью до миллисекунды).
Если запись успели изменить, сервер отвечает HTTP 409 с кодом `STALE_RECORD` и ничего не пишет; строка на время проверки блокируется
(`SELECT … FOR UPDATE` на PostgreSQL), поэтому две одновременные правки не затрут друг друга. Не строка и не дата — 422. Без поля (или с `null`)
поведение прежнее: побеждает последняя запись. Ответ `PUT` несёт новый `updated_at` — его нужно подставлять в форму, иначе вторая правка подряд
получит 409. Формы редактирования устройств, виртуальных машин, контейнеров и информационных систем этот контракт используют: передают `updated_at` записи, с которой
открыты (и обновляют его из ответа после каждой успешной записи), а при 409 `STALE_RECORD` показывают окно с тремя вариантами — «Сохранить мои изменения»
(повтор без проверки: чужая правка будет потеряна), «Загрузить свежие данные» (форма закрывается без сохранения, список обновляется) и «Остаться в форме»
(ничего не сохраняется; Esc и закрытие окна — то же). Остальные формы (здания, помещения, стойки, структурные единицы, VLAN и домены VLAN, справочники, стеки
устройств) токен пока не передают: там по-прежнему побеждает последняя запись.

Токен защищает и вложенные списки записи. Формы сохраняют их отдельными запросами (`PUT …/interfaces`, `…/ip-addresses`, `…/open-ports`, `…/deployed-software`,
`…/vlans`, `…/details` и им подобные), а `updated_at` у родителя меняется только при `UPDATE` его собственной строки, поэтому такой запрос теперь сам сдвигает версию
родителя (устройства, ВМ, контейнера, информационной системы) — но только если что-то действительно изменилось: повторная отправка тех же данных версию не трогает.
Сдвиг не меньше миллисекунды, чтобы сравнение с точностью до миллисекунды всегда замечало правку. Следствия: правка чужого списка портов, IP или ПО при открытой у вас форме даёт
409 `STALE_RECORD` при сохранении, а после сбоя вложенного шага форма перечитывает версию записи (`GET /resources/{resource}/{id}`), и повторное «Сохранить»
не конфликтует с изменениями, которые она успела записать сама. Исключение: правка отдельной вложенной строки через обычные generic-ресурсы (не через эти `PUT`-эндпоинты
списков) версию родителя не двигает — интерфейс использует только `PUT`-эндпоинты списков.

**Инварианты подключений** держит сама БД, а не только проверка в приложении: порт не соединяется сам с собой
(`CHECK ck_connections_distinct_ports`) и участвует не более чем в одном активном подключении в своей роли — источника или назначения
(частичные уникальные индексы `uq_connections_source_active` и `uq_connections_destination_active`). Понятный ответ `409` по-прежнему даёт
`validate_connection`; на PostgreSQL он перед проверкой блокирует строки портов (`SELECT … FOR UPDATE` по возрастанию `id`), поэтому два
одновременных запроса с общим портом не проходят проверку оба. Обмен соседями в форме устройства на время применения плана выключает
переставляемые подключения (`is_active = false`) и включает их снова в той же транзакции. Миграции этих правил — в разделе «Миграции Alembic».

### Структурные единицы

Справочник организационных структурных единиц (филиал, площадка, подразделение и т. п.) с
иерархией через родительскую единицу — тот же паттерн, что и у подразделений. Адрес размещения
физического оборудования (здание) дополнительно связывается со структурной единицей: у каждого
здания есть необязательное поле «Структурная единица», а через него — у всего оборудования,
размещённого в этом здании.

Эта связь используется при формировании отчётов (регламентированного и построенных в конструкторе
на сущностях реестра): отчёт можно ограничить оборудованием одной, нескольких или сразу всех
структурных единиц — выбор родительской единицы автоматически захватывает вложенные, без
необходимости отмечать каждую по отдельности. См. «Отчёт Excel» → «Фильтр по структурным единицам».

### Интерфейс

- Динамические CRUD-формы, построенные по схеме конкретной таблицы: текстовые/числовые/большие
  текстовые поля, Boolean как «Да/Нет», выпадающие списки для внешних ключей.
- Быстрое добавление справочных значений прямо из формы (кнопка «+»), без перехода в раздел
  справочников.
- Отдельные редакторы для сложных сущностей: интерфейсы физического устройства (с генерацией по
  шаблону имени/номера и подинтерфейсами порта — логическими интерфейсами на отдельном VLAN со своим
  IP и открытыми портами, как у маршрутизаторов и межсетевых экранов), VLAN устройства, IP-адреса и открытые порты ВМ, детали информационной
  системы (подразделения, протоколы, источники размещения, оборудование/ПО).
- Единые правила для всех мест, где добавляется открытый порт (TCP/UDP): ВМ, порты физических устройств,
  группы портов и протоколы передачи данных информационной системы. Список упорядочивается по номеру порта,
  но только когда добавляется следующая строка или форма открывается заново (заполняемая строка не «уезжает»
  из-под курсора); строки с одним номером порта подсвечиваются, сохранение с повтором блокируется (в форме и на
  сервере: `422` с номером порта — для ИС и в общем CRUD `/is-protocols` тоже); записи синхронизируются по id, без
  удаления и повторного создания. Уже существующие повторы показывает `GET /api/v1/integrity/open-port-duplicates`
  (ВМ, порты устройств, группы портов, ИС). Логика общая: `utils/openPorts.ts` и `composables/useUniquePortRows.ts`.
- Единый каталог оборудования «Производитель → Тип устройства → Модель».
- Сквозной поиск по нескольким сущностям сразу (устройства, ИС, ВМ, интерфейсы, IP интерфейсов,
  IP ВМ) с резолвингом IP-адреса до владеющего устройства/ВМ.
- Импорт физических устройств из CSV.
- Журнал аудита (read-only раздел): постраничная выборка с сервера — поиск по деталям и id записи, фильтры по
  действию и разделу, счётчики по всему журналу (`GET /api/v1/audit-log?q=&action=&entity_type=&offset=&limit=`);
  доступны все записи, а не только последние. При создании и удалении записи в журнал попадает её описание (имя, серийный номер,
  адрес и т. п. — по виду записи), а не только UUID: по удалённой записи видно, что это было.
  Срок хранения записей настраивается кнопкой «Настройки аудита» (экран «Журнал аудита» и «Настройки», только администратору) — см. «Безопасность по умолчанию».
- Сортировка таблиц списков по клику на заголовок, предупреждение о несохранённых изменениях при
  закрытии форм устройства/ИС и вкладки браузера.
- Разделы вынесены в левое меню тремя группами: «Реестр» (дашборд, информационные системы, устройства и их стеки,
  подключения, диаграмма топологии, виртуальные машины, контейнеры), «Справочники» (VLAN, здания и помещения, структурные
  подразделения, прочие справочники) и «Система» (отчёты и их шаблоны, правила согласования портов, журнал аудита — только
  администратору). Хлебные крошки экранов реестра единые: «Реестр › <экран>».
- Дашборд «Стеки устройств» (с 2.160.0): карточки сводки (стеков, устройств в стеках, пустых стеков, стеков без полного SIEM) и таблица
  стеков с числом устройств, моделью, IP управления, расположением и покрытием SIEM («да» / «нет» / «1 из 2»). Строка раскрывается в состав
  стека (позиция, системное имя, серийный номер, модель, IP, расположение, SIEM) и в блок «Общие VLAN стека» — номер и имя VLAN, адрес с
  префиксом, «Управление» и состояние применения к участникам; VLAN подгружаются лениво, только для раскрытых строк текущей страницы.
  Стек, созданный на экране «Инвентаризация устройств», появляется здесь сразу, без обновления страницы.
- Справочники (с 2.160.0): над таблицей выбранного справочника в «Других справочниках» есть поиск по значениям колонок так, как они показаны
  (для связанных записей — по названию; несколько слов сужают результат, регистр и «ё»/«е» не различаются). В окне «Добавить: Здание» рядом с
  блоком «Структурная единица» есть кнопка «+»: недостающую единицу можно завести, не закрывая окно здания.
- Списки: один набор размеров страницы на весь интерфейс — 10 / 25 / 50 / 100, по умолчанию 10 (прежний выбор вне этой шкалы
  читается как «не выбрано»). Пустой реестр так и пишет («Устройств пока нет.») и при праве записи предлагает создать запись, а когда
  пусты только результаты фильтров — предлагает «Сбросить фильтры». У широких таблиц (журнал аудита, шаблоны отчётов, справочники,
  ВМ, контейнеры) край затухает, подсказывая горизонтальную прокрутку.
- Модальные окна построены на одной основе (`components/BaseModal.vue`): фокус уходит в окно и замкнут в нём (Tab / Shift+Tab), при
  закрытии возвращается на кнопку, открывшую окно; Esc закрывает только верхнее из вложенных окон; страница под окном не
  прокручивается, а меню и основная область недоступны для клавиатуры и вспомогательных технологий (`inert`). Уведомления выводятся
  в живых областях (`role="status"` / `role="alert"`).
- Полнота данных. Формы, которые сохраняют списки целиком (ПО, VLAN, порты и группы устройства, IP-адреса, открытые порты и ПО ВМ),
  не отправляют список, который не загрузился или загружен не полностью: вместо него показывается «загружено n из N» с кнопкой
  «Повторить загрузку», остальные поля формы сохраняются. Иначе сервер удалил бы записи, которых пользователь не видел. Экраны,
  показывающие список целиком (контейнеры, подключения, стеки устройств, VLAN-домены, справочники), держат такое сообщение постоянно, а не
  только всплывающим уведомлением.
- Диаграмма топологии: рёбра идут ортогональными маршрутами в обход узлов (расчёт ограничен по времени — 250 мс и по размеру схемы; если
  часть связей проложена упрощённо, в заголовке экрана появляется подсказка). Файл диаграммы скачивается с настоящим именем, в том
  числе кириллическим. Экспорт в `.svg`, `.drawio` и `.vsdx` строится на сервере и от этой трассировки не зависит.

### Миграции Alembic

`Base.metadata.create_all()` не используется как механизм создания схемы — схема БД создаётся и
обновляется только миграциями:

```bash
cd backend
alembic upgrade head
```

Новая миграция после изменения моделей:

```bash
cd backend
alembic revision --autogenerate -m "описание изменения"
alembic upgrade head
```

Откат последней миграции:

```bash
alembic downgrade -1
```

Проверка, что модели и миграции не разошлись (ту же команду выполняет CI на SQLite и PostgreSQL; ожидаемый ответ —
`No new upgrade operations detected.`):

```bash
cd backend
alembic upgrade head
alembic check
```

Если `alembic check` находит расхождение, нужна миграция (`alembic revision --autogenerate`) или правка модели. На SQLite
ограничения UNIQUE в сравнении не участвуют (SQLite хранит безымянные ограничения без имени), их наличие проверяет тест
`backend/tests/test_migrations_match_models.py`.

В Docker миграция выполняется автоматически перед запуском Uvicorn (для SQLite — после резервной копии, см. «Обновление образа» в разделе
«Docker»), в EXE — автоматически при старте приложения (тоже после копии).

**Перед обновлением рабочей базы до 2.159.0.** Миграции `c4a9e2d7b185` и `e3b7a15c9d42` (инварианты подключений) **останавливаются с
понятной ошибкой, ничего не меняя**, если в данных уже есть нарушения: какое подключение настоящее (это физический кабель), решает человек,
а не миграция. Найти такие строки заранее:

```sql
-- порт, соединённый сам с собой
SELECT id FROM connections WHERE source_interface_id = destination_interface_id;
-- порт, занятый двумя активными подключениями в одной роли (источник; то же для destination_interface_id)
SELECT source_interface_id, COUNT(*), STRING_AGG(id::text, ', ')
  FROM connections WHERE is_active IS NOT FALSE
 GROUP BY source_interface_id HAVING COUNT(*) > 1;
```

(`STRING_AGG(id::text, …)` — синтаксис PostgreSQL; в SQLite — `GROUP_CONCAT(id, ', ')`.) Следующая ревизия `d6c1a8f3e594` создаёт таблицу
`audit_settings` (срок хранения журнала аудита); у всех трёх ревизий `downgrade()` работает. Перед `alembic upgrade head` на PostgreSQL
сделайте копию базы (`docker compose --profile backup run --rm db-backup`; EXE и SQLite в Docker копируют базу сами).

### Правила согласования данных порта

Страница «Правила согласования портов» (раздел «Система») — модуль правил, по которым данные порта (роль,
режим trunk/access, VLAN) согласуются с портом на другом конце активного подключения. Правила хранятся в БД
(таблица `port_sync_rules`), их можно создавать и менять, **в том числе стандартные**: изменить условия, действие,
порядок, отключить; стандартное правило нельзя удалить, но можно вернуть к исходному виду («Сбросить»).

Правило — шаблон над парой «порт ← соседний порт»: условия на каждый порт (роль, режим, состояние VLAN: «не назначены
совсем» / «назначены (в том числе все)» / «назначены все — галочка “Все VLAN”»), отношение между ними («совпадают» /
«различаются»), действие и то, что порт берёт у соседа (роль, режим, VLAN: «не менять» / «взять набор соседа» /
«привести к режиму» — в access остаётся один VLAN с наименьшим номером; «объединить» — оба порта получают объединение
наборов VLAN, ни один VLAN не снимается; политика симметрична, поэтому не сочетается со сменой роли или режима;
«назначить все VLAN своего устройства» — «Все VLAN»: порт получает все VLAN, доступные его устройству, а не номера VLAN
соседа; уже назначенные не снимаются, в access не применяется).
Действие: **Автоматически** (направление
определяют условия; изменения применяются после предпросмотра и подтверждения), **Решает человек** (расхождение
известного вида, какой порт менять — выбирает человек, как и раньше) или **Не трогать** (пару не согласовывать).
Проверка идёт сверху вниз по порядку, решает первое подходящее правило; для каждой пары проверяются обе ориентации,
а автоматическое правило, подходящее обоим портам, уходит на ручное решение (кроме правил с политикой «объединить» —
они меняют оба порта сразу).

Стандартные правила: **«“Все VLAN” на порту — “Все VLAN” у соседа»** (автоматически, проверяется первым: на порту trunk
с «Все VLAN», а соседний порт тоже trunk, но «Все VLAN» у него нет — соседу назначаются все VLAN его устройства; если у
устройств разные наборы VLAN, наборы на концах линии могут остаться разными — план предупреждает об этом и помечает
подключение «расхождение останется»; на существующих установках правило добавляется при старте приложения без
миграции), **«“Все VLAN” на обоих портах — не трогать»** («Не трогать», приоритет 6: на обоих портах trunk с «Все VLAN», роли
совпадают, а номера VLAN различаются, потому что у устройств разные наборы VLAN, — пара не согласовывается и показывается в
плане как «Исключено правилом», а не «Нельзя применить»; расхождение на дашборде остаётся, его можно одобрить; при разных
ролях правило не срабатывает), «Пустой trunk получает VLAN соседа» (автоматически: на порту trunk совсем без VLAN, а на соседнем
trunk с VLAN или с «Все VLAN» — порту применяется trunk с VLAN соседа), **«Trunk: наборы VLAN на концах линии
объединяются»** (автоматически: на обоих концах trunk с наборами VLAN, и наборы различаются — оба порта получают
объединение номеров VLAN; ни один VLAN не снимается, поэтому правило безопасно; VLAN, которых нет у устройства порта,
пропускаются с предупреждением — расхождение на таком подключении может остаться, его решает человек) и три правила
«решает человек», повторяющие сверку дашборда: «Роль порта совпадает с ролью соседа», «Режим порта совпадает с режимом соседа», «Наборы VLAN на
концах линии совпадают».

Где применяется: кнопка «Согласовать по правилам…» на дашборде «Подключения» (все активные подключения с неодобренным
расхождением), блок «По правилам согласования» в окне проверки расхождения (одно подключение) и «Что сделает» на
странице правил (только это правило, даже отключённое). Ещё одно место — уведомление после сохранения устройства, в котором изменился список VLAN: порты в состоянии «Все VLAN» подхватывают новый VLAN сами, а согласование с соседями идёт только вручную, поэтому форма (после закрытия) проверяет подключения этого устройства предпросмотром плана и, если есть что согласовать, показывает предупреждение с кнопкой «Показать план» (автоматически ничего не применяется; «исключено правилом» и «расхождения нет» в счёт не идут; у устройства больше 500 подключений — общее напоминание без подсчёта). Везде сначала показывается **план** — что изменится, что
нельзя применить и почему, что остаётся за человеком; изменения записываются только после отметки «Я проверил план»
и одной транзакцией. VLAN переносятся по номеру в записи, доступные устройству целевого порта; номера, которых у
устройства нет, пропускаются с предупреждением. Не меняются порты группы, задающей режим и VLAN, и результат с
несколькими VLAN в access. Если правило меняет оба порта, план показывает изменения каждого порта отдельно, а порт,
который изменить нельзя, не мешает второму. Подключения, у которых расхождение после применения останется (часть VLAN
пропущена — нет у устройства, или один из двух портов не меняется), помечаются в плане, а в сводке называется их число
(«расхождение останется у: N», `summary.partial` по всему плану). Применение пишет порты пакетно: на 6000 портов (3000
подключений) — около 2–4 с вместо ~10 с, число запросов к БД от числа портов не зависит. Согласование не срабатывает само при сохранении данных — только по запросу
пользователя. Новое стандартное правило добавляется в существующую установку при ближайшем запуске приложения (по коду
правила; изменённые администратором правила не перезаписываются), миграция БД не нужна.

Элементы плана показываются **страницами** (до 300 за раз, кнопка «Показать ещё»), а сводка и `plan_hash` относятся ко
всему плану: применяется весь план, а не показанная часть. Первая страница считает план и кладёт его в серверный кэш
(ключ — условия плана и `plan_hash`; живёт 5 минут, не более 4 планов в памяти процесса); следующие страницы
запрашиваются с `plan_hash` первой и берутся срезом из кэша без запросов к БД. Применение кэш не читает — всегда
считает план заново. Кэш сбрасывается после применения и после любой правки правил; если он уже пуст (срок вышел,
другой воркер) и план изменился, страница отвечает 409 — предпросмотр нужно начать заново.

API (`/api/v1/port-sync`): `GET|POST /rules`, `PUT|DELETE /rules/{id}`, `POST /rules/{id}/reset`,
`POST /rules/reorder`, `POST /preview` (`{connection_ids?, rule_id?, offset?, limit?, plan_hash?}` → страница плана,
`summary` и `plan_hash` по всему плану, `page: {offset, limit, total, has_more}`; ничего не пишет), `POST /apply`
(`{connection_ids?, rule_id?, plan_hash, confirm: true}`; при изменении данных после предпросмотра — 409).

### Проверки согласованности данных

`GET /api/v1/integrity/consistency` ищет в реестре противоречия между записями (`category=consistency`) и пробелы, из-за которых
лист отчёта будет неполным (`category=completeness`, поле `sheet` — номер листа 1–4). Только чтение: ничего не исправляется, решает
человек. Фильтры: `rule` (коды правил), `category`, `severity` (`error`/`warning`/`info`), `sheet`; страницы — `limit`/`offset`.
`summary` (по важности, категории, листу и правилу) считается по всему выбору, `total` — число находок до разбиения на страницы.
Каталог правил с названиями — `GET /api/v1/integrity/consistency/rules`.

**Одобрение проблем.** Находку можно признать допустимой (например, общий адрес VRRP): `POST /api/v1/integrity/consistency/approvals`
(`fingerprint` из отчёта и необязательный `comment`) и `DELETE /api/v1/integrity/consistency/approvals/{id}` (отзыв). У каждой находки в отчёте есть
`fingerprint`, `approved` и `approval` (кто, когда и зачем одобрил); отбор — параметр `approval` (`active` — требуют внимания, `approved`, `all`);
`summary.by_approval` показывает оба числа при любом отборе, а `ok` — что в выборке нет находок, требующих внимания. Одобрение привязано к отпечатку
проблемы и теряет силу, когда она меняется (у адреса появился ещё один владелец, не хватает другого поля), но не от переименования устройства. Одобрить
можно только проблему, которая есть сейчас (иначе 404), повторное одобрение ничего не меняет. Одобрение и отзыв пишутся в журнал аудита (раздел
«Одобрения проверки данных»); как и остальные записи, доступны только ролям с правом изменения.

В веб-интерфейсе — экран «Система → Проверка данных» (`/consistency`): счётчики (требуют внимания, по важности, одобрено), фильтры (поиск, категория,
лист отчёта, правило, важность, одобрение), таблица находок и постраничный вывод. Все находки читаются одним запросом, фильтры работают на клиенте.
Пишущему пользователю доступны «Одобрить» (окно с необязательным комментарием) и «Отозвать одобрение»; нажатие на имя объекта в находке открывает окно
его редактирования (устройство, ВМ, контейнер, ИС; у находок про повтор адреса или имени — окна объектов-владельцев), а после сохранения проверка
запускается заново. Наблюдателю имя объекта ведёт в раздел. Сами данные проверка не меняет.

- **Противоречия:** некорректная запись IP (например, с маской в адресе); один IP у разных объектов (порты одного устройства и
  участники одного стека — один узел; адреса «ручных» источников ИС не сравниваются); одно системное имя у устройств не из одного
  стека; помещение в другом здании или стойка в другом помещении, чем указано у устройства; криптозащита ИС отмечена без средства
  (и наоборот); внешнее взаимодействие ИС без криптозащиты.
- **Полнота по листам:** лист 1 — размещение, описание, поддержка, протоколы ИС; лист 2 — здание и помещение, производитель, модель
  и ОС, IP управления у управляемого устройства (у стека достаточно адреса одного участника); лист 4 — хост, ОС, назначение и IP
  виртуальной машины, место контейнера.

Правила — функции в `backend/app/services/consistency/rules_*.py`, регистрируются декоратором `@rule(...)`; число запросов к БД не
зависит от числа строк (проверяется тестом). Модель и внешние сервисы не используются: проверки детерминированные.

### Аутентификация и авторизация

По умолчанию выключена (`AuthSettings.enabled = False`) — однопользовательский локальный режим,
`/api/*` открыт без токена, поведение не отличается от версий до 2.61.0. Включается на экране
«Настройки» (нужен хотя бы один пользователь с ролью «Администратор» — завести его можно, пока
переключатель ещё выключен). Две роли: `admin` (полный доступ, управление пользователями и самим
переключателем) и `viewer` (только чтение данных; формировать и скачивать отчёты — инвентаризацию,
предпросмотр и «Сформировать» по шаблону, «Приложение к структурной схеме», предпросмотр согласования портов — viewer может, это не изменяет реестр; **журнал аудита** — раздел и отчёт — только `admin`: в нём имена пользователей, IP-адреса и неудачные попытки входа; при выключенной аутентификации журнал открыт). Пароли — `pbkdf2_hmac(sha256)`, токены сессий —
непрозрачные (в БД хранится только их sha256-хеш), блокировка учётной записи после серии неудачных
попыток входа и троттлинг входа с растущей задержкой (см. 2.110.0): по паре «IP + логин» и, отдельно, по адресу целиком — после 20 неудачных
попыток с одного адреса (с любыми логинами) ответ `429` с `Retry-After`, задержка растёт вдвое до 5 минут и затухает через 15 минут без неудач;
удачный вход счётчик адреса не сбрасывает. Проверка пароля на входе (PBKDF2) идёт не более чем в четыре потока одновременно: пятому
параллельному запросу сервер отвечает `503` с `Retry-After: 2`, чтобы поток подбора не занял весь пул обработчиков и API не перестал
отвечать; такой отказ не считается неудачной попыткой. Длина пароля — не больше 256 символов. **Блокировка и «знакомые» адреса.** После `INFRA_REGISTRY_AUTH_MAX_ATTEMPTS` (10) неверных паролей учётная запись блокируется на
`INFRA_REGISTRY_AUTH_LOCKOUT_MINUTES` (15) минут, но блокировка отклоняет вход (423 `ACCOUNT_LOCKED`) только с **незнакомых** адресов:
адрес, с которого этот пользователь уже входил успешно за последние `INFRA_REGISTRY_AUTH_KNOWN_CLIENT_DAYS` (30) дней, проходит
проверку пароля (верный пароль снимает блокировку), а подбор с него по-прежнему увеличивает счётчик и ограничивается
троттлингом входа. Без этого любой, кто достаёт до `/login`, мог бы держать администратора заблокированным постоянно. Адреса берутся
из записей `LOGIN` журнала аудита. За обратным прокси задайте `FORWARDED_ALLOW_IPS`, иначе у всех клиентов будет адрес прокси и
«знакомым» окажется любой. Сервер распознаёт такой случай по заголовкам `X-Forwarded-For`, `Forwarded` и `X-Real-IP`, пришедшим с адреса,
которому uvicorn не доверяет: исключение «знакомый адрес» для таких запросов **не применяется** (блокировка действует как для
незнакомого адреса), а в журнал один раз за запуск пишется предупреждение — см. «Безопасность по умолчанию». Прокси, который не шлёт никаких
заголовков, и клиентов за общим NAT сервер распознать не может: в таких развёртываниях задайте
`INFRA_REGISTRY_AUTH_LOCKOUT_KNOWN_CLIENT_BYPASS=0` — блокировка будет действовать для всех адресов, как раньше.
Любая роль может сменить свой собственный пароль (неверный текущий пароль — HTTP 422 с кодом
`WRONG_CURRENT_PASSWORD`, а не 401; такая попытка засчитывается как неудачный вход: счётчик блокировки, запись `LOGIN_FAILED`
в журнале аудита, а у заблокированной учётной записи пароль не проверяется — ответ 423) и посмотреть/завершить свои же
активные сессии (раздел «Моя учётная запись», см. 2.62.0), не дожидаясь администратора. Все
проверки, критичные для «не остаться без единого администратора» и учёт неудачных попыток входа,
устойчивы к нескольким одновременно пишущим процессам backend за общей БД — актуально для
серверного варианта (см. 2.63.0). Подробности реализации — в записях
[2.61.0](#история-изменений)/[2.62.0](#история-изменений)/[2.63.0](#история-изменений) истории
изменений.

## Быстрый старт

### Docker

Перед первым запуском скопируйте `.env.example` в `.env` и задайте свой `POSTGRES_PASSWORD` и
`INFRA_REGISTRY_SETUP_TOKEN` (без них `docker compose` откажется стартовать; токен — длинная случайная строка,
например `openssl rand -hex 24`):

```bash
cp .env.example .env
# отредактируйте .env
docker compose up --build
```

Данные хранятся в двух томах Docker: `pgdata` — база PostgreSQL, `appdata` (`/app/data` в контейнере приложения) —
сформированные отчёты (и база, если `DATABASE_URL` указывает на SQLite). Оба переживают пересоздание контейнеров
(`docker compose up --build`, `down`); `docker compose down -v` удаляет их. Процесс приложения работает от
непривилегированного пользователя `app` и может писать только в `/app/data`: код в образе доступен ему лишь для чтения.
`docker stop` завершает приложение штатно (uvicorn — PID 1 контейнера и получает SIGTERM).

Если значения остались заглушками из `.env.example` (`change_me…`) или слишком короткими (токен — меньше 16 символов, пароль БД —
меньше 8), приложение запустится, но при каждом старте напишет предупреждение в журнал; сами значения в журнал не попадают.
Слабый **токен установки** при этом ещё и **не принимается**: сервер считает его незаданным, а в Docker прямого `localhost` нет, поэтому
включить аутентификацию с заглушкой не получится — ответ `403 SETUP_ACCESS_DENIED` назовёт причину. Замените токен
(`openssl rand -hex 24`) и перезапустите контейнер. Пароль БД только предупреждает: порт БД наружу не публикуется.

Переменные окружения `.env` (все опциональны, кроме `POSTGRES_PASSWORD` и `INFRA_REGISTRY_SETUP_TOKEN`). В Docker приложению доходят
только переменные, перечисленные в `docker-compose.yml` (раздел `app.environment`); значение из `.env` подхватывается после
`docker compose up -d` (контейнер пересоздаётся). Тест `backend/tests/test_compose_env_passthrough.py` следит, чтобы каждая настройка,
описанная в `.env.example`, была и в compose:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `POSTGRES_PASSWORD` | — (обязательна) | пароль пользователя БД; допустимы любые символы (при `#`, `$` или пробеле возьмите значение в одинарные кавычки) |
| `POSTGRES_DB` / `POSTGRES_USER` | `infra_registry` / `infra` | имя БД и пользователя |
| `DATABASE_URL` | пусто | готовый адрес БД (внешний сервер, нестандартные параметры); имеет приоритет над `POSTGRES_*`, пароль в нём нужно экранировать самому (`@` → `%40`). Без него адрес собирается из `POSTGRES_*` и `INFRA_REGISTRY_DB_HOST` (в compose — `db`), с экранированием |
| `INFRA_REGISTRY_CORS_ORIGINS` | пусто (CORS выключен) | список разрешённых origin'ов через запятую; нужен только для отдельного фронтенда. Такие origin'ы также могут отправлять запросы, меняющие данные (см. «Защита от межсайтовых запросов») |
| `INFRA_REGISTRY_ALLOWED_HOSTS` | `localhost,127.0.0.1` | допустимые **имена** в заголовке `Host` (защита от DNS-rebinding); если сервер открывают по имени, перечислите его вместе с локальными. `*` отключает проверку целиком — при выключенной аутентификации не используйте (при старте пишется предупреждение) |
| `INFRA_REGISTRY_ACCEPT_IP_HOSTS` | `true` в compose, `false` без него | принимать `Host` в виде IP-адреса (`http://10.0.0.5:8000`) без перечисления: подменить IP-адрес через DNS нельзя. Имена по-прежнему проверяются по `INFRA_REGISTRY_ALLOWED_HOSTS` |
| `INFRA_REGISTRY_ALLOWED_CLIENTS` | пусто (без ограничений) | IP-адреса и подсети клиентов через запятую (`192.168.1.15,10.0.5.0/24`); остальные получают `403`. EXE задаёт его сам из `infra_registry.toml`. В Docker приложение видит тот адрес клиента, который ему передал Docker или прокси (см. `FORWARDED_ALLOW_IPS` и примечание ниже таблицы) |
| `INFRA_REGISTRY_SETUP_TOKEN` | — (обязателен в compose) | токен первичной настройки аутентификации (заголовок `X-Setup-Token`); `docker compose` не стартует без него. Заглушка из `.env.example` и значение короче 16 символов не принимаются (считаются незаданным токеном) |
| `INFRA_REGISTRY_BIND` | `127.0.0.1` | адрес, на котором compose публикует порт `8000`; `0.0.0.0` — доступ по сети (сначала включите аутентификацию) |
| `FORWARDED_ALLOW_IPS` | `127.0.0.1` | адреса обратных прокси, которым uvicorn доверяет при определении IP клиента; если указан не loopback-адрес (или `*`), для проверки origin учитывается и `X-Forwarded-Host`. **За прокси обязательна** (иначе у всех клиентов адрес прокси); при `X-Forwarded-For`, `Forwarded` или `X-Real-IP` от адреса вне списка сервер один раз пишет предупреждение в журнал, а исключение «знакомый адрес» из блокировки учётной записи для такого запроса не действует |
| `INFRA_REGISTRY_CSP` | строгая политика по умолчанию | `Content-Security-Policy` ответов; пустое значение отключает заголовок |
| `INFRA_REGISTRY_REPORT_RETENTION_DAYS` | `30` | через сколько дней удаляются сформированные отчёты (очистка при формировании нового); `0` — не удалять по возрасту |
| `INFRA_REGISTRY_REPORT_MAX_FILES` | `200` | сколько файлов отчётов (.xlsx/.docx) остаётся в каталоге: при формировании нового самые старые сверх лимита удаляются независимо от возраста (отчёт может сформировать роль viewer, без квоты цикл запросов заполнил бы диск); `0` — без ограничения по количеству |
| `INFRA_REGISTRY_AUDIT_RETENTION_DAYS` | `0` (не удалять) | через сколько дней удаляются записи журнала аудита (не больше `3650`, иначе ошибка запуска с именем переменной); `0` — хранить без ограничения. Значение по умолчанию: срок, сохранённый администратором в форме «Настройки аудита», важнее переменной |
| `INFRA_REGISTRY_MAX_REQUEST_BODY_BYTES` | `2097152` (2 МБ) | наибольший размер тела запроса к API, байт: запрос больше получает `413 REQUEST_BODY_TOO_LARGE` и не разбирается (без предела тело любого размера читалось бы в память целиком). Все тела — JSON, обычные запросы занимают единицы килобайт, самый тяжёлый легитимный (SVG-иконка; длиннее 256 К символов её всё равно пропускает экспорт диаграммы) укладывается с запасом; поднимайте значение, только если реальный сценарий упирается в предел. `0` — без проверки (защита тогда нужна на обратном прокси) |
| `INFRA_REGISTRY_SESSION_TTL_HOURS` | `12` | срок жизни сессии, часов (при включённой аутентификации). Не продлевается активностью; у одного пользователя не более 20 действующих сессий — при входе сверх предела удаляются самые старые его сессии |
| `INFRA_REGISTRY_AUTH_MAX_ATTEMPTS` / `INFRA_REGISTRY_AUTH_LOCKOUT_MINUTES` | `10` / `15` | сколько неверных паролей подряд блокируют учётную запись и на сколько минут (подробнее — раздел об аутентификации выше) |
| `INFRA_REGISTRY_AUTH_MIN_PASSWORD_LENGTH` | `8` | наименьшая длина пароля (проверки «буквы и цифры» и «не совпадает с именем» остаются) |
| `INFRA_REGISTRY_AUTH_KNOWN_CLIENT_DAYS` / `INFRA_REGISTRY_AUTH_LOCKOUT_KNOWN_CLIENT_BYPASS` | `30` / `1` | за сколько дней адрес считается «знакомым» и включено ли это исключение из блокировки (`0` — блокировать все адреса) |
| `INFRA_REGISTRY_DB_POOL_SIZE` / `INFRA_REGISTRY_DB_MAX_OVERFLOW` / `INFRA_REGISTRY_DB_POOL_TIMEOUT` | не заданы (значения SQLAlchemy: `5` / `10` / `30` с) | размер пула соединений PostgreSQL и время ожидания соединения; поднимайте при многих одновременных пользователях (не выше `max_connections` сервера БД). Для SQLite не применяются |

**Числовые настройки.** Пустое значение (`VAR=` в `.env`) означает «по умолчанию»; нечисловое значение или значение ниже границы
останавливает запуск с сообщением, где названа переменная. Границы: `INFRA_REGISTRY_AUTH_MAX_ATTEMPTS` и
`INFRA_REGISTRY_AUTH_MIN_PASSWORD_LENGTH`, `INFRA_REGISTRY_BACKUP_KEEP` — не меньше 1; `INFRA_REGISTRY_DB_PORT` — от 1 до 65535; `INFRA_REGISTRY_BACKUP_INTERVAL_HOURS` — не меньше 0; `INFRA_REGISTRY_MAX_REQUEST_BODY_BYTES`, `…_SESSION_TTL_HOURS`,
`…_AUTH_LOCKOUT_MINUTES`, `…_AUTH_KNOWN_CLIENT_DAYS` — не меньше 0; у `INFRA_REGISTRY_REPORT_RETENTION_DAYS` границы нет (`0` и меньше —
«не удалять»).

**Список клиентов в Docker (`INFRA_REGISTRY_ALLOWED_CLIENTS`).** Приложение сверяет со списком тот адрес клиента, который ему
передали Docker или обратный прокси. За прокси без `FORWARDED_ALLOW_IPS` у всех клиентов будет адрес самого прокси — список тогда либо
пропустит всех, либо не пропустит никого. Адрес, который приложение видит при обращении с самого хоста, зависит от режима сети Docker
(на Docker Desktop для Windows/macOS это может быть адрес шлюза сети Docker, а не `127.0.0.1`), поэтому **перед включением ограничения**
выясните, с какого адреса приходят ваши запросы (при включённой аутентификации его хранит запись входа в журнале аудита), и добавьте
его в список — иначе вы заблокируете сами себя. Раньше значение этой переменной из `.env` в контейнер не доходило и ограничение не
действовало; после обновления оно начнёт действовать, если переменная в `.env` уже задана.

**Обновление образа (Docker).** Контейнер `app` при каждом старте выполняет `alembic upgrade head`, а часть миграций необратима
(удаляет данные; у 9 из них `downgrade` запрещён намеренно), поэтому **откатить образ на прежнюю версию после миграции нельзя — только
восстановить базу из копии**. Порядок обновления:

1. Сделайте копию базы.
   - **PostgreSQL (compose по умолчанию).** Приложение копию не делает — её делает отдельный одноразовый сервис `db-backup`
     (профиль `backup`, он не стартует вместе с остальными): `docker compose --profile backup run --rm db-backup`. Файл формата
     `pg_dump -Fc` — `<имя БД>.<дата-время>.dump` — ложится в том `appdata` (каталог `/app/data/db-backups`), хранятся пять последних.
     Скопировать на хост: `docker compose cp app:/app/data/db-backups/<файл>.dump .`. Для внешнего сервера (`DATABASE_URL`) выполните
     `pg_dump -Fc` с него: `db-backup` подключается только к сервису `db` из compose.
     Плановые копии (см. «[Периодические резервные копии](#периодические-резервные-копии)») эту копию не заменяют: последняя из них
     могла быть сделана за сутки до обновления.
   - **SQLite (`DATABASE_URL` указывает на файл в `/app/data`).** Копию делает сам образ: перед миграцией базы, созданной предыдущей версией,
     `docker-entrypoint.sh` создаёт согласованную копию `<имя базы>.pre-<версия схемы>.<дата-время>.bak` рядом с базой (том `appdata`;
     хранятся пять последних, чужие `.bak` не затрагиваются). Если копию сделать не удалось (нет места, нет прав), контейнер не
     стартует, а база остаётся прежней. Отключить копирование (на свой риск) можно переменной `INFRA_REGISTRY_SKIP_BACKUP=1`,
     добавленной в `app.environment` через `docker-compose.override.yml`.
2. Обновите образ: `docker compose up -d --build` (или `docker compose pull && docker compose up -d`).
3. Если миграция не прошла — верните прежнюю версию образа и восстановите базу из копии.

Восстановление PostgreSQL (приложение остановите: `docker compose stop app`):

```bash
docker compose --profile backup run --rm --entrypoint sh db-backup -c 'pg_restore --clean --if-exists --no-owner --dbname="$PGDATABASE" /backup/db-backups/<файл>.dump'
```

Восстановление SQLite: остановите контейнер и скопируйте нужный `.bak` под именем базы (`infra_registry.db`) в том `appdata`.

Том `pgdata` не заменяет копию: он защищает только от перезапуска контейнера, но не от ошибочной миграции.

**Один экземпляр приложения.** РИС рассчитан на **один** контейнер `app` (один процесс uvicorn) на базу: миграции применяются при старте
контейнера, и две одновременно стартующие реплики запустят `alembic upgrade head` наперегонки. Не масштабируйте сервис
(`docker compose up --scale app=N`) и не подключайте второй экземпляр к той же базе.

### Периодические резервные копии

Копия перед обновлением защищает только от неудачной миграции. От порчи файла базы, ошибочного массового удаления, сбоя диска или
шифровальщика между обновлениями защищают **плановые** копии: по времени, в отдельный каталог, со своей ротацией.

| СУБД | Копия перед обновлением | Плановая копия |
| --- | --- | --- |
| PostgreSQL (compose) | вручную: сервис `db-backup` (см. «Обновление образа») | сервис `db-backup-scheduled` (ниже) |
| SQLite (EXE и Docker) | автоматически: `.bak` рядом с базой, только когда меняется схема | приложение само: файлы `*.auto.*.bak` в каталоге `backups` (ниже) |

**PostgreSQL: сервис `db-backup-scheduled`.** Профиль `backup-schedule`, вместе с остальными сервисами не стартует. Запустить один раз —
дальше он поднимается вместе с Docker (`restart: unless-stopped`):

```bash
docker compose --profile backup-schedule up -d db-backup-scheduled
```

Первая копия делается сразу при старте сервиса, затем — через каждые `BACKUP_INTERVAL_SECONDS`. Дамп (`pg_dump -Fc`, файл
`<имя БД>.<дата-время>.dump`) пишется в каталог **хоста**, а не в том Docker: потеря тома или диска Docker не должна уничтожать и базу,
и копии. Дамп публикуется под своим именем только после проверки `pg_restore --list`; хранятся `BACKUP_KEEP` последних, остальные
`*.dump` удаляются, посторонние файлы в каталоге не трогаются. Права на дамп — только у владельца (`umask 077`).

Параметры (в `.env`, см. `.env.example`):

| Переменная | По умолчанию | Смысл |
| --- | --- | --- |
| `BACKUP_HOST_DIR` | `./backups` (рядом с `docker-compose.yml`, в `.gitignore`) | каталог хоста для дампов; лучше другой диск или сетевая папка |
| `BACKUP_INTERVAL_SECONDS` | `86400` (раз в сутки) | интервал между копиями, целое число секунд больше нуля |
| `BACKUP_KEEP` | `14` | сколько последних копий хранить, целое число больше нуля |

Неверное значение параметра останавливает сервис с сообщением в логе (код выхода 64), а не запускает бесконечный цикл копий.

*Контроль.* `docker compose ps` показывает `healthy`, пока свежая копия моложе двух интервалов, и `unhealthy`, если копий нет дольше.
В `docker compose logs db-backup-scheduled` — строки «Резервная копия: …» или «ОШИБКА резервного копирования» с причиной от `pg_dump`.
Сам по себе `unhealthy` никого не оповещает: подключите наблюдение за контейнерами или за свежестью файлов в каталоге копий.

*Восстановление из плановой копии* (приложение остановите: `docker compose stop app`):

```bash
docker compose --profile backup-schedule run --rm --entrypoint sh db-backup-scheduled -c 'pg_restore --clean --if-exists --no-owner --dbname="$PGDATABASE" /backup/<файл>.dump'
```

`--clean` удаляет и пересоздаёт только объекты, которые есть в дампе: таблицы, появившиеся после копии, останутся. Для полностью
чистого восстановления сначала пересоздайте пустую базу. Сервис работает только с `db` из этого compose-файла; для внешнего
PostgreSQL (`DATABASE_URL`) используйте средства поставщика или `pg_dump -Fc` по расписанию на хосте.

**SQLite.** Плановые копии делает само приложение, пока оно запущено: при старте (если копий нет или последняя старше интервала) и
затем раз в 24 часа; хранятся 7 последних, каждая проверяется `PRAGMA quick_check`. Параметры, каталог, восстановление и настройка из
интерфейса («Настройки → Резервные копии») описаны в разделе «Запуск как EXE (Windows)», абзац «Плановые резервные копии (SQLite…)».
В Docker с SQLite (`DATABASE_URL` на SQLite) параметры задаются в `.env`: `INFRA_REGISTRY_BACKUP_INTERVAL_HOURS`,
`INFRA_REGISTRY_BACKUP_KEEP`, `INFRA_REGISTRY_BACKUP_DIR` (compose передаёт их в контейнер `app`; пусто — умолчания). По умолчанию
каталог копий лежит внутри тома `appdata` — на том же диске, что и база; чтобы копии пережили потерю диска, смонтируйте в `app`
каталог другого диска или сетевой папки и укажите путь к нему в `INFRA_REGISTRY_BACKUP_DIR`.

**Общие требования к копиям**

- Храните копии вне основного диска: другой диск, сетевая папка, другой хост; в идеале одна копия — за пределами площадки.
- В копиях лежат хеши паролей и журнал аудита: доступ только у администраторов, при выносе за пределы организации — шифрование.
- Проверяйте восстановление, а не только создание копии: например, раз в квартал разворачивайте последнюю копию на тестовом стенде и
  проверяйте вход и данные. `pg_restore --list` подтверждает лишь, что архив читается.
- Отсутствие свежей копии — инцидент: настройте оповещение, а не просматривайте логи «когда-нибудь».

### Безопасность по умолчанию

**Docker.** По умолчанию compose публикует порт только на `127.0.0.1`, а `INFRA_REGISTRY_SETUP_TOKEN` обязателен.
Выключенная аутентификация оставляет реестр (IP-адреса, VLAN, ПО, топологию) открытым на чтение и запись всем, кто
достаёт до порта, а из контейнера включить защиту без токена нельзя: адрес клиента — шлюз Docker, не `localhost`.
Порядок для сервера:

1. Задайте `INFRA_REGISTRY_SETUP_TOKEN` в `.env` и запустите `docker compose up --build`.
2. Откройте `http://localhost:8000` на этом же компьютере (или по SSH-туннелю): «Настройки → Аутентификация», введите
   токен, создайте администратора и включите вход.
3. Только теперь, если нужен доступ по сети, добавьте в `.env` `INFRA_REGISTRY_BIND=0.0.0.0`, затем `docker compose up -d`.
   По IP-адресу сервера (`http://10.0.0.5:8000`) приложение открывается без дополнительной настройки. Если его открывают
   **по имени** (`http://reestr.corp.local:8000`), перечислите имя в `INFRA_REGISTRY_ALLOWED_HOSTS`
   (`localhost,127.0.0.1,reestr.corp.local`), иначе сервер ответит `400 Invalid host header`.

Аутентификация по-прежнему **выключена** — реестр открыт без входа, как и раньше. Но выключенная
аутентификация больше не позволяет постороннему захватить приложение:

- **Первичная настройка** (создание пользователей и включение аутентификации) при выключенной
  аутентификации доступна только с `localhost` (прямое соединение, без заголовков прокси) либо — если
  задан `INFRA_REGISTRY_SETUP_TOKEN` (не заглушка и не короче 16 символов) — по заголовку `X-Setup-Token`. Интерфейс сам просит токен в
  «Настройки → Аутентификация», когда сервер отвечает 403 `SETUP_ACCESS_DENIED`. За обратным прокси или в
  Docker задайте токен.
- **CORS выключен**, а заголовок `Host` проверяется: чужая веб-страница в браузере владельца не может ни
  читать, ни менять данные локального приложения. Отдельному фронтенду разрешите origin явно. Проверка Host
  включена и в Docker: прежнее умолчание compose `INFRA_REGISTRY_ALLOWED_HOSTS=*` отключало её, и страница
  злоумышленника через DNS-rebinding (Host и Origin совпадают) могла читать и менять реестр. Если вы задавали `*`
  осознанно, а аутентификация выключена, при старте в журнале появится предупреждение.
- **Защита от межсайтовых запросов (CSRF).** CORS не мешает браузеру *отправить* «простой» POST без тела, поэтому при
  выключенной аутентификации вредоносная страница могла вслепую запустить `POST /api/v1/seed`, дублирование диаграмм,
  формирование отчётов или синхронизацию VLAN. Теперь запросы `POST`/`PUT`/`PATCH`/`DELETE` к `/api/` с чужим `Origin`
  (не совпадающим с `Host`, включая `null`) или с `Sec-Fetch-Site: cross-site` получают `403` с кодом
  `CROSS_ORIGIN_BLOCKED` до выполнения; проверка включена всегда, при любой настройке аутентификации. Не затрагиваются:
  запросы без `Origin` (curl, скрипты, Power Query), безопасные методы (`GET`, `HEAD`, `OPTIONS`) и работа интерфейса со
  своего адреса. Исключения: origin'ы из `INFRA_REGISTRY_CORS_ORIGINS` (запись `*` разрешает любой origin — защита тогда
  не работает, как и CORS); за обратным прокси, который подменяет `Host`, добавьте его внешний адрес в
  `INFRA_REGISTRY_CORS_ORIGINS` либо передавайте исходный `Host` (`proxy_set_header Host $host;` в nginx). Если в
  `FORWARDED_ALLOW_IPS` перечислены адреса прокси не из loopback, учитывается и первый адрес из `X-Forwarded-Host`.
  Отклонённый origin один раз записывается в журнал сервера с подсказкой. **Разработка:** прокси Vite (`npm run dev`,
  `changeOrigin: true`) заменяет `Host`, а браузер шлёт `Origin: http://localhost:5173` — перечислите его в
  `INFRA_REGISTRY_CORS_ORIGINS=http://localhost:5173`, иначе запись отвечает `403 CROSS_ORIGIN_BLOCKED`.
- **Журнал аудита** хранит автора действия: имя пользователя (если аутентификация включена) и IP-адрес.
  **Срок хранения.** По умолчанию журнал не очищается (запись делается на каждое изменение и на каждый неудачный вход, поэтому он растёт
  постоянно: ориентируйтесь на объём своей базы). Администратор задаёт
  срок в форме «Настройки аудита» (кнопка на экранах «Журнал аудита» и «Настройки»; `GET`/`PUT /api/v1/audit-log/settings`, у роли viewer
  доступа нет): `0` — не удалять, `null` — вернуться к значению `INFRA_REGISTRY_AUDIT_RETENTION_DAYS`, наибольший срок — 3650 дней. Записи
  строго старше срока удаляются пакетами по 1000 строк (до 100 000 за запуск), не чаще раза в сутки; запуск — при старте сервера и при
  открытии журнала (отдельного планировщика нет), а сохранение формы очищает журнал сразу. `GET /api/v1/audit-log` сам ничего не удаляет:
  очистка идёт фоновой задачей после ответа, в своей сессии, поэтому страница журнала не ждёт её (первая страница после смены срока ещё
  показывает неочищенные записи, очистка видна со следующего открытия). Запуск «занимается» одним атомарным `UPDATE`: при нескольких
  одновременных запросах или воркерах очищает один. Не получилось очистить (сбой БД) — отметка возвращается и очистка повторится при ближайшем
  запуске. О каждой очистке и о смене срока остаётся запись в самом журнале (раздел «Настройки аудита»): сколько строк удалено, до какой границы
  и в каком файле лежит их копия.
  **Архив удаляемых записей.** Очистка не стирает журнал бесследно: перед удалением каждого пакета его строки записываются в файл
  `reports/audit/Архив_журнала_аудита_<дата-время UTC>Z.csv` (один файл на один проход, создаётся только если есть что удалять) и сбрасываются
  на диск. Не удалось сохранить архив (диск полон, нет прав на каталог) — записи не удаляются, форма сообщает «очистка не удалась», срок
  сохраняется, следующий запуск повторит попытку; причина — в журнале приложения. Файл — CSV в UTF-8 с BOM, разделитель `;`, все колонки
  таблицы `audit_log` (включая `id`), права `0600`; значение, которое Excel принял бы за формулу (начинается с `=`, `+`, `-`, `@`), дополнено
  ведущим апострофом. Уборка отчётов (`INFRA_REGISTRY_REPORT_RETENTION_DAYS`, `INFRA_REGISTRY_REPORT_MAX_FILES`) архивы не считает и не
  удаляет, и **приложение их само не удаляет никогда**: свободное место и срок хранения архивов — на стороне администратора (в Docker
  каталог лежит в томе данных `appdata`). Если проход прервался между записью архива и удалением, те же записи попадут в следующий файл —
  дубли между файлами различает `id`. Читать архив, не запуская приложение, можно любым редактором или `python -m csv`.
  Отчёт журнала аудита (`.xlsx`) сохраняется в подкаталоге `reports/audit/` и скачивается отдельным адресом
  `GET /api/v1/reports/audit-log/download/{имя}` — только администратору (адрес приходит в ответе формирования отчёта). Общий адрес
  `/api/v1/reports/download/…` этот подкаталог не читает. Срок хранения и лимит числа файлов (`INFRA_REGISTRY_REPORT_RETENTION_DAYS`,
  `INFRA_REGISTRY_REPORT_MAX_FILES`) считаются по корню и подкаталогу вместе. Отчёты, сформированные прежними версиями, остаются в
  корне и по-прежнему отдаются только администратору (проверка по имени файла).
- **За обратным прокси** перечислите его адрес в `FORWARDED_ALLOW_IPS` (адреса или подсети через запятую). Иначе uvicorn не
  подставляет адрес клиента из `X-Forwarded-For`, и у всех клиентов адрес прокси: троттлинг входа становится общим — несколько неверных
  паролей нападающего задерживают вход и настоящего администратора, — «знакомым» был бы любой адрес, а в журнале аудита и списке
  сессий записан адрес прокси. Если заголовок `X-Forwarded-For`, `Forwarded` или `X-Real-IP` приходит с адреса, которого нет в этом списке,
  сервер один раз за запуск пишет в журнал предупреждение, а исключение «знакомый адрес» из блокировки учётной записи для такого запроса
  не применяется (блокировка действует как для незнакомого адреса); сам запрос при этом не блокируется. Значение `*` допустимо, только если
  порт доступен одному прокси: иначе любой клиент подделает свой адрес заголовком. Заголовки `Forwarded` (RFC 7239) и `X-Real-IP` uvicorn
  не разбирает — настройте прокси на `X-Forwarded-For` (в nginx: `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`).
- **Иконки диаграмм** проходят проверку по белому списку тегов и атрибутов SVG; `.svg`-экспорт вкладывает
  пользовательскую иконку как изображение (data URI), а не как исполняемую разметку. У разметки есть пределы: не более 256 К символов,
  вложенность не глубже 32 уровней и не более 5000 элементов; иконка сверх предела отклоняется при сохранении (422), а не обходится рекурсией
  или разбором гигантского документа на сервере.
- **Заголовки безопасности.** Ответы содержат `Content-Security-Policy`, `X-Content-Type-Options`, `X-Frame-Options` и `Referrer-Policy` — в том
  числе отказы внешних проверок (`400` по `Host`, `403` по `Origin` и по адресу клиента, `413` по размеру тела): заголовки ставятся
  самым внешним слоем, а не только обработчиками. Исключение — CSP на `/docs`, `/redoc` и `/openapi.json` (по умолчанию выключены, см. ниже).
  Ответы `/api/*` (включая отказы шлюза доступа) несут `Cache-Control: no-store`: данные реестра и списки сессий не должны оседать в кэше
  браузера или общего прокси. Политика CSP по умолчанию не разрешает ни `'unsafe-inline'`, ни `'unsafe-eval'` для скриптов (проверяет тест).
  Шлюз доступа и слои ограничений — чистые ASGI-middleware (без `BaseHTTPMiddleware`), поэтому предел тела запроса работает одинаково
  с включённой и выключенной аутентификацией, в том числе для тела без `Content-Length` (`413`).
- **Документация API** (`/docs`, `/redoc`, `/openapi.json`) по умолчанию выключена и отвечает `404`: иначе полную карту API и моделей
  данных видел бы любой посетитель без входа, а Swagger UI/ReDoc грузят скрипты с внешнего CDN (в закрытом контуре они не работают).
  Для разработки включите `INFRA_REGISTRY_ENABLE_DOCS=1` — страницы будут открыты без входа, не оставляйте опцию на сервере.

Открыть:

```text
http://localhost:8000        # UI (Vue)
http://localhost:8000/docs   # только при INFRA_REGISTRY_ENABLE_DOCS=1 (по умолчанию выключено)
```

### Локальный запуск без Docker

Требуется Python 3.12+ и Node.js 22+ (CI и Docker-образ собирают на 26 LTS) (для сборки UI):

```bash
python -m venv .venv
# Windows
.venv\Scripts\activate
# Linux/macOS
source .venv/bin/activate

pip install -r backend/requirements.txt   # диапазоны версий; для точно тех же версий, что в Docker и CI: см. «Зависимости backend»

npm run build   # собирает dist/, который раздаёт бэкенд на '/' (см. frontend-vue/README.md)
```

Если пропустить сборку `frontend-vue`, `/` ответит понятной 500-ошибкой с
подсказкой собрать фронтенд (`npm run build`).

### Запуск как EXE (Windows)

`InfraRegistry.exe` — самостоятельное Windows-приложение с локальным веб-интерфейсом, не требующее
интернета, PostgreSQL или Docker. При запуске оно:

1. создаёт/использует каталог рядом с самим EXE;
2. создаёт или обновляет SQLite БД `infra_registry.db`;
3. автоматически выполняет `alembic upgrade head` (если база создана предыдущей версией — сначала делает её резервную копию, см. ниже);
4. запускает локальный FastAPI/Uvicorn-сервер;
5. открывает браузер на `http://127.0.0.1:8000`.

**Хранение данных.** База данных SQLite и каталог отчётов хранятся **рядом с исполняемым файлом**,
а не внутри него:

```text
InfraRegistry.exe
infra_registry.db
reports\
```

Это позволяет переносить каталог приложения целиком вместе с базой, а обновление самого EXE не
удаляет накопленный реестр. Каталог с EXE должен быть доступен для записи текущему пользователю —
приложение создаёт/изменяет `infra_registry.db`, каталог `reports` и выполняет миграции.

**Резервные копии базы при обновлении.** Часть миграций необратима (удаляет данные), а в SQLite изменение схемы
нельзя откатить транзакцией: сбой посреди миграции оставляет базу в промежуточном состоянии. Поэтому, если при запуске
`infra_registry.db` существует, содержит данные и её версия схемы не равна текущей (то есть вы заменили EXE на более
новый), перед миграцией рядом с базой создаётся согласованная копия (средствами SQLite, это безопасно и при открытой базе):

```text
infra_registry.db
infra_registry.pre-3a7c1e5d.20261024-093000.bak   <- <имя базы>.pre-<версия схемы>.<дата-время>.bak
```

Путь копии выводится в консоли при запуске. Хранятся **5 последних** копий, более старые удаляются; удаляются только файлы
этой маски — ваши собственные `.bak` рядом с базой не затрагиваются. На уже актуальной базе, новой или пустой копия не
создаётся (запуск без обновления ничего не копирует). Если копию создать не удалось (нет места, нет прав на запись),
приложение **не запускает миграцию**, сообщает причину и завершается с кодом 2 — база остаётся нетронутой.
Если сбой случился уже в ходе миграции, приложение так же завершается с кодом 2 и выводит причину и путь к копии, сделанной перед
миграцией, откуда вернуть прежнюю версию (или сообщает, что копии нет: база была пустой либо копирование отключено). Другие ожидаемые
сбои запуска — нет прав на каталог данных, неверное значение переменной окружения — тоже выводятся понятным текстом, без трассировки.

*Восстановление после неудачного обновления:* закройте приложение, верните прежний EXE, переименуйте повреждённый
`infra_registry.db` (например, в `infra_registry.broken.db`) и скопируйте нужный `.bak` под именем `infra_registry.db`.
Копия — обычный файл SQLite, открывается любым клиентом SQLite. Запуск без копии (на свой риск, например при нехватке
места) — переменная окружения `INFRA_REGISTRY_SKIP_BACKUP=1`.

**Плановые резервные копии (SQLite: EXE, локальный запуск, SQLite в Docker).** Копия перед обновлением защищает только от неудачной
миграции, а от потери данных между обновлениями (сбой диска, ошибочное массовое удаление, чужая правка) приложение само делает
плановые копии, пока оно запущено:

- **когда:** при запуске, если плановых копий ещё нет или последняя старше интервала, и затем через каждые 24 часа работы. EXE
  выключают на ночь, поэтому «раз в сутки в 03:00» не сработало бы никогда — проверка выполняется при каждом запуске, а перезапуск
  приложения не плодит копии (ждётся остаток интервала). Базу, не менявшуюся с прошлой копии, не копируем;
- **как:** согласованная копия средствами SQLite (безопасно при открытой базе), записывается во временный файл, проверяется
  `PRAGMA quick_check` и только потом получает имя `.bak`. Копия, не прошедшая проверку, удаляется, а в журнале приложения появляется
  ошибка; при любом сбое (нет места, нет прав) повтор через час, приложение работает как обычно;
- **где:** каталог `backups` рядом с базой (в Docker — внутри тома данных, он переживает пересоздание контейнера), файлы
  `<имя базы>.auto.<дата-время>.bak`; на Linux каталог и файлы доступны только владельцу (в копии хэши паролей и весь журнал аудита).
  Хранятся **7 последних** плановых копий; копии перед обновлением (`.pre-…`) и ваши собственные `.bak` не затрагиваются.
  **Копия на том же диске, что и база, от поломки этого диска не спасает** — задайте каталог на другом диске или сетевой папке;
- **настройки:** переменные окружения, в EXE — раздел `[backup]` файла `infra_registry.toml` (строки в шаблоне закомментированы):

| Переменная | `infra_registry.toml` | По умолчанию | Значение |
| --- | --- | --- | --- |
| `INFRA_REGISTRY_BACKUP_INTERVAL_HOURS` | `[backup] interval_hours` | `24` | как часто делать копию, часов; `0` — плановых копий нет; допустимы дробные значения (`0.5`) |
| `INFRA_REGISTRY_BACKUP_KEEP` | `[backup] keep` | `7` | сколько плановых копий хранить (не меньше 1) |
| `INFRA_REGISTRY_BACKUP_DIR` | `[backup] directory` | `<каталог данных>/backups` | каталог копий, только абсолютный путь |

Неверное значение останавливает запуск с сообщением, где названа переменная (в EXE — параметр файла настроек).

**Настройка из интерфейса.** Интервал и число копий администратор меняет в «Настройки → Резервные копии» (при выключенной аутентификации — любой
пользователь: в этом режиме ролей нет; `GET`/`PUT /api/v1/backup/settings`, у роли viewer — 403). Изменение действует сразу, перезапускать приложение не
нужно: планировщик отменяется и запускается заново (копия при этом делается, только если она уже пора по новому интервалу). Приоритет значений —
**окружение (или `infra_registry.toml`) > форма > умолчание**: параметр, заданный окружением, в форме виден с пометкой «задано в окружении» и не
меняется (сервер на такую правку отвечает 409). Через форму интервал — `0` (копии выключены; перед сохранением форма просит подтверждение) или от 1
до 8784 часов (чаще раза в час — только переменной окружения), число копий — от 1 до 365. **Каталог копий из формы не меняется**: он задаётся только
`INFRA_REGISTRY_BACKUP_DIR` и в форме лишь показывается — запись пути из веб-формы позволила бы положить копию всей базы (хэши паролей, журнал аудита) в
раздаваемый каталог или за пределы тома Docker. Каждое изменение пишется в журнал аудита (раздел «Настройки резервных копий»: кто, старое и новое
значение). Панель показывает и статус: последнюю копию (время, имя файла, размер) и итог последней попытки планировщика, в том числе текст ошибки
(только с запуска приложения: после перезапуска «последней попытки» нет, пока не пройдёт очередная проверка). Для PostgreSQL планировщика нет, и панель только
подсказывает, что копии делает оператор средствами СУБД; сохранить настройки там нельзя (409).

**Восстановление** — как после неудачного обновления: закройте приложение,
переименуйте повреждённый `infra_registry.db` и скопируйте нужный `.auto.….bak` под именем `infra_registry.db`.

**Сборка** выполняется **на Windows** (PyInstaller собирает исполняемый файл под текущую ОС;
сначала собирается основной UI — `installer\build_windows.bat` делает это автоматически,
поэтому требуется установленный Node.js 22+ (CI и Docker-образ собирают на 26 LTS)):

```bat
installer\build_windows.bat
```

Результат — `dist\InfraRegistry.exe`.

**Проверка уязвимостей при сборке.** Скрипт сам останавливается на известных уязвимостях в пакетах: после `npm ci` запускает
`npm run audit:gate` (`npm audit` по runtime-зависимостям frontend, уровень high и выше, с исключениями из
`frontend-vue/scripts/audit-gate.mjs`), а после установки Python-пакетов — `python -m pip_audit` по `backend\requirements.lock`
(блокирует сборку: эти пакеты попадают в EXE) и по `backend\requirements-build.lock` (только сообщает: PyInstaller и его хуки иногда
дают замечания, не относящиеся к рантайму). pip-audit входит в `requirements-build.txt` и ставится в `.venv` из того же lock с хешами;
в EXE он не попадает. Правила совпадают с одноимёнными шагами CI. Проверкам нужен доступ к PyPI и registry.npmjs.org — тот же, что и для
установки пакетов. В CI эту сборку и эти проверки выполняет job `build-windows` (windows-latest): он запускает тот же
`installer\build_windows.bat` и проверяет, что в `dist\` появились `InfraRegistry.exe`, `README_EXE.md` и `run_infra_registry.bat`.
Затем job делает smoke-запуск готового EXE: `InfraRegistry.exe --no-browser` на порту 8765 с базой во временном каталоге
(`INFRA_REGISTRY_DATA_DIR`), проверка `/api/v1/health` и версии (она совпадает с `APP_VERSION` из `backend/app/config.py`; публичный health версию
не отдаёт, поэтому smoke включает `INFRA_REGISTRY_ENABLE_DOCS=1` и читает её из `/openapi.json`), раздачи собранного
интерфейса на `/` и того, что миграции внутри EXE создали схему в `infra_registry.db`; при падении в журнал шага выводятся логи EXE.
Вход в систему и экспорт `.vsdx` smoke не проверяет. Job `build-windows` выполняется и по расписанию — раз в неделю, по понедельникам
(04:17 UTC): новая уязвимость в уже влитых зависимостях иначе осталась бы незамеченной до следующего PR; остальные job по расписанию
пропускаются. Весь CI можно запустить и вручную (`workflow_dispatch`, вкладка Actions). Расписание работает только в ветке по умолчанию,
а GitHub отключает его в репозитории без активности 60 дней.

Рядом с ним скрипт кладёт `dist\README_EXE.md` (краткая инструкция для пользователя; исходник — `installer\README_EXE.md`) и
`dist\run_infra_registry.bat`. Ошибка копирования любого из файлов, как и ошибка PyInstaller, прерывает сборку с ненулевым кодом.

**Запуск** — двойным щелчком по `InfraRegistry.exe`, либо с параметрами (они важнее файла настроек):

```bat
InfraRegistry.exe --port 8010
InfraRegistry.exe --no-browser
```

**Перенос на другой ПК** — достаточно скопировать `InfraRegistry.exe`; при первом запуске
приложение самостоятельно создаст БД, каталоги и файл настроек.

#### Файл настроек и доступ с других компьютеров

Настройки EXE хранятся в файле `infra_registry.toml` **рядом с `InfraRegistry.exe`**. Если файла нет, приложение
при запуске создаёт его со значениями по умолчанию (существующий файл не перезаписывается; изменения применяются
после перезапуска). Подробные комментарии с примерами — в самом файле.

```text
InfraRegistry.exe
infra_registry.toml
infra_registry.db
reports\
```

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `[server] port` | `8000` | порт веб-интерфейса (`--port` важнее) |
| `[server] open_browser` | `true` | открывать браузер при запуске (`--no-browser` важнее) |
| `[access] allowed_clients` | `[]` | IP-адреса и подсети компьютеров, которым разрешено подключаться по сети |
| `[access] allowed_hosts` | `[]` | имена компьютера, по которым открывают приложение (по IP-адресу — без настройки) |

**По умолчанию доступ только с этого компьютера:** приложение слушает порт на `127.0.0.1`, из сети он не виден.
Чтобы пускать другие компьютеры, перечислите их в `allowed_clients` и перезапустите приложение — оно начнёт слушать
порт на всех интерфейсах, а подключения с адресов вне списка получат `403`. Этот компьютер разрешён всегда.

```toml
allowed_clients = ["192.168.1.15"]                      # один компьютер
allowed_clients = ["192.168.1.15", "192.168.1.20"]      # несколько компьютеров
allowed_clients = ["192.168.1.0/24"]                    # вся подсеть (192.168.1.1 – 192.168.1.254)
allowed_clients = ["192.168.1.0/24", "10.0.5.7"]        # подсеть и отдельный компьютер
```

Запись `/24` — длина маски подсети (`255.255.255.0`); `/16` — `255.255.0.0`, `/32` — один адрес. Поддерживается
только IPv4. Дальше нужно:

1. **Брандмауэр Windows.** Разрешить входящие TCP-подключения на порт приложения (командная строка администратора):
   `netsh advfirewall firewall add rule name="RIS" dir=in action=allow protocol=TCP localport=8000`
   (добавьте `remoteip=192.168.1.0/24`, чтобы правило действовало только для своей подсети).
2. **Адрес.** С другого компьютера открыть `http://<IP-адрес компьютера с EXE>:8000`. Адрес-литерал принимается
   сразу; если нужно открывать по имени (`http://reestr-pc:8000`), добавьте имя в `allowed_hosts`.
3. **Аутентификация.** Пока вход выключен, любой разрешённый компьютер читает и меняет весь реестр без пароля
   (при запуске в консоль выводится предупреждение). Первичная настройка (создание администратора, включение
   входа) по-прежнему доступна **только с самого компьютера, где запущено приложение**, поэтому сначала включите
   аутентификацию в «Настройки → Аутентификация», затем открывайте доступ.

Ошибка в файле (неверный адрес, неизвестный параметр, опечатка в синтаксисе) не игнорируется: приложение выводит
причину и не запускается, чтобы запись о доступе не оказалась «молча не применённой». Исправьте файл или удалите
его — он будет создан заново. Если каталог с EXE недоступен для записи и файл создать нельзя, приложение работает с
настройками по умолчанию (только локально).

> **Ограничения.** Подключение идёт по HTTP без шифрования — используйте только доверенную сеть. SQLite и один
> процесс рассчитаны на небольшое число одновременных пользователей (записи выполняются по очереди). Для
> постоянной работы многих сотрудников используйте серверный вариант: Docker + PostgreSQL.

## Отчёт Excel

Отчёт формируется по техническому заданию и состоит из 4 листов.

**Лист 1. Перечень ИС** — №, наименование и описание ИС, назначение использования, работники и
подразделения, использующие ИС, локализация, оборудование, на котором размещена ИС, протокол и
IP-адрес взаимодействия, применение сертифицированных СКЗИ, признак получения событий в SIEM,
организация внешнего взаимодействия/техподдержки и способ её оказания, описание процесса
функционирования ИС, а также физический сервер/ВМ (контейнер), обеспечивающие работу ИС, с их
IP-адресами.

**Лист 2. Инвентаризация физических устройств ИС** — №, вид устройства (сервер, сетевое
оборудование, средство защиты информации, рабочий ПК администратора), производитель, модель,
серийный номер, системное имя, версия ОС, порт и IP-адрес управления, признак получения событий в
SIEM, количество физических портов, адрес и здание расположения, помещение/место размещения.

**Лист 3. Организация подключений** — №, вид устройства, серийный номер и системное имя, ОС,
физический/логический порт и его IP-адрес, перечень открытых портов с протоколами, VLAN ID/Name,
тип и назначение физической линии связи, а также аналогичный набор колонок для соседнего
подключённого устройства (вид, серийный номер, системное имя, ОС, IP-адрес порта).

**Подинтерфейсы портов в отчёте** выводятся внутри строки своего порта, отдельных строк у них нет. Колонка порта:
`Gi0/0 (подинтерфейсы: Gi0/0.10 [VLAN 10], Gi0/0.20 [VLAN 20])`; IP, открытые порты и назначение подинтерфейса идут
в тех же колонках с его именем (`Gi0/0.10: 10.0.10.1/24`); VLAN подинтерфейсов добавляются в колонки VLAN ID / Name без
повторов. Если управление устройством висит на подинтерфейсе (у него стоит «Управление»), его порт и IP — это порт и IP
управления на Листе 2, в колонке IP соседа на Листе 3 и в IP физического сервера на Листе 1. Количество физических портов
подинтерфейсы не увеличивают. На схеме подключений IP подинтерфейсов входят в IP узла (назначение начинается с имени
подинтерфейса), а VLAN — во VLAN ребра порта.

**Подинтерфейсы в форме устройства и в группах портов.** Подинтерфейсы порта — таблица («Имя», «VLAN», «Управление», «Данные» и
разворачиваемый столбец «IP-адреса / маски», по умолчанию свёрнутый). VLAN подинтерфейса выбирается (`SearchableSelect`) только из
VLAN, выбранных на этом порту, и только из ещё не занятых другими подинтерфейсами порта. Группа портов может задавать подинтерфейсы
всех своих портов (галочка «Задать подинтерфейсы»): каждому порту записываются подинтерфейсы `<порт>.<номер VLAN>` с общими ролью,
IP и открытыми портами, остальные подинтерфейсы порта удаляются; у такого порта список только для просмотра. Правило «VLAN
подинтерфейса — один из VLAN порта» (у порта с «Все VLAN» — любой VLAN устройства) проверяют и форма, и сервер: `PUT /devices/{id}/interfaces`
отвечает 422, если после записи портов и групп подинтерфейс остался на VLAN, не выбранном на его порту. В окне группы «Скопировать
значения с порта» умеет копировать и подинтерфейсы порта: они становятся шаблонами группы (без имён и id), а те, чей VLAN не входит
в VLAN группы, не копируются, и уведомление называет их.

**Несколько общих IP-адресов у группы портов.** Группа может задавать не один общий IP, а список («Общие IP-адреса», кнопка «IP-адрес»):
у каждого адреса свои префикс и назначение. Группа с хотя бы одним адресом управляет IP своих портов ПОЛНЫМ списком — каждому порту
записываются все адреса группы, остальные IP порта удаляются (у такого порта блок «IP-адреса интерфейса» только для просмотра);
группа без адресов IP портов не трогает. Строка без адреса — пустой плейсхолдер: не сохраняется, назначение у неё недоступно.
Адрес в пределах группы не повторяется (проверяют и форма, и сервер — 422); одинаковые адреса в разных группах допустимы. Записи IP
порта не пересоздаются: совпавшие по адресу и префиксу сохраняют `id`, лишние переиспользуются под новые адреса группы. Хранение —
таблица `interface_group_ips` (Alembic `d5a8c3e7b196`; прежние колонки `interface_groups.ip_address/prefix_length/ip_purpose`
перенесены в неё одной строкой на группу и сняты). Контракт API: у группы поле `ips` (`id`, `ip_address`, `prefix_length`, `purpose`)
вместо `ip_address`/`prefix_length`/`ip_purpose`. В окне группы «Скопировать значения с порта» копирует все IP порта (повторы адреса
схлопываются), а не только первый.

**Подинтерфейсы на дашборде устройств и «устаревший» VLAN.** Подинтерфейс с ролью «Управление» показывается в списке
устройств как порт и IP управления (`Gi0/0 (подинтерфейс Gi0/0.99)`), как и в отчёте. Подинтерфейс никогда не удаляется
молча: если VLAN сняли с устройства, убрали из его типа или перенесли в другой домен, подинтерфейс остаётся на этом VLAN.
Форма устройства предупреждает об этом сразу при снятии VLAN, помечает порт значком и до отправки на сервер не даёт
сохранить, пока подинтерфейсу не выбран другой VLAN (или он не удалён); при переносе VLAN между доменами оставшиеся
подинтерфейсы перечисляются в журнале аудита. Автоимена подинтерфейсов (`<порт>.<VLAN>`) следуют за переименованием
порта, имена, введённые вручную, остаются как есть.

Все подинтерфейсы на недоступном VLAN по реестру сразу показывает диагностика
`GET /api/v1/integrity/stale-subinterfaces` (устройство, порт, подинтерфейс, VLAN и причина `reason`: `device` — VLAN больше не разрешён
устройству, `port` — разрешён устройству, но не выбран на порту; в `group_subinterfaces` — шаблоны подинтерфейсов групп портов на VLAN,
которого у группы больше нет; только чтение). В форме устройства
предупреждение о снятом VLAN имеет кнопку «Показать» (раскрывает порты с такими подинтерфейсами), а у самого подинтерфейса —
список «Перенести на VLAN…»: VLAN меняется одним действием, автоимя пересчитывается. Если таких подинтерфейсов много, над
таблицей портов появляется панель «Перенести все на VLAN…»: все они переносятся на выбранный VLAN устройства разом (где на
порту этот VLAN уже занят, подинтерфейс остаётся на месте, и уведомление называет такие).

Диагностика видна и в интерфейсе: на экране «VLAN» над таблицей появляется карточка «Подинтерфейсы на VLAN, не разрешённом
устройству» со списком по устройствам и кнопкой «Открыть устройство» (откроется форма, где подинтерфейс переносят или удаляют);
после сохранения устройства карточка обновляется, а если проблем нет — на экране её нет.

Назначение линии связи (управление / передача данных) не вводится в подключении — оно берётся из
ролей портов (`is_management` / `is_data_transfer` у самого интерфейса). Дашборд «Подключения»
сверяет конфигурацию портов-соседей: **роль**, **режим порта** (trunk / access) и **набор VLAN**
(по номеру VLAN, не по записи справочника). Если что-то из этого различается (например, порт
управления сервера включён в порт коммутатора, настроенный на передачу данных, или один конец
линии — trunk, другой — access), подключение попадает в «Расхождения»: можно выровнять роль,
поправить режим и VLAN в окне портов устройства или одобрить расхождение.

**Правка порта прямо с дашборда.** Карандаш рядом с именем порта в строке (и кнопки «Изменить порт…» в окне проверки
расхождения) открывает окно «Конфигурация порта»: роль (тип использования: управление / передача данных), режим
(access / trunk) и набор VLAN. VLAN предлагаются те же, что в форме устройства (типа устройства и собственные); в access
выбирается один VLAN, при переходе trunk → access остаётся VLAN с наименьшим номером. Кнопка «Задать как у соседа» берёт
роль, режим и VLAN порта на другом конце линии (по номеру VLAN; номера, которых нет у устройства, не назначаются, об
этом сообщается). Окно сразу показывает, совпадёт ли порт с соседом после сохранения. Режим меняется общим каскадом
(`POST /interfaces/{id}/vlan-mode-cascade[/preview]`): сервер считает связанные порты и группы, а окно показывает
последствия до применения. Роль и VLAN уходят в том же запросе (поле `port: {role?, vlan_ids?}`) и записываются **одной
транзакцией** с каскадом: либо записано всё, либо ничего — состояния «режим сменён, а роль и VLAN нет» не бывает; ошибку в
роли или VLAN (например, VLAN, которого нет у устройства, или несколько VLAN при целевом access) сервер показывает уже при
предпросмотре, до подтверждения. Если режим не меняется, роль и VLAN записываются атомарным запросом
`PUT /api/v1/interfaces/{id}/port-config` (`{role?, vlan_ids?, mode?}`; `vlan_ids` — полный набор, `mode` — только проверка:
если режим порта изменился, ответ 409). Порт в группе, которая задаёт режим и VLAN, по VLAN не правится (409) — меняйте
группу; роль у такого порта менять можно. Запись попадает в журнал аудита, статус сверки пересчитывает сервер. Форма подключения
перед сохранением показывает роль, режим и VLAN обоих портов и не сохраняет подключение с
расхождением молча: нужно выровнять роль порта или одобрить расхождение (режим и VLAN правятся в окне
портов — кнопка «Управлять портами» в форме). Сверку для формы делает сервер теми же правилами
(`GET /api/v1/connections/port-config/preview?source_interface_id=&destination_interface_id=&connection_id=&is_active=`),
поэтому предупреждение формы и статус на дашборде не расходятся; если сервер не ответил, форма
сверяет хотя бы роли по каталогу. Дашборд показывает такие подключения
(счётчик, фильтры «Расхождения» / «Одобренные», пакетное одобрение), а одобрение теряет силу, как
только меняется роль, режим или набор VLAN любого из портов. Неактивные подключения в сверке не
участвуют.

Таблица дашборда постраничная: поиск, фильтры, статус сверки и счётчики считает сервер
(`GET /api/v1/connections?q=&is_active=&port_config_status=&offset=&limit=`), браузер держит только
текущую страницу, поэтому число подключений не ограничено 1000 записями. Поиск нечувствителен к
регистру и для кириллицы (в SQLite для этого подменяется встроенный `LOWER()`, см. `app/db.py`).
«Одобрить все найденные» одобряет расхождения по всем страницам под текущими поиском и фильтром.

**Лист 4. Организация управления ВМ** — название и ОС виртуальной машины, наименование контейнера,
физическое устройство-хост по его системному имени, среда виртуализации и её версия, целевое
назначение ВМ/контейнера, IP-адрес и IP-адрес администрирования, открытые порты с протоколами,
развёрнутые программные активы (1С, веб-сервер, файловый сервер, AD и т. п.).

**Фильтр по структурным единицам.** Перед формированием отчёта (кнопка «Сформировать Excel» на
дашборде, и генерация шаблонов конструктора, построенных на сущностях реестра — см. ниже) можно
ограничить его оборудованием, размещённым в одной, нескольких или всех структурных единицах сразу
(см. раздел «Возможности» → «Структурные единицы»). Без выбора отчёт формируется как раньше, без
ограничения.

## Приложение к структурной схеме (Word)

Отдельный отчёт (страница «Отчёты» → «Приложение к структурной схеме», `POST /api/v1/reports/structural-appendix`,
тело `{is_name?, structural_unit_ids?}`) — Word-документ из трёх пронумерованных таблиц под заголовком
«Приложение к структурной схеме» / «ЕАИС `<имя>`». Имя ИС (по умолчанию «ЕАИС ТО»; ведущее «ЕАИС»/«ИС» в заголовках не дублируется) подставляется в заголовки
(«ЕАИС ТО», «… ИС ТО»); необязательный фильтр по структурным единицам действует так же, как у Excel-отчёта.

1. **Сведения о назначении линий связи** — строка на каждое действующее подключение
   (`Производитель модель (системное имя) (порт)` — то же для второго конца). Назначение — одна объединённая
   ячейка на группу линий: «управление активами», «передача данных», «передача данных и управление активами»
   (объединение ролей обоих портов и их подинтерфейсов; линии без роли идут последними). Неактивные
   подключения не попадают в документ.
2. **Перечень VLAN** — под строкой-заголовком устройства (`Тип Производитель модель (имя) (серийные номера)`)
   идут его VLAN: идентификатор, имя, адресация «IP/префикс» как введено на устройстве. Участники одного стека —
   одна группа без дублей; устройства без VLAN не показываются.
3. **Перечень телекоммуникационного оборудования** — все устройства: наименование, заводской номер, системное
   имя, IP управления (по одному на строку ячейки, без префикса), место размещения — объединённая ячейка на
   устройства одного помещения.

Порядок устройств — порядок их создания в реестре, участники стека идут подряд. Данные собирает
`backend/app/services/structural_appendix.py` (на том же загрузчике реестра, что и Excel-отчёт), документ
рисует `structural_appendix_docx.py`; оформление (Times New Roman, сетка, поля) выбрано по обычаям делового
документа. Прежний шаблон конструктора «Приложение к структурной схеме (по образцу)» (плоские таблицы без
объединения ячеек) удалён миграцией `a9e3d4f17b26`: она убирает только нетронутую заготовку, отредактированный
пользователем шаблон с этим именем остаётся.

## Конструктор произвольных отчётов

Помимо регламентированного 4-листового отчёта (см. выше), приложение включает **конструктор
произвольных отчётов** — модуль, позволяющий пользователю без программирования собрать
собственный отчёт `.xlsx` или `.docx` на основе данных реестра. Открывается пунктом меню «🧩
Конструктор отчётов». Формат `.xlsx` редактируется визуальным **grid-редактором листа** (см.
ниже), формат `.docx` — **блочным редактором документа** (см. ниже).

При обновлении в список шаблонов автоматически добавляется готовый шаблон:
- **«Регламентированный отчёт — заготовка (4 листа)»** (`.xlsx`) — точное воспроизведение
  содержимого фиксированного отчёта выше (данные и заголовки совпадают 1:1 — проверено тестом на
  реальных данных, не только структурно), но собранное через grid-движок конструктора и открытое
  для дальнейшей правки. Подробности — в записи 2.39.0 в истории изменений ниже и в комментарии в
  начале `backend/app/services/report_seed_templates.py`.

Word-документ «Приложение к структурной схеме» формирует отдельный отчёт (см. раздел
[«Приложение к структурной схеме (Word)»](#приложение-к-структурной-схеме-word)); бывший шаблон-заготовка
конструктора для него (запись 2.42.0) удалён миграцией `a9e3d4f17b26`.

### Что умеет grid-редактор (.xlsx)

Редактор показывает лист как настоящую таблицу-канвас (строки/колонки/ячейки), а не форму со
списком колонок — состав, положение и оформление каждой ячейки задаются визуально:

- **Перетаскивание полей из палитры прямо на ячейку листа** (drag-and-drop). Палитра строит
  плоский список доступных путей на глубину до двух связей, включая связи «многие-ко-многим»
  через связующие таблицы (например, `is_departments[].department.name` — подразделения ИС).
  Первое поле, перетащенное в строку, автоматически включает для неё повторение (см. ниже) и
  привязывает её к соответствующей сущности.
- **Повторяющиеся строки.** Любая строка листа может быть отмечена как «повторяющаяся» —
  тогда при генерации файла она клонируется по одной физической строке на каждую запись
  выбранной сущности (с опциональным циклическим разворотом по связи «один/многие-ко-многим» —
  например, отдельная строка на каждую ВМ каждого физического сервера — и фильтрами по любому
  доступному пути поля: равно / не равно / содержит / не содержит / не пусто / да·нет).
  Остальные строки — статические (заголовки, титульная часть, произвольный текст).
- **Объединение ячеек** по горизонтали и вертикали (выделение диапазона — клик по первой ячейке,
  Shift+клик по последней) — с проверкой, что вертикальное объединение не пересекает
  повторяющуюся строку.
- **Оформление ячейки**: жирный/курсив/подчёркнутый, рамка, перенос текста, выравнивание по
  горизонтали/вертикали, цвет фона и текста, числовой формат (в т.ч. даты) — сохраняется как
  настоящее форматирование ячейки в итоговом `.xlsx` (не только текст); высота строки при
  необходимости автоматически увеличивается под перенесённый текст (см. запись 2.41.0).
- **Формулы Excel** — ячейка может содержать формулу (`=...`), которую вычислит сам Excel при
  открытии файла; в тексте формулы, как и в статическом тексте, работает подстановка параметров
  (`{{ключ}}`, `{{report_date}}`).
- **Параметры отчёта**, которые пользователь вводит непосредственно перед формированием файла
  (например, «Организация», «Дата отчёта», «Составил»).
- **Живой предпросмотр** — материализованные строки/ячейки (с учётом объединений и оформления)
  можно посмотреть прямо в редакторе, не сохраняя шаблон и не создавая файл.
- Несколько листов на шаблон; шаблоны можно **сохранять, дублировать, смотреть историю версий и
  восстанавливать** предыдущее состояние, удалять.

### Что умеет блочный редактор (.docx)

Документ собирается из блоков сверху вниз, порядок блоков — это порядок содержимого в файле:

- **Заголовок** (уровень 1-6) и **Абзац** (с выравниванием) — текст, в котором работает
  подстановка параметров (`{{ключ}}`, `{{report_date}}`), как и в xlsx.
- **Таблица** — привязывается к сущности реестра (тот же выбор сущности/поля/фильтров/сортировки/
  циклического вывода по связи, что и в xlsx-редакторе, с тем же помощником-подсказкой пути поля);
  колонка — заголовок + один из трёх источников: поле из БД (с разделителем для полей-списков),
  статический текст или № по порядку. Колонки и блоки переставляются кнопками (←/→ и ↑/↓).
- **Разрыв страницы.**
- **Живой предпросмотр** табличных блоков и сохранение/формирование — по общей схеме с xlsx.

### Ограничения текущей версии

- В grid-редакторе (.xlsx) нет многоклеточного выделения мышью (только Shift+клик по паре ячеек),
  undo/redo, копирования ячеек и авто-подбора ширины колонок по содержимому — состав и порядок
  листов/строк/колонок настраивается явными действиями (кнопки +/✕, инспектор ячейки/строки справа).
- В блочном редакторе (.docx) нет drag-and-drop полей на таблицу (путь поля вводится текстом с
  помощником-подсказкой, как в старом xlsx-редакторе до grid) и нет группировки строк таблицы под
  вложенным заголовком (см. пример в описании шаблона «Приложение к структурной схеме» выше) —
  один блок-таблица всегда плоский, на одной сущности.

### Как это устроено технически

- `backend/app/services/report_meta.py` — граф полей и связей (`to_one`/`to_many`) выводится
  **автоматически** из существующих моделей БД (`MODEL_MAP`) через `sqlalchemy.inspection`, без
  ручного описания каждой пары таблиц; при добавлении новой сущности/поля в схему БД конструктор
  подхватывает её без изменений в этом модуле.
- `backend/app/services/report_engine.py` — разбор путей полей, подстановка параметров,
  циклический вывод строк по связи и (для формата `.docx`) структурная валидация блоков документа.
  **Сортировка строк (`sort_by`)** идёт по «сырому» значению поля, а не по готовой строке (`_sort_key`): числа (VLAN `2, 9, 10, 100`) и даты
  (хронологически) сортируются как числа и даты, пустые значения — в конец; для `.docx` и `.xlsx` одинаково. В шаблонах, где задан `sort_by`,
  пустые значения теперь внизу таблицы, а не вверху (с 2.159.0).
- `backend/app/services/report_grid.py` — grid-движок формата `.xlsx`: валидация листа (позиции и
  объединения ячеек, источники данных повторяющихся строк), материализация конфигурации в
  физические строки/ячейки и рендеринг в настоящий `.xlsx` через openpyxl (стили, объединение,
  числовой формат, формулы), а также предпросмотр без записи файла на диск.
- `backend/app/services/report_render.py` — сборка `.docx` (python-docx: заголовки, абзацы,
  таблицы, разрывы страниц) и предпросмотр блоков документа.
- `backend/app/api/report_builder.py` — REST API: `GET /api/v1/report-builder/entities` (список
  сущностей/полей/связей для UI), CRUD `/api/v1/report-templates` (+ история версий и
  восстановление), `POST /api/v1/report-templates/{id}/generate`, `POST
  /api/v1/report-templates/{id}/duplicate`, `POST /api/v1/report-builder/preview` — валидация и
  предпросмотр диспетчеризуются по `format` шаблона (`xlsx` → `report_grid.py`, `docx` →
  `report_engine.py`/`report_render.py`), поскольку обе структуры конфигурации хранятся в одном
  JSON-поле `config` и неразличимы по форме без знания формата.
- Конфигурация шаблона (листы/строки/ячейки, параметры) хранится одним JSON-документом в таблице
  `report_templates` — набор возможных полей/связей динамический и выводится из схемы БД, поэтому
  жёсткая реляционная схема под конструктор отчётов дублировала бы её и требовала бы отдельной
  миграции на каждый новый тип ячейки.
- **`frontend-vue/src/views/ReportGridEditorView.vue`** (.xlsx) и **`ReportDocxEditorView.vue`**
  (.docx) — визуальные редакторы содержимого шаблона в браузере: листы/колонки/строки и ячейки с
  выделением/объединением (xlsx) или блоки заголовок/абзац/разрыв/таблица (docx). Поля БД
  вставляются кликом по select'у «Вставить поле» — не drag-and-drop, как было в удалённом
  vanilla-варианте: тот же результат, но надёжнее тестируется и доступнее с клавиатуры. Оба
  редактора подключены к живому предпросмотру и истории версий шаблона. Подробности — в
  [`frontend-vue/README.md`](frontend-vue/README.md).

### Зависимости backend

`backend/requirements.txt`, `requirements-dev.txt` и `requirements-build.txt` задают допустимые диапазоны версий; **точные
версии с хешами** зафиксированы в `backend/requirements.lock` (runtime), `backend/requirements-dev.lock` (runtime + тесты и
анализ) и `backend/requirements-build.lock` (runtime + PyInstaller для сборки EXE). Docker-образ, CI и сборка EXE
(`installer/build_windows.bat`) ставят пакеты из lock-файлов (`pip install --require-hashes -r ...`), поэтому сборка завтра даёт те
же версии, что сегодня, а подмена пакета на PyPI не пройдёт проверку хеша. Версии общих пакетов во всех трёх lock-файлах
одинаковы: в EXE попадает ровно то, что тестируется в CI. Lock универсальный (Linux, Windows, macOS), Python 3.12. Скрипт
сборки EXE не обновляет `pip` отдельно (версия из venv Python 3.12 понимает `--require-hashes`, а нужная версия закреплена
в самом `requirements-build.lock`) и не удаляет лишние пакеты из уже существующего `.venv`: для воспроизводимой сборки удалите
каталог `.venv` перед запуском.

Обновление после правки `requirements*.txt` (или чтобы подтянуть свежие версии в пределах диапазонов):

```bash
pip install uv
cd backend
uv pip compile requirements.txt       --universal --generate-hashes --python-version 3.12 -o requirements.lock       --no-header
uv pip compile requirements-dev.txt   --universal --generate-hashes --python-version 3.12 -o requirements-dev.lock   --no-header
uv pip compile requirements-build.txt --universal --generate-hashes --python-version 3.12 -o requirements-build.lock --no-header
# подтянуть новые версии: добавьте --upgrade (или --upgrade-package <имя> для одного пакета), затем прогоните тесты
```

CI проверяет, что lock-файлы актуальны (пересборка не даёт diff), запускает `pip-audit` по `requirements.lock` (блокирует сборку)
и по `requirements-build.lock` (только сообщает: PyInstaller и его хуки иногда дают замечания, не относящиеся к рантайму).
Те же проверки выполняет `installer/build_windows.bat` при сборке EXE, а job `build-windows` гоняет этот скрипт на windows-latest.
Кроме того, CI запускает `bandit -r backend/app -ll` — статический анализ безопасности собственного кода (срабатывания среднего и
высокого уровня блокируют слияние; неактуальные помечены в коде `# nosec Bxxx # пояснение`).

**Цепочка поставок.** Базовые образы `backend/Dockerfile` закреплены по digest (`python:3.12-slim@sha256:…`), поэтому образ,
собранный завтра, состоит из тех же слоёв, что проверенный сегодня. Тег оставлен для читателя и Dependabot: файл
`.github/dependabot.yml` включает еженедельные PR на обновление pip, npm, базовых образов (тег и digest вместе) и действий GitHub
Actions (они закреплены по SHA). PR с обновлением Python-зависимости покажет красный шаг «Lock-файлы backend актуальны», пока
lock не пересобран командами выше. Digest вручную: `docker buildx imagetools inspect python:3.12-slim` (строка `Digest`).

Dependabot **не предлагает** смену версии Python в образе и мажорное обновление TypeScript (в `dependabot.yml` для них задан `ignore`): CI,
lock-файлы и тесты идут на Python 3.12, а TypeScript 7 пока не ставится из-за peer-зависимостей `vue-tsc` и `typescript-eslint`. Исправления безопасности для
закреплённых линий приходят обновлением digest того же тега (`python:3.12-slim`, `node:26-slim`) и патч-обновлениями. Node (LTS 26, поддержка до 30.04.2029) не заблокирован:
образ и CI обязаны жить на одной версии (`test_the_pinned_images_match_the_versions_ci_runs_on` сверяет `FROM` в Dockerfile с `node-version` и `python-version` в `ci.yml`), поэтому PR Dependabot
на новую линию Node красный, пока `node-version` в `ci.yml` не поднят той же миграцией. Смена версии Python или Node — отдельная миграция (Dockerfile, `ci.yml`, lock-файлы и тесты вместе).

**`npm audit` при сборке EXE.** `npm ci` в `installer/build_windows.bat` печатает итог `npm audit` по всему дереву, включая dev-инструменты
(ESLint, Vitest), хотя блокирующий gate — и в CI, и следом за `npm ci` в том же скрипте — смотрит только runtime-зависимости (`npm run audit:gate` — `npm audit --omit=dev`, уровень high и выше,
с явным списком исключений в `frontend-vue/scripts/audit-gate.mjs`: id advisory, причина и срок; сейчас список пуст (исключение для `picomatch`,
GHSA-fc5q-39xc-vjpf, действовавшее с 2.160.0, снято: advisory отозван 2026-11-18); подробности — `frontend-vue/README.md`, «Аудит зависимостей»). В 2.159.0 сборка
показывала 12 замечаний уровня moderate — два пакета в цепочках `typescript-eslint` и `@vue/test-utils` → `js-beautify`: `minimatch`
(GHSA-g3hv-75wg-m249, отказ в обслуживании при разборе шаблона) и `glob` (GHSA-3g3m-2fjr-6pw4, обход отмены через `AbortSignal`). В
собранный интерфейс (`dist/`) они не попадают. Закрыто блоком `overrides` в `frontend-vue/package.json` (`minimatch` `^11.0.8`, `glob`
`^14.0.6`): исправленные версии есть, но родительские пакеты ещё требуют прежние диапазоны. Блок нужно убрать, когда `typescript-eslint`
и `js-beautify` сами перейдут на исправленные версии (проверка: удалить блок, `npm install`, `npm audit`). `npm audit fix --force` не
используйте: он «исправляет» понижением `typescript-eslint` до 8.36.0, `eslint-plugin-vue` до 10.2.0 и `@vue/test-utils` до 2.4.11.

## Известные ограничения и заметки

- EXE-вариант — однопользовательский локальный режим; для одновременной работы нескольких
  сотрудников по сети используйте серверный вариант (Docker + PostgreSQL). С 2.61.0 это не жёсткое
  ограничение, а настройка по умолчанию: аутентификацию можно включить и в EXE-варианте
  («Настройки → Аутентификация»), если несколько человек работают с одним и тем же файлом БД. С 2.150.0
  подключение к EXE с других компьютеров открывается в `infra_registry.toml` (`allowed_clients`), см.
  [«Запуск как EXE»](#запуск-как-exe-windows).
- **SQLite и порт в двух ролях.** На PostgreSQL строки портов блокируются на время записи подключения (`SELECT … FOR UPDATE`), поэтому два
  одновременных запроса не могут занять один порт в разных ролях. На SQLite (EXE) блокировки строк нет: файл блокируется лишь на время самой
  записи, а проверка «порт свободен» читает без блокировки. Дубли в одной роли (источник — источник, назначение — назначение) ловят уникальные
  индексы и там, а случай «порт — назначение в одном подключении и источник в другом» при двух параллельных запросах база не отклонит. Для одного
  пользователя риск мал; если с одним файлом БД работают несколько человек одновременно, используйте серверный вариант (Docker + PostgreSQL).
- **Запускайте один процесс uvicorn** (без `--workers N` и без нескольких реплик приложения за балансировщиком). Часть состояния хранится
  в памяти процесса и не разделяется между процессами: троттлинг входа (счётчики неудач по паре «адрес + логин» и по адресу), кэш флага
  «аутентификация включена» (до 2 секунд) и признак однократного предупреждения о заголовках прокси. При нескольких процессах лимит
  неудачных входов умножается на число процессов, а переключение аутентификации в настройках становится видно на остальных процессах
  с задержкой кэша. Блокировка учётной записи, сессии и журнал аудита лежат в БД и от числа процессов не зависят. `backend/Dockerfile`
  запускает именно один процесс (`exec uvicorn app.main:app …`).
- **Сессии.** Срок сессии фиксирован (`INFRA_REGISTRY_SESSION_TTL_HOURS`, 12 часов от входа) и не продлевается активностью; отдельного
  таймаута простоя нет. У одного пользователя не более 20 действующих сессий: при входе сверх предела удаляются самые старые его
  сессии (на других пользователей это не влияет).
- **Записи с неизвестным `owner_type` остаются в базе навсегда.** Открытые порты, ПО и IP-адреса ссылаются на владельца парой
  (`owner_type`, `owner_id`). Миграция `7c3d9a5e1b24` один раз удалила потомков, у которых тип известен, а владельца с таким id нет, и поставила
  триггеры на удаление владельцев. Строки, у которых сам `owner_type` не входит в известные значения, она не трогает: это не «потерянный владелец»,
  а ошибка данных (ручная правка, импорт). Приложение их не удаляет и не исправляет; `GET /api/v1/integrity` показывает их с причиной
  `reason: unknown_owner_type` (`ok: false`), а чистят их вручную после проверки, чья это запись.
- **Настройки читаются один раз, при импорте `app.config`.** Окружение разбирает неизменяемый объект `Settings` (`Settings.from_env()`); прежние имена
  модуля (`config.APP_DATA_DIR`, `config.ALLOWED_HOSTS` и т. д.) — псевдонимы его значений. Переменная окружения, выставленная после первого импорта
  приложения, не подействует: `launcher.py` выставляет окружение через `apply_environment()`, которая при нарушении порядка падает с `RuntimeError`, а не молча
  работает с чужими настройками. Импорт `app.config` каталогов не создаёт: каталоги данных и отчётов создаёт `ensure_data_dirs()` — при старте приложения
  (lifespan), в `launcher.py` и в `alembic/env.py` (поэтому `alembic upgrade head` в `docker-entrypoint.sh` и при локальном запуске работает на чистом
  каталоге данных до первого старта приложения). Скрипту, которому нужны каталоги, нужно вызвать `ensure_data_dirs()` самому.
- `backend/alembic/README` — служебный файл, сгенерированный самим Alembic, и не относится к
  документации приложения.
- **Alembic-миграции и PyInstaller:** `alembic/env.py` и `alembic/versions/*.py` в EXE грузятся как данные и импортируются самим
  Alembic уже после старта, поэтому PyInstaller не видит их импортов. Модули `app.*`, которые они импортируют, попадают в сборку
  потому, что `infra_registry.spec` включает в `hiddenimports` весь пакет `app` (обходом каталога `backend/app`, см.
  `collect_app_modules`) — вручную ничего перечислять не нужно. Прежний `collect_submodules('app')` при сборке из корня
  репозитория возвращал пустой список (в `sys.path` нет `backend/`), из-за чего EXE падал с
  `ModuleNotFoundError: No module named 'app.alembic_filters'`; подробности — в [CHANGELOG.md](./CHANGELOG.md). Падение проявляется
  только в собранном EXE, не в Docker и не при обычном запуске. Правило держит `tests/test_pyinstaller_spec.py`: итоговый
  `hiddenimports` (выполняется сам `.spec`, PyInstaller для теста не нужен) обязан покрывать все модули `backend/app` и все `app.*`,
  которые импортирует `env.py` или любая миграция (на верхнем уровне или внутри функций).
- **Обычный прогон тестов строит схему не миграциями.** По умолчанию `tests/conftest.py` создаёт схему БД
  из текущих определений моделей (копия шаблона, собранного `Base.metadata.create_all()`) — быстро, но
  расхождение между моделью и тем, что реально накопится в БД после `alembic upgrade head` на
  продовой истории миграций, этим прогоном не видно (см. запись 2.43.0 — так `information_systems.name`
  потеряло UNIQUE на несколько миграций и ни один тест этого не заметил). Страхуют от этого
  тест-страж `tests/test_migrations_match_models.py` (цепочка миграций на пустой базе сверяется с моделями; падает при любом
  новом расхождении) и режим `INFRA_REGISTRY_TEST_SCHEMA=migrations` (весь набор на схеме из миграций, в CI — job
  `test-postgres-migrations`). Миграции, которые перестраивают таблицы или работают с накопленными данными, всё равно
  стоит проверять на копии реальной базы: при `batch_alter_table()` на SQLite смотрите итоговую DDL (`sqlite_master`), а
  не только зелёный pytest.
- **PostgreSQL: цепочка миграций Alembic проходит на пустой базе** (с 2.156.0; проверено на PostgreSQL 16). Раньше
  `alembic upgrade head` на чистом томе падал, и контейнер из `docker-compose.yml` не стартовал. Исправлено в девяти
  миграциях: булевы литералы `1`/`0` в сырых SQL заменены параметрами (`e8c2f1a9b430`, `e7a2c9f4d813`, `8c5d1f7a2b40`,
  `b7f2c1e5a904`), для `6f4b2c8d1a90` и `c9a4e7d2f610` добавлены ветки PostgreSQL вместо пересборки таблицы сырым
  SQLite-DDL (внешний ключ и уникальность меняются на месте), у `f4a29c7e1d60` убран алиас в `HAVING` и повторное
  ограничение уникальности, у `c4a91e6f2b83` и `d8e35a1c7f60` `DateTime(timezone=True)` заменён на `DateTime()` (в
  SQLite DDL тот же, в PostgreSQL столбцы стали `TIMESTAMP`, как в моделях). Путь SQLite не менялся.
  **Что проверено:** `tests/test_migrations_postgres.py` (пустая база доходит до единственного head, повторный `upgrade`
  ничего не меняет, все таблицы и колонки моделей на месте, уникальность и внешние ключи моделей действуют, VLAN
  уникален в пределах домена, ветки с данными двенадцати миграций, которые переносят строки или удаляют их:
  `e8c2f1a9b430`, `e7a2c9f4d813`, `d8e35a1c7f60`, `b3f7a2c91d54`, `d5a8c3e7b196`, `8c5d1f7a2b40`, `944bd490d967`,
  `a1b7c9d3e502`, `c4e8a7d91b20`, `38e9b2624a53`, `d7a3f1c8b254`, `e9b4c2a7d136`), весь набор тестов на схеме из миграций (job
  `test-postgres-migrations`) и живой запуск приложения на пустой базе (`backend/tests/tools/pg_app_smoke.py`: `alembic
  upgrade head`, `uvicorn`, создание данных по API, Excel-отчёт).
  **Чего это не гарантирует.** У остальных миграций, которые что-то пишут в базу (засев справочников, простые `UPDATE` и
  заполнение новых колонок), отдельных тестов на строки в PostgreSQL нет: их проходит цепочка на пустой базе. Статический
  просмотр их SQL не нашёл типичных для SQLite конструкций (`IS :параметр`, `INSERT OR`, `= 1` для булевых полей, функции
  даты SQLite; `PRAGMA` стоят под проверкой диалекта), но это просмотр, а не проверка. Тесты ветвей с данными строят
  строки старой схемы сами, а не берут настоящую базу: на
  накопленной продовой истории могут встретиться сочетания, которых там нет. Поэтому перед `alembic upgrade head` на
  PostgreSQL с реальными данными делайте копию базы. Один дефект такая проверка уже нашла: `c4e8a7d91b20` искала запись
  каталога ОС условием `version IS :version`, а PostgreSQL принимает после `IS` только `NULL`/`TRUE`/`FALSE`/`DISTINCT FROM`,
  и миграция падала на первой же базе с заполненным свободным текстом ОС (на SQLite и пустой базе — нет). Теперь это два
  запроса (`IS NULL` и `= :version`), тест — `test_free_text_os_moves_into_the_catalog_and_repeats_share_one_entry`. Если у вас
  PostgreSQL уже упал на этой ревизии, ничего не потеряно (DDL в PostgreSQL транзакционен, неудавшийся `upgrade`
  откатывается целиком, база остаётся на ревизии, с которой он начался): после обновления приложения повторите
  `alembic upgrade head`. Модели и миграции больше
  не расходятся: список допустимых расхождений в `tests/test_migrations_match_models.py` (`EXPECTED_DRIFT`) пуст, а тест
  падает при любом новом (прежнее расхождение — необязательные `created_at`/`updated_at` — устранила миграция
  `a7d3f1c8e925`).
  Устаревшие `os_name`, `os_version`, `virtualization_platform_id` и таблица `virtualization_platforms` удалены миграцией
  `e9b4c2a7d136`, а `connection_type_id`/`device_type_id` стали обязательными (`d7a3f1c8b254`): обе останавливаются с понятной
  ошибкой, не меняя базу, если в ней есть строки без значения или данные, которых нет в каталоге ОС, — исправьте данные и
  повторите `alembic upgrade head` (на SQLite для второй нужна версия ≥ 3.35). `test_migrations_postgres.py` следит за тем,
  чтобы остатки схем не мешали вставкам. Порядок
  сортировки по тексту в PostgreSQL зависит от локали базы (в `en_US` порт `eth0` стоит перед `Gi0/1`, в SQLite — после),
  пустые значения в выдаче отчёта идут первыми на обоих движках (`ORDER BY … IS NULL DESC`).
- **Тесты backend идут и на SQLite, и на PostgreSQL.** Job `test-postgres` в CI выполняет весь набор на PostgreSQL 16
  (`INFRA_REGISTRY_TEST_DATABASE_URL`; схема создаётся из моделей, между тестами таблицы очищаются), job
  `test-postgres-migrations` — тот же набор на схеме, собранной цепочкой миграций (`INFRA_REGISTRY_TEST_SCHEMA=migrations`),
  и затем живой запуск приложения. Локально:
  `INFRA_REGISTRY_TEST_DATABASE_URL=postgresql+psycopg://user:pass@localhost:5432/infra_test pytest` (к этой команде
  добавьте `INFRA_REGISTRY_TEST_SCHEMA=migrations` для схемы из миграций). Тесты с пометкой `@pytest.mark.sqlite_only` в
  этом режиме пропускаются, а с `@pytest.mark.postgres_only` (например, `test_migrations_postgres.py`) выполняются только в нём.
  Для воспроизведения CI создавайте базу с локалью `en_US.UTF-8`, как у образа `postgres:16`: сортировка текста зависит от неё.
  **Что учитывать при написании тестов с БД.** SQLite прощает то, что PostgreSQL отвергает или делает иначе, поэтому тест,
  зелёный локально, может упасть в `test-postgres`:
  - не кладите в БД через ORM значения, которые PostgreSQL не хранит. Главный пример — NUL-байт `\x00` в текстовых полях
    (`DataError: PostgreSQL text fields cannot contain NUL (0x00) bytes`; так упал `test_structural_appendix.py` в 2.149.0).
    Такой вход проверяйте unit-тестом функции без БД, а в тесте с БД берите значение, которое хранится на обоих движках
    (например, `\x08` вместо `\x00`);
  - порядок строк, блокировки `FOR UPDATE`, частичные индексы и типы ведут себя иначе (см. комментарий к job в
    `.github/workflows/ci.yml`): тест, зависящий от порядка, должен задавать его явно (`ORDER BY`/сортировка), а не
    полагаться на порядок вставки;
  - если тест трогает схему, ограничения или сырой SQL, прогоните его локально на PostgreSQL (команда выше) до слияния.

- **Экспорт диаграммы в `.vsdx` (2.64.0) — не точная копия `.svg`/`.drawio`.** Библиотека `vsdx`
  устроена как редактор уже существующего файла, а не конструктор объектной модели с нуля;
  геометрия узла воспроизводится копированием готовой фигуры-прямоугольника из встроенного
  шаблона пакета. Размер шрифта подписей (11 у узлов, 9 у связей — как в `.svg`/`.drawio`, через ShapeSheet-секцию

  портов (отдельные фигуры 4×6 вдоль нижней грани, связь начинается над своей засечкой — как в `.svg`/`.drawio`) в `.vsdx`
  есть; цвет текста не задаётся (подпись остаётся чёрной, как в стиле шаблона). Одно сознательное упрощение:

    встраивается как отдельная фигура-оверлей поверх основной через `ForeignData`/`Rel`,

    видимой иконки по-прежнему есть по цвету заливки (`shape.fill_color`, находка №1). Засечки и

  `.vsdx` рисуются не поверх всей фигуры узла, как на канвасе, а отдельной плиткой в верхней части
  узла (тёмный фон, иконка вписана с сохранением пропорций) — нижняя полоса высотой

  цвет текста шаблонной фигуры (см. пункт выше), а без этого белая подпись поверх

- **Экспорт `.vsdx` тяжелее остальных, поэтому ограничен по параллелизму** (код-ревью r3, A-06). Библиотека `vsdx` при каждом
  копировании шаблонной фигуры заново обходила все фигуры страницы (рост квадратичный: 160 устройств — 13 с). Теперь копирование
  идёт без повторного обхода (`_ShapeTemplate` в `backend/app/services/diagram_export/vsdx.py`, результат совпадает с
  `Shape.copy()` байт в байт — тест-страж `test_shape_template_copy_is_identical_to_library_copy`), рост линейный: 120 устройств
  и 150 подключений — около 0,5 с, а с 24 засечками на каждом устройстве — около 2,5 с (`.svg` — единицы мс, `.drawio` — до 0,2 с).
  Экспорт остаётся самым тяжёлым по процессору, а эндпоинт синхронный и работает в пуле потоков, поэтому лимит сохранён:
  одновременно выполняется не больше двух экспортов `.vsdx`, третий запрос сразу получает `503` с `Retry-After: 10`
  (клиент повторяет позже). `.svg` и `.drawio` лимит не затрагивает. Обход обеспечивает `HEAVY_EXPORT_FORMATS` в
  `backend/app/api/diagrams.py`. Дополнительно (код-ревью r3, ИА-01 и ИА-07):
  - **потолок размера** — диаграмма больше `MAX_VSDX_NODES` (1000 узлов; замер: ≈19 мс на узел, 1000 узлов — около 19 с) получает `422`
    с советом скачать `.svg`/`.drawio` или сузить фильтр, не занимая слот;
  - **таймаут** — рендер идёт в отдельном процессе (`services/vsdx_process.py`) и убивается через 60 с: ответ `504`, слот свободен,
    а не занят до тех пор, пока рендер сам закончится; тот же процесс не даёт библиотеке `vsdx` засорять stdout сервера
    (≈13 строк на узел и столько же на засечку порта);
  - **кэш** — готовый файл хранится в памяти процесса (16 последних) под отпечатком самого графа: повторное скачивание того же графа не занимает
    слот и не запускает рендер, а правка устройства, подключения или раскладки даёт другой отпечаток, поэтому устаревший файл не отдаётся.
  Цена изоляции — около 0,7 с на запуск процесса при каждом непопавшем в кэш экспорте `.vsdx`; в Windows-EXE для этого `launcher.py` вызывает
  `multiprocessing.freeze_support()` (вживую в EXE не проверялось).

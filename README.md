# РИС — Реестр ИТ-инфраструктуры

[![CI](https://github.com/MrGAVER/IT-Infrastructure-Report/actions/workflows/ci.yml/badge.svg)](https://github.com/MrGAVER/IT-Infrastructure-Report/actions/workflows/ci.yml)

Приложение для учёта информационных систем, физических устройств, сетевой инфраструктуры,
виртуальных машин, контейнеров и программных активов организации с выгрузкой регламентированного
Excel-отчёта из 4 листов (перечень ИС, инвентаризация физических устройств, организация
подключений, организация управления ВМ).

Стек: **FastAPI + SQLAlchemy + Alembic** на бэкенде, **Vue 3 + TypeScript + Vite** — фронтенд
(см. [Фронтенд](#фронтенд)), **SQLite** (локально/EXE) или **PostgreSQL** (Docker/сервер)
в качестве СУБД, выгрузка отчётов через **openpyxl**.

## Возможности

### CRUD по всем сущностям

Единый REST CRUD реализован для всех основных сущностей БД: организации, подразделения, структурные
единицы, здания, помещения, стойки, типы устройств/производители/модели, физические устройства,
информационные системы (и их подразделения, IP, протоколы), интерфейсы и IP интерфейсов, VLAN и
привязки VLAN, физические подключения, среды виртуализации, виртуальные машины и их IP, контейнеры,
программные активы, ПО физических устройств и ВМ, связи ИС с устройствами/ВМ/контейнерами, открытые
порты, журнал аудита.

Для каждой сущности доступен единый набор эндпоинтов:

```text
GET    /api/v1/resources/{resource}
GET    /api/v1/resources/{resource}/{id}
POST   /api/v1/resources/{resource}
PUT    /api/v1/resources/{resource}/{id}
DELETE /api/v1/resources/{resource}/{id}
GET    /api/v1/resources/{resource}/schema
```

Поддерживаются полнотекстовый поиск (`?q=`), точная фильтрация по полю (`?field=value`),
`offset`/`limit`, проверка уникальности и обработка внешних ключей. Удаление объекта, на который
есть ссылки, блокируется с HTTP 409 и понятным сообщением о том, где именно он используется.

### Структурные единицы

Справочник организационных структурных единиц (филиал, площадка, подразделение и т. п.) с
иерархией через родительскую единицу — тот же паттерн, что и у подразделений. Адрес размещения
физического оборудования (здание) дополнительно связывается со структурной единицей: у каждого
здания есть необязательное поле «Структурная единица», а через него — у всего оборудования,
размещённого в этом здании.

Эта связь используется при формировании отчётов (регламентированного и построенных в конструкторе
на сущностях реестра): отчёт можно ограничить оборудованием одной, нескольких или сразу всех
структурных единиц — выбор родительской единицы автоматически захватывает вложенные, без
необходимости отмечать каждую по отдельности. См. «Отчёт Excel» → «Фильтр по структурным единицам».

### Интерфейс

- Динамические CRUD-формы, построенные по схеме конкретной таблицы: текстовые/числовые/большие
  текстовые поля, Boolean как «Да/Нет», выпадающие списки для внешних ключей.
- Быстрое добавление справочных значений прямо из формы (кнопка «+»), без перехода в раздел
  справочников.
- Отдельные редакторы для сложных сущностей: интерфейсы физического устройства (с генерацией по
  шаблону имени/номера), VLAN устройства, IP-адреса и открытые порты ВМ, детали информационной
  системы (подразделения, протоколы, источники размещения, оборудование/ПО).
- Единый каталог оборудования «Производитель → Тип устройства → Модель».
- Сквозной поиск по нескольким сущностям сразу (устройства, ИС, ВМ, интерфейсы, IP интерфейсов,
  IP ВМ) с резолвингом IP-адреса до владеющего устройства/ВМ.
- Импорт физических устройств из CSV.
- Журнал аудита (последние 300 действий, read-only раздел).
- Сортировка таблиц списков по клику на заголовок, предупреждение о несохранённых изменениях при
  закрытии форм устройства/ИС и вкладки браузера.
- Основные разделы вынесены в левое меню: ИС, устройства, интерфейсы, подключения, ВМ, контейнеры,
  ПО, VLAN, открытые порты, аудит и справочники.

### Миграции Alembic

`Base.metadata.create_all()` не используется как механизм создания схемы — схема БД создаётся и
обновляется только миграциями:

```bash
cd backend
alembic upgrade head
```

Новая миграция после изменения моделей:

```bash
cd backend
alembic revision --autogenerate -m "описание изменения"
alembic upgrade head
```

Откат последней миграции:

```bash
alembic downgrade -1
```

В Docker миграция выполняется автоматически перед запуском Uvicorn, в EXE — автоматически при
старте приложения.

### Отчёт Excel

`POST /api/v1/reports/inventory` формирует XLSX-файл из 4 листов согласно техническому заданию
(см. раздел [«Отчёт Excel»](#отчёт-excel)). Генерация выполняется из нормализованной БД с
объединением связанных объектов; для листов включены перенос текста, автофильтр, закрепление
заголовка и автоматическая ширина колонок.

### Конструктор произвольных отчётов

Помимо фиксированного 4-листового Excel-отчёта, приложение позволяет пользователю самостоятельно
собирать **произвольные отчёты xlsx и docx** — без программирования, через веб-интерфейс (пункт
меню «🧩 Конструктор отчётов»). Подробности — в разделе [«Конструктор
отчётов»](#конструктор-произвольных-отчётов).

### Аутентификация и авторизация

По умолчанию выключена (`AuthSettings.enabled = False`) — однопользовательский локальный режим,
`/api/*` открыт без токена, поведение не отличается от версий до 2.61.0. Включается на экране
«Настройки» (нужен хотя бы один пользователь с ролью «Администратор» — завести его можно, пока
переключатель ещё выключен). Две роли: `admin` (полный доступ, управление пользователями и самим
переключателем) и `viewer` (только чтение). Пароли — `pbkdf2_hmac(sha256)`, токены сессий —
непрозрачные (в БД хранится только их sha256-хеш), блокировка учётной записи после серии неудачных
попыток входа. Любая роль может сменить свой собственный пароль и посмотреть/завершить свои же
активные сессии (раздел «Моя учётная запись», см. 2.62.0), не дожидаясь администратора. Все
проверки, критичные для «не остаться без единого администратора» и учёт неудачных попыток входа,
устойчивы к нескольким одновременно пишущим процессам backend за общей БД — актуально для
серверного варианта (см. 2.63.0). Подробности реализации — в записях
[2.61.0](#история-изменений)/[2.62.0](#история-изменений)/[2.63.0](#история-изменений) истории
изменений.

## Быстрый старт

### Docker

Перед первым запуском скопируйте `.env.example` в `.env` и задайте свой `POSTGRES_PASSWORD`
(без него `docker compose` откажется стартовать):

```bash
cp .env.example .env
# отредактируйте .env
docker compose up --build
```

Переменные окружения `.env` (все опциональны, кроме `POSTGRES_PASSWORD`):

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `POSTGRES_PASSWORD` | — (обязательна) | пароль пользователя БД |
| `POSTGRES_DB` / `POSTGRES_USER` | `infra_registry` / `infra` | имя БД и пользователя |
| `INFRA_REGISTRY_CORS_ORIGINS` | `*` | список разрешённых origin'ов через запятую для CORS; `*` подходит для локальной сети |

Открыть:

```text
http://localhost:8000        # UI (Vue)
http://localhost:8000/docs
```

### Локальный запуск без Docker

Требуется Python 3.12+ и Node.js 20+ (для сборки UI):

```bash
python -m venv .venv
# Windows
.venv\Scripts\activate
# Linux/macOS
source .venv/bin/activate

pip install -r backend/requirements.txt

cd frontend-vue
npm ci
npm run build   # собирает dist/, который раздаёт бэкенд на '/' (см. frontend-vue/README.md)
cd ..

cd backend
alembic upgrade head
uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Если пропустить сборку `frontend-vue`, `/` ответит понятной 500-ошибкой с
подсказкой собрать фронтенд (`npm run build`).

### Запуск как EXE (Windows)

`InfraRegistry.exe` — самостоятельное Windows-приложение с локальным веб-интерфейсом, не требующее
интернета, PostgreSQL или Docker. При запуске оно:

1. создаёт/использует каталог рядом с самим EXE;
2. создаёт или обновляет SQLite БД `infra_registry.db`;
3. автоматически выполняет `alembic upgrade head`;
4. запускает локальный FastAPI/Uvicorn-сервер;
5. открывает браузер на `http://127.0.0.1:8000`.

**Хранение данных.** База данных SQLite и каталог отчётов хранятся **рядом с исполняемым файлом**,
а не внутри него:

```text
InfraRegistry.exe
infra_registry.db
reports\
```

Это позволяет переносить каталог приложения целиком вместе с базой, а обновление самого EXE не
удаляет накопленный реестр. Каталог с EXE должен быть доступен для записи текущему пользователю —
приложение создаёт/изменяет `infra_registry.db`, каталог `reports` и выполняет миграции.

**Сборка** выполняется **на Windows** (PyInstaller собирает исполняемый файл под текущую ОС;
сначала собирается основной UI — `installer\build_windows.bat` делает это автоматически,
поэтому требуется установленный Node.js 20+):

```bat
installer\build_windows.bat
```

Результат — `dist\InfraRegistry.exe`.

**Запуск** — двойным щелчком по `InfraRegistry.exe`, либо с параметрами:

```bat
InfraRegistry.exe --port 8010
InfraRegistry.exe --no-browser
```

**Перенос на другой ПК** — достаточно скопировать `InfraRegistry.exe`; при первом запуске
приложение самостоятельно создаст БД и каталоги.

> **Важное ограничение.** EXE-вариант рассчитан на локальную работу одного пользователя. Для
> общего сетевого доступа нескольких сотрудников следует использовать серверный вариант с
> Docker + PostgreSQL.

## Отчёт Excel

Отчёт формируется по техническому заданию и состоит из 4 листов.

**Лист 1. Перечень ИС** — №, наименование и описание ИС, назначение использования, работники и
подразделения, использующие ИС, локализация, оборудование, на котором размещена ИС, протокол и
IP-адрес взаимодействия, применение сертифицированных СКЗИ, признак получения событий в SIEM,
организация внешнего взаимодействия/техподдержки и способ её оказания, описание процесса
функционирования ИС, а также физический сервер/ВМ (контейнер), обеспечивающие работу ИС, с их
IP-адресами.

**Лист 2. Инвентаризация физических устройств ИС** — №, вид устройства (сервер, сетевое
оборудование, средство защиты информации, рабочий ПК администратора), производитель, модель,
серийный номер, системное имя, версия ОС, порт и IP-адрес управления, признак получения событий в
SIEM, количество физических портов, адрес и здание расположения, помещение/место размещения.

**Лист 3. Организация подключений** — №, вид устройства, серийный номер и системное имя, ОС,
физический/логический порт и его IP-адрес, перечень открытых портов с протоколами, VLAN ID/Name,
тип и назначение физической линии связи, а также аналогичный набор колонок для соседнего
подключённого устройства (вид, серийный номер, системное имя, ОС, IP-адрес порта).

**Лист 4. Организация управления ВМ** — название и ОС виртуальной машины, наименование контейнера,
физическое устройство-хост по его системному имени, среда виртуализации и её версия, целевое
назначение ВМ/контейнера, IP-адрес и IP-адрес администрирования, открытые порты с протоколами,
развёрнутые программные активы (1С, веб-сервер, файловый сервер, AD и т. п.).

**Фильтр по структурным единицам.** Перед формированием отчёта (кнопка «Сформировать Excel» на
дашборде, и генерация шаблонов конструктора, построенных на сущностях реестра — см. ниже) можно
ограничить его оборудованием, размещённым в одной, нескольких или всех структурных единицах сразу
(см. раздел «Возможности» → «Структурные единицы»). Без выбора отчёт формируется как раньше, без
ограничения.

## Конструктор произвольных отчётов

Помимо регламентированного 4-листового отчёта (см. выше), приложение включает **конструктор
произвольных отчётов** — модуль, позволяющий пользователю без программирования собрать
собственный отчёт `.xlsx` или `.docx` на основе данных реестра. Открывается пунктом меню «🧩
Конструктор отчётов». Формат `.xlsx` редактируется визуальным **grid-редактором листа** (см.
ниже), формат `.docx` — **блочным редактором документа** (см. ниже).

При обновлении в список шаблонов автоматически добавляются два готовых шаблона:
- **«Регламентированный отчёт — заготовка (4 листа)»** (`.xlsx`) — точное воспроизведение
  содержимого фиксированного отчёта выше (данные и заголовки совпадают 1:1 — проверено тестом на
  реальных данных, не только структурно), но собранное через grid-движок конструктора и открытое
  для дальнейшей правки. Подробности — в записи 2.39.0 в истории изменений ниже и в комментарии в
  начале `backend/app/services/report_seed_templates.py`.
- **«Приложение к структурной схеме (по образцу)»** (`.docx`) — 3 таблицы (назначение линий связи /
  перечень VLAN / перечень телекоммуникационного оборудования) по мотивам структуры документа,
  приложенного пользователем к задаче — не побитовая копия, подробности расхождений в записи
  2.42.0 и в комментарии в начале `backend/app/services/report_seed_word_template.py`.

### Что умеет grid-редактор (.xlsx)

Редактор показывает лист как настоящую таблицу-канвас (строки/колонки/ячейки), а не форму со
списком колонок — состав, положение и оформление каждой ячейки задаются визуально:

- **Перетаскивание полей из палитры прямо на ячейку листа** (drag-and-drop). Палитра строит
  плоский список доступных путей на глубину до двух связей, включая связи «многие-ко-многим»
  через связующие таблицы (например, `is_departments[].department.name` — подразделения ИС).
  Первое поле, перетащенное в строку, автоматически включает для неё повторение (см. ниже) и
  привязывает её к соответствующей сущности.
- **Повторяющиеся строки.** Любая строка листа может быть отмечена как «повторяющаяся» —
  тогда при генерации файла она клонируется по одной физической строке на каждую запись
  выбранной сущности (с опциональным циклическим разворотом по связи «один/многие-ко-многим» —
  например, отдельная строка на каждую ВМ каждого физического сервера — и фильтрами по любому
  доступному пути поля: равно / не равно / содержит / не содержит / не пусто / да·нет).
  Остальные строки — статические (заголовки, титульная часть, произвольный текст).
- **Объединение ячеек** по горизонтали и вертикали (выделение диапазона — клик по первой ячейке,
  Shift+клик по последней) — с проверкой, что вертикальное объединение не пересекает
  повторяющуюся строку.
- **Оформление ячейки**: жирный/курсив/подчёркнутый, рамка, перенос текста, выравнивание по
  горизонтали/вертикали, цвет фона и текста, числовой формат (в т.ч. даты) — сохраняется как
  настоящее форматирование ячейки в итоговом `.xlsx` (не только текст); высота строки при
  необходимости автоматически увеличивается под перенесённый текст (см. запись 2.41.0).
- **Формулы Excel** — ячейка может содержать формулу (`=...`), которую вычислит сам Excel при
  открытии файла; в тексте формулы, как и в статическом тексте, работает подстановка параметров
  (`{{ключ}}`, `{{report_date}}`).
- **Параметры отчёта**, которые пользователь вводит непосредственно перед формированием файла
  (например, «Организация», «Дата отчёта», «Составил»).
- **Живой предпросмотр** — материализованные строки/ячейки (с учётом объединений и оформления)
  можно посмотреть прямо в редакторе, не сохраняя шаблон и не создавая файл.
- Несколько листов на шаблон; шаблоны можно **сохранять, дублировать, смотреть историю версий и
  восстанавливать** предыдущее состояние, удалять.

### Что умеет блочный редактор (.docx)

Документ собирается из блоков сверху вниз, порядок блоков — это порядок содержимого в файле:

- **Заголовок** (уровень 1-6) и **Абзац** (с выравниванием) — текст, в котором работает
  подстановка параметров (`{{ключ}}`, `{{report_date}}`), как и в xlsx.
- **Таблица** — привязывается к сущности реестра (тот же выбор сущности/поля/фильтров/сортировки/
  циклического вывода по связи, что и в xlsx-редакторе, с тем же помощником-подсказкой пути поля);
  колонка — заголовок + один из трёх источников: поле из БД (с разделителем для полей-списков),
  статический текст или № по порядку. Колонки и блоки переставляются кнопками (←/→ и ↑/↓).
- **Разрыв страницы.**
- **Живой предпросмотр** табличных блоков и сохранение/формирование — по общей схеме с xlsx.

### Ограничения текущей версии

- В grid-редакторе (.xlsx) нет многоклеточного выделения мышью (только Shift+клик по паре ячеек),
  undo/redo, копирования ячеек и авто-подбора ширины колонок по содержимому — состав и порядок
  листов/строк/колонок настраивается явными действиями (кнопки +/✕, инспектор ячейки/строки справа).
- В блочном редакторе (.docx) нет drag-and-drop полей на таблицу (путь поля вводится текстом с
  помощником-подсказкой, как в старом xlsx-редакторе до grid) и нет группировки строк таблицы под
  вложенным заголовком (см. пример в описании шаблона «Приложение к структурной схеме» выше) —
  один блок-таблица всегда плоский, на одной сущности.

### Как это устроено технически

- `backend/app/services/report_meta.py` — граф полей и связей (`to_one`/`to_many`) выводится
  **автоматически** из существующих моделей БД (`MODEL_MAP`) через `sqlalchemy.inspection`, без
  ручного описания каждой пары таблиц; при добавлении новой сущности/поля в схему БД конструктор
  подхватывает её без изменений в этом модуле.
- `backend/app/services/report_engine.py` — разбор путей полей, подстановка параметров,
  циклический вывод строк по связи и (для формата `.docx`) структурная валидация блоков документа.
- `backend/app/services/report_grid.py` — grid-движок формата `.xlsx`: валидация листа (позиции и
  объединения ячеек, источники данных повторяющихся строк), материализация конфигурации в
  физические строки/ячейки и рендеринг в настоящий `.xlsx` через openpyxl (стили, объединение,
  числовой формат, формулы), а также предпросмотр без записи файла на диск.
- `backend/app/services/report_render.py` — сборка `.docx` (python-docx: заголовки, абзацы,
  таблицы, разрывы страниц) и предпросмотр блоков документа.
- `backend/app/api/report_builder.py` — REST API: `GET /api/v1/report-builder/entities` (список
  сущностей/полей/связей для UI), CRUD `/api/v1/report-templates` (+ история версий и
  восстановление), `POST /api/v1/report-templates/{id}/generate`, `POST
  /api/v1/report-templates/{id}/duplicate`, `POST /api/v1/report-builder/preview` — валидация и
  предпросмотр диспетчеризуются по `format` шаблона (`xlsx` → `report_grid.py`, `docx` →
  `report_engine.py`/`report_render.py`), поскольку обе структуры конфигурации хранятся в одном
  JSON-поле `config` и неразличимы по форме без знания формата.
- Конфигурация шаблона (листы/строки/ячейки, параметры) хранится одним JSON-документом в таблице
  `report_templates` — набор возможных полей/связей динамический и выводится из схемы БД, поэтому
  жёсткая реляционная схема под конструктор отчётов дублировала бы её и требовала бы отдельной
  миграции на каждый новый тип ячейки.
- **`frontend-vue/src/views/ReportGridEditorView.vue`** (.xlsx) и **`ReportDocxEditorView.vue`**
  (.docx) — визуальные редакторы содержимого шаблона в браузере: листы/колонки/строки и ячейки с
  выделением/объединением (xlsx) или блоки заголовок/абзац/разрыв/таблица (docx). Поля БД
  вставляются кликом по select'у «Вставить поле» — не drag-and-drop, как было в удалённом
  vanilla-варианте: тот же результат, но надёжнее тестируется и доступнее с клавиатуры. Оба
  редактора подключены к живому предпросмотру и истории версий шаблона. Подробности — в
  [`frontend-vue/README.md`](frontend-vue/README.md).

  Подробности состава и статус по экранам — в [`frontend-vue/README.md`](frontend-vue/README.md).

## Модуляризация фронтенда (архив)

Касается только старого vanilla-фронтенда (`frontend/`) — удалён в 2.60.0 вместе с раздачей
`/legacy` (см. «Изменения»), основной и теперь единственный UI (`frontend-vue/`) написан на
Vue-компонентах и в этой модуляризации не нуждался, см. [Фронтенд](#фронтенд). Раздел ниже
сохранён как есть — историческое обоснование решения, актуальное на момент, когда `frontend/`
ещё существовал.

`app.js`/`report_builder.js` были одним файлом каждый — сознательное решение, разобранное предметно
в [`docs/frontend-modularization.md`](docs/frontend-modularization.md): инлайн-обработчики
`onclick=`/`onchange=` (101+ штук) полагаются на глобальную область видимости, поэтому простое
переключение на `type="module"` или фреймворк без сопутствующего рефакторинга рендеринга сломает UI.
Документ рекомендует поэтапное разбиение на несколько обычных `<script>` (без модулей, без
сборщика) начиная с наименее связанных зон, и объясняет, почему переход на фреймворк сейчас не
оправдан.

Предпосылка из документа — «сначала хотя бы smoke-тесты фронтенда» — выполнена (см.
`frontend/tests/app.smoke.test.js` в разделе [Тестирование](#тестирование)). Сделано девять шагов
разбиения, каждый — отдельный коммит, проверенный полным набором тестов:

1. `frontend/static/core.js` — базовая инфраструктура без исходящих зависимостей (константы
   справочников меток, кеш GET-запросов, единый разбор ошибок API, toast-уведомления, обёртка над
   `fetch()`, `esc()`/`formatValue()`/`lookupLabel()`) — единственная часть исходного файла, ничего
   не вызывающая из кода ниже неё.
2. `frontend/static/vm-editors.js` — общая фабрика редактора вложенных списков
   (`attachNestedListEditor()`) и все построенные на ней редакторы для ВМ/устройства (IP-адреса ВМ,
   открытые порты ВМ и устройства, программные активы ВМ). Должен грузиться раньше `app.js` — тот
   на верхнем уровне вызывает `attachNestedListEditor(...)` для `deviceVlanEditor`.
3. `frontend/static/csv-import.js` — импорт устройств из CSV (`csvParse`, `openCsvImport` и т.п.),
   был уже помечен в исходном коде комментарием как «полностью автономный оверлей».
4. `frontend/static/connections.js` — форма создания/редактирования подключения между портами
   устройств (`connectionState`, `openConnectionForm()`, `saveConnectionForm()` и т.п.).
5. `frontend/static/device-interfaces.js` — редактор физических интерфейсов устройства (карточки
   портов, генерация по шаблону, массовое редактирование, IP-адреса интерфейса) и редактор VLAN
   устройства (`deviceVlanEditor`), плюс форма одиночного интерфейса.
6. `frontend/static/information-systems.js` — форма/редактор информационной системы
   (`openInformationSystemForm`, вложенные списки подразделений/протоколов/источников/мест
   размещения) и её сохранение (`saveInformationSystemForm`). Самый крупный оставшийся
   самодостаточный блок на момент выделения — состояние держится на `window.isEditor`.
7. `frontend/static/vlan.js` — вся предметная область VLAN, собранная из трёх разных мест исходного
   `app.js`: экран «VLAN» (дашборд + массовое назначение), форма отдельного VLAN, форма типа
   устройства (управляет разрешёнными для типа VLAN) и запуск синхронизации VLAN-домена.
8. `frontend/static/audit-log.js` — раздел «Аудит»: фильтр по разделу/дате, экспорт в Excel, рендер
   журнала (`renderAuditLog()` и связанные `auditQueryParams`/`setAuditFilter`/`resetAuditFilters`/
   `exportAuditLog`).
9. `frontend/static/search.js` — сквозной поиск (`globalSearch`, `renderGlobalSearchResults`):
   устройства, ИС, ВМ, интерфейсы и IP-адреса из шести разных таблиц, каждая резолвится к своему
   владельцу для перехода по клику.

Порядок в `index.html`: `core.js` → `vm-editors.js` → `device-interfaces.js` →
`information-systems.js` → `vlan.js` → `audit-log.js` → `search.js` → `csv-import.js` →
`connections.js` → `app.js` → `report_builder.js`, все — обычные `<script>` в общей глобальной
области видимости (не модули) — инлайн-обработчики в HTML продолжают работать без изменений.
`app.js` сократился с ~980 до ~305 строк. Состояние, используемое только внутри одного нового
модуля (`auditFilters`, `vlanBulkAssignOpen`), объявляется через `var`, а не `let`/`const`:
let/const верхнего уровня не становится свойством `window`, из-за чего тесты не могли бы прочитать/
подменить его через `win.X` (см. историю коммита 2219cd5, где это уже один раз ловилось как баг).
Дальнейшее разбиение (маршрутизация/список/generic-форма, quick-add модалки) — на будущее: эти
зоны тесно переплетены через общие state-переменные (`resource`, `schema`, `editingId`) и требуют
более осторожного подхода.

## История изменений

Ниже — сводная хронология версий, собранная из всех ранее отдельных `README_*.md` файлов проекта.

### 2.1 — исправление 404 на `/` в EXE
Путь к `frontend` теперь передаётся launcher-ом в EXE явно (`INFRA_REGISTRY_FRONTEND_DIR`), вместо
косвенного определения через расположение `main.py` внутри PyInstaller `_MEIPASS`. `GET /` в EXE
корректно отдаёт `frontend/index.html`.

### 2.2
- В форме физического устройства у полей «Тип устройства», «Производитель», «Модель», «Здание»,
  «Помещение», «Стойка» появилась кнопка быстрого добавления записи `＋` без перехода в справочники.
- Поле «№» ИС и колонка «№» листов 2–3 больше не вводятся вручную — нумерация всегда генерируется
  автоматически при экспорте.

### 2.5
Модель физического устройства однозначно связана с производителем и типом устройства (например,
Huawei 2288 нельзя выбрать как модель коммутатора) — в форме устройства модели фильтруются по
обеим характеристикам.

### 2.8 (ранее также фигурировала как 2.7)
- ОС физического устройства отображается в формате «Наименование + версия».
- Внешние ключи в списках и связях отображаются человекочитаемыми значениями вместо UUID.
- «Порт управления» стал свойством интерфейса; интерфейсы редактируются в едином окне формы
  устройства, с возможностью сгенерировать их по количеству портов (шаблоны `{n}`, `{n0}`).
- У интерфейса появился признак «Управление», используемый при формировании Excel.
- Добавлен атомарный API `PUT /api/v1/devices/{device_id}/interfaces`.

### 2.11
- Добавлены идемпотентные стандартные значения в справочники типов устройств, ОС/гипервизоров и
  скоростей интерфейсов (не удаляют пользовательские записи).
- Поля «Порт управления», «IP управления», «Количество интерфейсов» скрыты из основной формы
  устройства — ведутся в редакторе «Порты / интерфейсы».
- Миграция `f2a9c7d1e530_standard_catalog_values`.

### 2.12 — оптимизация и рефакторинг
- Backend: `main.py` стал минимальной application factory; CRUD, валидации, сериализация и
  инициализация справочников вынесены в `app/services/*`; API разделён на роутеры
  (`system.py`, `resources.py`, `devices.py`); устранён N+1-запрос для списка устройств; добавлены
  индексы на часто используемые FK/поисковые запросы.
- Frontend: CSS и JS вынесены из `index.html` в `app.css`/`app.js`, отдаваемые через `/static`.
- Миграция `3a7c1e5d9b20_performance_indexes.py` (индексы для зданий/помещений/стоек, каталога,
  устройств, интерфейсов/IP, подключений, ОС и ВМ).

### 2.13
- В списках устройств и интерфейсов снова отображаются имена и IP-адреса интерфейсов управления.
- Редактор интерфейса объединён для Dashboard «Интерфейсы» и формы устройства.
- Понятная ошибка `422` вместо SQLite `NOT NULL constraint` при создании подключения без
  выбранных интерфейсов; выбор портов фильтруется по выбранному устройству.

### 2.14.0
- Подключения: явная валидация выбора исходного/конечного устройства и интерфейса.
- Информационные системы: отдельный редактор связанных подразделений, IP, протоколов, устройств,

- Виртуальные машины: гипервизор определяется автоматически по ОС хоста; хостом ВМ может быть

### 2.39.0 — шаблон конструктора с точным воспроизведением регламентированного отчёта

При обновлении (data-миграция `b1f0a2265711`, применяется автоматически как обычная alembic-
миграция и в Docker, и в EXE-сборке) в конструктор отчётов добавляется готовый шаблон
**«Регламентированный отчёт — заготовка (4 листа)»** — те же 4 листа, те же заголовки колонок и,
что важнее, **то же содержимое строк**, что и у фиксированного регламентированного отчёта (кнопка
«Отчёт Excel» на дашборде), но собранный через grid-движок конструктора (`report_grid.py`), то
есть открытый для правки в визуальном редакторе (см. запись 2.38.0 выше).

- **Как достигнута точность 1:1, а не приближение.** Первая версия этой задачи (в рамках этой же
  ветки) пыталась выразить логику `reporting.py` обобщёнными путями полей конструктора (вида
  `a.b[].c`) и упёрлась в принципиальные ограничения этой модели — часть логики оригинала (цепочки
  резервных источников данных, объединение нескольких связей в одну колонку, фильтрация списка по
  вложенному признаку, открытые порты с полиморфным владельцем) обобщённым путём не выражается.
  Решение — `backend/app/services/report_registry_rows.py`: 4 "виртуальные" сущности конструктора
  (без своей таблицы в БД), каждая строка которых считается ДОСЛОВНО ТЕМИ ЖЕ функциями, что и сам
  `reporting.py` (`_is_row_values`/`_device_row_values`/`_connection_row_values_list`/
  `_vm_row_values` — вынесены из `reporting.py` в переиспользуемые функции, поведение исходного
  отчёта не изменилось ни на бит, проверено полным прогоном `test_reporting.py` до и после
  рефакторинга). У виртуальной сущности нет связей для обхода — все поля уже плоские, конструктору
  достаточно взять готовое значение по имени, поэтому обобщённые ограничения путей полей здесь
  просто не участвуют.
- Технически это новая возможность самого grid-движка, не только этого шаблона: сущность в
  конструкторе теперь может быть не только таблицей БД (`MODEL_MAP`), но и "виртуальной" —
  плоским списком уже посчитанных строк от функции-загрузчика (`ReportContext.all_rows()` в
  `report_engine.py` вызывает её вместо `SELECT`). Другие части приложения при желании могут

- Точность проверена не только структурно: `backend/tests/test_report_registry_rows.py::ExactParityTestCase`

### 2.41.0 — фиксы grid-редактора и шаблона по обратной связи пользователя

- **Текст в ячейках сгенерированного `.xlsx` обрезался по высоте строки.** openpyxl, в отличие от
  интерактивного Excel, не пересчитывает высоту строки под перенесённый текст сам — заданная в

  400pt), применяется как `max(заданная высота, расчётная)` — не сжимает то, что задано намеренно,
  но не даёт клетке оказаться меньше, чем нужно для содержимого. Тот же приём "символов на юнит
  ширины", что уже использует сам регламентированный отчёт (`reporting.py: finalize_sheet`) для
  подбора ширины колонок по факту содержимого.
- Заодно расширены колонки шаблона-заготовки, где значения типично длинные (списки через `; `) —

### 2.57.0 — Vue: подсказка с полным текстом при наведении на обрезанные поля (п.3)

  элемента реально обрезано (`scrollWidth`/`scrollHeight` больше `clientWidth`/`clientHeight`

    select не отражают обрезку текста выбранной опции — это ограничение рендеринга контрола

### 2.63.0 — задел на многопроцессный деплой (concurrency-safety)

Последний пункт из «возможных улучшений» 2.62.0 — не полноценный Redis/распределённый кеш (для
однопроцессного локального/EXE-сценария это было бы избыточно), а закрытие конкретных гонок,
которые реально проявляются только при нескольких ОДНОВРЕМЕННО пишущих процессах backend за общей
БД (см. «Быстрый старт» — серверный вариант, Docker + PostgreSQL).

- **Гонка «оба администратора разжалованы одновременно»**: `ensure_not_last_admin` раньше делала
  check-then-act («посчитать активных админов, потом изменить») — классический TOCTOU. Два admin'а
  A и B, каждый на своём процессе, одновременно разжалующие СЕБЯ ИЛИ ДРУГ ДРУГА, оба видели друг
  друга как «ещё есть один admin» и оба проходили проверку → ноль администраторов. Исправлено:
  `SELECT ... FOR UPDATE` по ВСЕМ активным администраторам (не «остальным, кроме текущего» — иначе
  блокировки над A и над B не пересекались бы и гонка сохранялась) перед проверкой и мутацией в
  одной транзакции. На PostgreSQL это реальная блокировка строк; на SQLite — безопасный no-op
  (диалект не рендерит `FOR UPDATE`, проверено эмпирически) — там гонки и так нет, SQLite
  сериализует писателей на уровне файла БД целиком.
- **Атомарный счётчик неудачных попыток входа**: было `user.failed_attempts += 1;
  session.commit()` — read-modify-write в Python. Два параллельных неверных пароля от одного
  пользователя на разных процессах могли прочитать один и тот же счётчик и оба записать n+1
  вместо n+2, теряя попытку из порога блокировки. Заменено на `UPDATE ... SET failed_attempts =
  failed_attempts + 1` одним SQL-запросом — атомарно на уровне БД независимо от числа процессов.
- **Самоочистка `auth_sessions`**: каждый логин (`create_session`) заодно удаляет ВСЕ просроченные
  сессии всех пользователей — без этого таблица только росла (строка убиралась явно лишь при
  logout или попытке использовать именно этот истёкший токен). Это ленивая уборка, не
  cron/планировщик: безопасна при любом числе процессов, поскольку `DELETE ... WHERE expires_at <
  now()` идемпотентен — два процесса, одновременно решившие подчистить одну и ту же строку, друг
  другу не мешают.
- Мёртвый код: `count_active_admins` (некритичный к гонкам подсчёт) удалён — после перехода
  критичных проверок на блокирующую `_lock_active_admins` он больше нигде не вызывался.
- 5 новых тестов (компиляция `FOR UPDATE` на диалекте PostgreSQL, атомарность инкремента, уборка
  просроченных сессий) — сам факт гонки под нагрузкой синхронный SQLite-тест не воспроизводит
  (нужен реальный параллелизм нескольких процессов), поэтому тесты фиксируют защитный SQL и
  наблюдаемое поведение уборки, а не гонку напрямую. Полный прогон: 241 pytest — зелёные.

## Известные ограничения и заметки

- EXE-вариант — однопользовательский локальный режим; для одновременной работы нескольких
  сотрудников по сети используйте серверный вариант (Docker + PostgreSQL). С 2.61.0 это не жёсткое
  ограничение, а настройка по умолчанию: аутентификацию можно включить и в EXE-варианте
  («Настройки → Аутентификация»), если несколько человек работают с одним и тем же файлом БД.
- `backend/alembic/README` — служебный файл, сгенерированный самим Alembic, и не относится к
  документации приложения.
- **Alembic-миграции и PyInstaller:** если новая data-миграция импортирует что-то из `app.services.*`
  ТОЛЬКО внутри своих `upgrade()`/`downgrade()` (а не так, как обычный код приложения — через
  цепочку импортов, достижимую из `main.py`), добавьте этот модуль явной строкой в `hiddenimports`
  в `infra_registry.spec` — `collect_submodules('app')` не всегда достаточно (см. запись 2.40.0
  выше), и падение проявляется только в frozen EXE-сборке, не в Docker/обычном запуске.
- **Тесты не проверяют реальную цепочку alembic-миграций.** `tests/conftest.py` строит схему БД
  через `Base.metadata.create_all()` из текущих определений моделей — быстро, но означает, что
  расхождение между моделью и тем, что реально накопится в БД после `alembic upgrade head` на
  продовой истории миграций, невидимо для pytest (см. запись 2.43.0 — так `information_systems.name`
  потеряло UNIQUE на несколько миграций и ни один тест этого не заметил). При добавлении
  `batch_alter_table()` на SQLite стоит вручную проверять итоговую DDL (`sqlite_master`), а не
  полагаться только на зелёный pytest.
- **CI не запускает собранный Docker-образ, только собирает его** (`docker build`, без
  `docker run`) — баг вида «контейнер падает на старте» (как найденный и исправленный в 2.45.0
  для `BASE_DIR`) не будет пойман автоматически, если появится снова. При правке
  `backend/Dockerfile`, `config.py` или переменных `INFRA_REGISTRY_*` стоит хотя бы раз
  вручную поднять `docker compose up --build` и проверить, что `/` и `/api/v1/health` реально
  отвечают, а не полагаться только на успешную сборку образа.
- **Миграция `38e9b2624a53` (2.64.0) необратимо удаляет данные.** Перед `alembic upgrade head` на
  реальной БД, где уже есть устройства типов `Сетевое оборудование`/`Средство защиты информации`,
  нужно явное подтверждение, что эти устройства и вся их «дочерняя» история (интерфейсы,
  подключения, VLAN-привязки, размещённые ВМ, ПО, связи с ИС) не нужны — восстановить их после
  миграции нельзя, `downgrade()` этой ревизии сознательно поднимает исключение вместо тихого
  отката только схемы. Проверено на тестовых данных (`backend/tests/test_migrations_diagram.py`),
  не на продовой истории миграций конкретного инстанса.
- **Экспорт диаграммы в `.vsdx` (2.64.0) — не точная копия `.svg`/`.drawio`.** Библиотека `vsdx`
  устроена как редактор уже существующего файла, а не конструктор объектной модели с нуля;
  геометрия узла воспроизводится копированием готовой фигуры-прямоугольника из встроенного
  шаблона пакета, без отдельных фигур-засечек портов на switch-устройствах (в `.svg`/`.drawio` они
  есть). Если библиотека получит более высокоуровневый API в будущей версии — стоит пересмотреть
  `backend/app/services/diagram_export.py:export_vsdx`.

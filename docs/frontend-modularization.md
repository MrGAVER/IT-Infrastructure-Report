# Модуляризация фронтенда: анализ и рекомендация

> **Архивный документ.** Касается `frontend/` — старого vanilla-фронтенда, удалённого в 2.60.0
> вместе с раздачей `/legacy` (см. корневой `README.md`, «Изменения» и раздел «Модуляризация
> фронтенда (архив)»). Файлы, упомянутые ниже (`frontend/static/app.js` и т.д.), в текущем
> дереве исходников больше не существуют — сохранено как историческое обоснование решения,
> актуальное на момент, когда `frontend/` ещё существовал.

Дата: 2026-08-13. Контекст: `frontend/static/app.js` (982 строки, 140 функций верхнего уровня),
`frontend/static/report_builder.js` (375 строк) — оба подключены как обычные `<script defer>` в
`frontend/index.html`, без сборщика. В README (запись 2.35.0) уже зафиксировано, что разбиение
`app.js` на модули один раз сознательно отклонили как рискованное для текущей архитектуры — этот
документ разбирает вопрос заново, предметно, с учётом конкретных цифр по проекту.

## Почему это на самом деле рискованно — конкретная причина

Вся вёрстка генерируется шаблонными строками с инлайн-обработчиками:

```js
`<button onclick="removeVMIPRow(${i})">Удалить</button>`
```

В `app.js` таких `onclick=` — **71**, в `report_builder.js` — **30**, плюс 22 `onchange=`.
Инлайн-обработчик резолвится браузером через **глобальную область видимости** (`window.*`).
Обычный ES-модуль (`<script type="module">`) не кладёт свои функции в `window` автоматически —
значит простое переименование `<script src="app.js">` → `<script type="module" src="app.js">`
сразу сломает все 101+ обработчик молча (в рантайме, не на этапе загрузки).

Это и есть причина прошлого отказа, и она объективна — вопрос не в том, «делать или нет», а в том,
**как разбить, не задев этот механизм**.

## Рассмотренные варианты

### Вариант A — полноценные ES-модули (`type="module"`)
Правильный современный подход, но требует одновременно с разбиением на файлы переписать все 101+
`onclick=/onchange=` на `addEventListener` (делегирование событий) — то есть это не рефакторинг
структуры, а полноценный рефакторинг механизма рендеринга UI. Большой объём изменений в файле без
единого теста на фронтенде (frontend тестов сейчас нет вообще) — высокий риск регрессии, которую
некому будет поймать автоматически до ручного прогона.

### Вариант B — фреймворк (React/Vue/Svelte)
Требует сборщика (Vite/webpack), полного переписывания рендеринга ~140 функций и всех форм/таблиц,
скорее всего — недели работы с нуля для проекта такого размера, при этом функционально ничего не
добавляет пользователю. Оправдан, если и когда проект дорастёт до потребности в сложном
клиентском состоянии (сейчас состояние в основном — «текущий открытый ресурс + данные формы»,
без пересекающихся живых обновлений между частями экрана). На сегодняшнем этапе — избыточно
рискованное вложение при нулевом тестовом покрытии фронтенда.

### Вариант C — расширение существующего паттерна (рекомендуется)
В файле уже есть подходящий прецедент — `attachNestedListEditor()` (строка 306): общая фабрика,
переиспользуемая для VM IP / открытых портов VM / открытых портов устройства / ПО VM. Это и есть
модуляризация *по смыслу*, только без файловой границы. Дальнейший шаг — раздвинуть её и на
файловый уровень, не трогая механизм `onclick`:

1. **Разбить на несколько `<script defer>` без `type="module"`**, каждый — plain script в общей
   глобальной области видимости (как сейчас), но по файлам вместо одного. Ничего не ломается:
   `onclick="foo()"` продолжает резолвиться в `window.foo`, потому что классические `<script>`
   (не модули) кладут свои top-level `function` в `window` как и раньше.
   Порядок файлов в `index.html` заменяет `import`:
   ```html
   <script src="/static/core/http.js" defer></script>       <!-- get(), esc(), parseApiError() -->
   <script src="/static/core/nested-editor.js" defer></script> <!-- attachNestedListEditor() -->
   <script src="/static/resources/devices.js" defer></script>
   <script src="/static/resources/information-systems.js" defer></script>
   <script src="/static/resources/vms.js" defer></script>
   <script src="/static/app.js" defer></script>              <!-- routing, dashboard, list/table -->
   ```
   Это чисто механическое разбиение (copy-paste функций в новые файлы по зонам ответственности,
   видным уже сейчас — блоки `VM IP`, `открытые порты`, `ИС`, `устройства` в файле визуально
   сгруппированы). Риск — на уровне «не забыть скопировать функцию» и проверяется тем же
   `node --check` на каждый файл + ручной прогон.
2. Как только это сделано, при желании **постепенно** внутри каждого файла обработчики можно
   заменить на `addEventListener` с делегированием (без изменения границ файлов) — это уже
   безопасно делать маленькими шагами по одному файлу за раз, а не всё сразу.
3. Framework (вариант A/B) остаётся опцией на будущее, когда/если появится реальный драйвер
   (например, необходимость в живых обновлениях нескольких независимых виджетов на одном экране).

## Рекомендация

Делать **вариант C**, поэтапно, начиная с наименее связанных зон (справочники → устройства →
информационные системы, в порядке роста связности), и **не переходить на фреймворк сейчас** —
у проекта нет ни сборочной инфраструктуры, ни тестового покрытия фронтенда, которые оправдали бы
инвестицию, а плоское разбиение файлов даёт большую часть выгоды (читаемость, границы
ответственности, меньшие диффы в review) почти без риска.

Предварительное условие, которое стоит закрыть раньше или параллельно: **тесты фронтенда**.
Сейчас нет ни одного (ни unit, ни e2e) — прежде чем безопасно двигать функции между файлами или
менять `onclick` на `addEventListener`, стоит завести хотя бы smoke-тесты на Playwright/Puppeteer
для 3–5 ключевых сценариев (создать устройство, создать ИС, сгенерировать отчёт) — они будут
единственной защитой от молчаливой регрессии при любом из описанных вариантов.

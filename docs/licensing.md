# Лицензирование и защита от несанкционированного использования

Документ описывает схему лицензионных ключей РИС: что в ключе, как он проверяется, от чего защищает и — так же
важно — от чего **не** защищает. Код: `backend/app/licensing/`, вендорский CLI: `tools/license_admin.py`.

## 1. Принцип

Ключ — это **подписанный документ**. Вендор подписывает его приватным ключом Ed25519, приложение проверяет подпись
встроенным *публичным* ключом. Из этого следует всё остальное:

- подделать или «продлить» ключ нельзя, не имея приватного ключа; в приложении его нет и извлекать нечего;
- приложение работает **офлайн** — серверу активации не нужен доступ в сеть (закрытые контуры — основной сценарий РИС);
- выпускать ключи можно на любом компьютере, где лежит приватный ключ, без инфраструктуры.

Цена офлайн-схемы — **отозвать выданный ключ нельзя**, можно лишь дождаться окончания срока. Поэтому выдавайте
временные ключи и продлевайте их (см. §6).

## 2. Что в ключе

Токен: `RIS1.<kid>.<содержимое base64url(JSON)>.<подпись base64url>`. Подписываются сами байты содержимого вместе с
префиксом формата и `kid` (идентификатором ключа подписи): подпись нельзя перенести на токен другого формата или с другим
`kid`, а канонизация JSON не нужна.

| Поле | Смысл |
|---|---|
| `id` | уникальный идентификатор ключа (для журнала и поддержки) |
| `product` | `infra-registry`; ключ другого продукта отвергается |
| `licensee` | на кого выдан — показывается в интерфейсе |
| `iat`, `nbf` | выдан / действует с (секунды Unix, UTC) |
| `exp` | действует до; **нет поля — постоянный ключ**, есть — временный |
| `grace_days` | льготный период после `exp` (0–365): полная работа с предупреждением, окно на продление |
| `bind` | привязки (см. ниже) |
| `claims` | любые подписанные данные без проверки на хосте (`edition`, `max_devices`, …) для будущих ограничений |

Модели **закрыты** (`extra="forbid"`): ключ с неизвестным полем отвергается целиком, а не принимается с потерей
части ограничений.

### Привязки (`bind`)

Измерения комбинируются по **И**: ключ действует, только если совпали все заданные.

| Измерение | Как проверяется |
|---|---|
| `ips` + `networks` | **одно** измерение «адрес»: у хоста есть адрес, равный одному из `ips` или входящий в одну из `networks`. Хост может иметь несколько адресов — достаточно любого. IPv4 и IPv6 не смешиваются; `::ffff:10.0.0.5` приводится к IPv4 |
| `hostnames` | имя компьютера без учёта регистра; допускается шаблон (`srv-*`); `srv-205.corp.local` подходит под `srv-205` |
| `params` | произвольные пары «имя → значение»; значение хоста должно совпасть точно |

Параметры хоста, известные приложению: `os`, `machine_id` (SHA-256 от идентификатора машины ОС — сам идентификатор
не покидает компьютер) и любые `INFRA_REGISTRY_LICENSE_PARAM_<ИМЯ>=значение`, заданные администратором («токены
конфигурации»: площадка, договор, отдел). Встроенные параметры нельзя перекрыть переменной окружения.

**Fail closed.** Если измерение нельзя определить (нет сети — не узнать адрес; нет `machine_id`), ключ, привязанный к нему,
не совпадает. Привязка, подходящая любому хосту (`0.0.0.0/0`, `127.0.0.1`, `*`), **не принимается при выпуске и при
проверке**: «привязанный» ключ не может незаметно оказаться непривязанным. Ключ без привязок CLI выпускает только с
явным `--unbound`.

## 3. Порядок проверки

`evaluate_token` — чистая функция (время и хост передаются снаружи):

1. разбор структуры и длин → `INVALID: malformed / too_long / empty`;
2. **подпись** → `INVALID: unknown_key / bad_signature` — до разбора содержимого: недоверенный JSON не парсится;
3. содержимое → `INVALID: bad_payload`; продукт → `INVALID: wrong_product`;
4. **привязки** → `MISMATCH` (с перечнем несовпавших измерений: `address`, `hostname`, `param:<имя>`);
5. **срок** → `NOT_YET_VALID / VALID / GRACE / EXPIRED`.

Привязка проверяется раньше срока: чужой просроченный ключ сообщает «не для этого компьютера», а не «просрочен».

## 4. Что происходит без лицензии

`LicenseGateMiddleware` — самый внешний слой после CORS/Host/клиентского фильтра, **снаружи** проверки аутентификации:
запись закрыта независимо от роли.

- `INFRA_REGISTRY_LICENSE_MODE=readonly` (по умолчанию): чтение работает, любая запись и формирование отчётов → `402 LICENSE_REQUIRED`;
- `block`: `402` на весь API.

Данные реестра не берутся в заложники: просроченная лицензия не лишает организацию доступа к её записям. Всегда
доступны: оболочка интерфейса (иначе не нарисовать экран активации), `/api/v1/health`, `/api/v1/auth/*` (чтобы
администратор мог войти) и `/api/v1/license`.

Активация (`POST /api/v1/license`, `{"key": "..."}`) проверяет ключ **полностью на этом компьютере** и только потом
сохраняет его (`license.key` в каталоге данных, права 0600, атомарная запись). Негодный ключ не затирает рабочий.
При включённой аутентификации нужен администратор; при выключенной — те же условия, что у первичной настройки
(localhost или `X-Setup-Token`). Состояние лицензии перепроверяется раз в 30 с, поэтому окончание срока подхватывается
без перезапуска.

## 5. Защита от взлома: модель угроз

| Атака | Мера | Остаточный риск |
|---|---|---|
| Выдумать ключ | подпись Ed25519; приватного ключа в приложении нет | — |
| Править ключ (продлить срок, снять привязку) | подпись покрывает все байты содержимого | — |
| Перенести подпись на другой `kid`/формат | `kid` и префикс формата входят в подписываемое сообщение | — |
| Подсунуть ключ с «лишними» полями или привязкой «ко всем» | закрытые модели, запрет вырожденных привязок при выпуске и проверке | — |
| Скопировать ключ на другой компьютер | привязка к адресу/подсети/имени/`machine_id` | имя и адрес можно сменить: привязка к ним — организационный барьер. Надёжнее `machine_id`, но и он подделывается привилегированным пользователем |
| Откатить системные часы, чтобы продлить временный ключ | «верхняя отметка времени» (high-water mark): время не идёт назад; состояние подписано HMAC от `machine_id`; о расхождении сообщает `clock_rollback` | удаление файла `license_state.json` сбрасывает отметку; HMAC-секрет выводится из данных компьютера, а не хранится отдельно |
| Подменить результат проверки через переменные окружения | `INFRA_REGISTRY_LICENSE_ENFORCEMENT=off` **не действует в собранном EXE** | см. ниже |
| Подменить публичный ключ в приложении | — | **см. ниже** |
| Атаки на сам процесс (отладчик, патч байткода) | — | **см. ниже** |
| Украсть приватный ключ вендора | рекомендуется парольная фраза (`--ask-passphrase`), хранение вне репозитория; `kid` позволяет ротацию | при утрате контроля — новый `kid`, новая версия приложения, перевыпуск ключей |
| Перебор/спам эндпоинта активации | проверка подписи — доли миллисекунды; ограничение длины токена 16 КБ и тела запроса 20 000 символов | — |
| Утечка ключа через API/журнал | `GET /api/v1/license` не возвращает ни ключ, ни подпись, ни значения параметров привязки (только их имена); в журнал ключ не пишется | — |

### Честные границы

**Лицензия на стороне клиента не может быть непробиваемой.** Тот, кто контролирует компьютер, на котором запущено
приложение, может его изменить:

- **Docker-образ и запуск из исходников** содержат читаемый Python-код — проверку можно убрать правкой одной строки.
  Для них лицензия — *договорная* защита с технической поддержкой честного исполнения, а не барьер.
- **Собранный EXE** (PyInstaller) защищён лучше, но не абсолютно: байткод извлекается, публичный ключ подменяется.
  Обфускация и упаковщики лишь повышают цену; мы сознательно их не добавляем, чтобы не ломать сборку, не провоцировать
  антивирусные срабатывания и не вносить непрозрачность в программу, которая работает в защищённых контурах.

Практическая защита — это сочетание: подпись (нельзя выдать ключ себе), **короткие временные ключи с продлением**
(взлом «стареет» вместе с версией), привязка к хосту (нельзя просто раздать), договор и аудит. Для максимальной
стойкости критичную логику выносят на сервер вендора — для офлайн-продукта это невозможно по условию.

## 6. Эксплуатация

### Первая настройка (один раз, у вендора)

```bash
python tools/license_admin.py gen-keypair --kid k1 --ask-passphrase
# → license_keys/k1.private.pem (0600, вне репозитория: папка в .gitignore)
# → печатает строку для backend/app/licensing/keys.py → EMBEDDED_PUBLIC_KEYS
```

Вставьте публичный ключ в `EMBEDDED_PUBLIC_KEYS`, соберите релиз. **Пока набор пуст, проверка лицензии выключена**
(приложение работает как раньше) — релизная сборка обязана содержать ключ. Сделайте резервную копию приватного ключа:
без него новые ключи не выпустить.

### Выпуск ключа

Клиент присылает сведения о своём компьютере: `InfraRegistry.exe --license-info` (или `GET /api/v1/license`, поле `host`).

```bash
# временный, на год, с подсетью, шаблоном имени и произвольными данными
python tools/license_admin.py issue --licensee 'ООО «Организация»' --days 365 --grace-days 14 \
    --network 10.20.0.0/16 --hostname 'srv-*' --claim edition=pro --claim max_devices=500 --out client.lic

# постоянный, на конкретную машину
python tools/license_admin.py issue --licensee 'ООО «Организация»' --perpetual \
    --ip 192.168.1.205 --bind-param machine_id=958cb539779791d6d919782081485e9d --armor

# срок «по дату включительно»
python tools/license_admin.py issue --licensee 'Пилот' --until 2027-03-31 --ip 10.0.0.7
```

Каждый выпуск пишется в `license_keys/issued.jsonl` (без самих токенов): кому, на что, до когда.

### Проверка «подойдёт ли ключ там»

```bash
python tools/license_admin.py inspect client.lic --public-key k1=<ключ> \
    --host-ip 10.20.3.4 --host-name srv-1 --now 2027-01-01      # код выхода 0 — подойдёт
```

### Продление и ротация

- **Продление** — выпуск нового ключа с тем же `licensee`; установка заменяет прежний ключ. Льготный период (`grace_days`)
  оставляет полную работу с предупреждением, пока ключ меняют.
- **Ротация ключа подписи** — создайте `k2`, добавьте его публичный ключ в `EMBEDDED_PUBLIC_KEYS` **рядом** с `k1`,
  выпустите версию приложения; новые ключи подписывайте `k2`, а после того как все `k1`-ключи истекут — удалите `k1`.
- **Ошибочный перевод часов вперёд** на стороне клиента — удалить `license_state.json`.

### Настройки (переменные окружения)

| Переменная | Назначение |
|---|---|
| `INFRA_REGISTRY_LICENSE_KEY` | ключ (удобно для Docker secrets); файл `license.key` приоритетнее |
| `INFRA_REGISTRY_LICENSE_FILE`, `…_STATE_FILE` | пути к файлу ключа и состоянию часов (по умолчанию — каталог данных) |
| `INFRA_REGISTRY_LICENSE_ENFORCEMENT` | `auto` (включено, если в сборке есть публичный ключ) / `on` / `off` (не действует в EXE) |
| `INFRA_REGISTRY_LICENSE_MODE` | `readonly` (по умолчанию) / `block` |
| `INFRA_REGISTRY_LICENSE_HOSTNAME`, `…_HOST_IPS` | задать имя и адреса явно (Docker, NAT) |
| `INFRA_REGISTRY_LICENSE_PARAM_<ИМЯ>` | параметр хоста для привязки `params` |

Неверное значение `ENFORCEMENT`/`MODE` — ошибка при старте, а не молчаливый откат к умолчанию.

## 7. Что сделано и что осталось

Сделано: формат и подпись ключа, привязки (адрес, подсеть, имя, параметры), постоянные и временные ключи, льготный
период, защита от отката часов, принуждение на уровне HTTP (readonly/block), активация и состояние через API, вендорский
CLI (выпуск, проверка, журнал, ротация, шифрование приватного ключа), 84 теста.

Не сделано (сознательно, отдельными задачами):

- экран «Настройки → Лицензия» во фронтенде (сейчас активация через API, состояние — в журнале при старте и в `GET /api/v1/license`);
  при включённом принуждении интерфейс до его появления покажет текст ошибки `402` на попытку записи;
- использование `claims` (например, лимит числа устройств) — данные в ключе уже подписываются и отдаются в API;
- предупреждение в интерфейсе за N дней до окончания срока (`days_left` в API уже есть);
- сборка релиза с вшитым публичным ключом в CI — требует решения, где хранится приватный ключ и кто выпускает ключи.
